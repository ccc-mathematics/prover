# 3.3 可信核心 check()：以型別遞迴驗證證明項

3.2 節把一個字串變成了 AST。但 AST 只說了「要證什麼」，還沒有說「證明了沒有」。這一節要看的，就是那個負責回答後者的函式：`check()`。

它是整個 `lean-prover` 裡最重要的一段程式碼，理由不只是它位於中央：它是**唯一有權說「不」的元件**。策略層可以寫錯、可以產生形狀怪異的證明項、可以給出誤導的錯誤訊息，但只要 `check()` 沒有回應「核心檢查失敗」，那個命題就是真的被證明了。第 7.1 節會把這個原則正式命名為 de Bruijn 準則；這裡先把機制看清楚。

## 3.3.1 介面：check(p, ctx, fl) 回傳命題

核心的簽名只有三個參數：

```js
function check(p, ctx, fl = {}) {
  const C = (q, c = ctx) => check(q, c, fl);
  const bad = m => { throw new Error('核心檢查失敗:' + m); };
  const need = (f, t, m) => f.t === t ? f : bad(m + ' 的對象形狀不對');
```
（`lean-prover/src/lean.js:80-83`）

三個參數的意義是這樣的：`p` 是要檢查的**證明項**（3.1 節那棵以規則名為節點的樹），`ctx` 是**上下文**（假設名稱對公式的配對陣列），`fl` 是**旗標物件**，用來往外傳遞「這個證明裡有沒有用到 `sorry`」之類的副作用資訊。

回傳值的型別是**命題**，不是布林值。這是整個設計裡最漂亮的一步棋，值得想清楚為什麼。

一個「布林值」介面的核心會長成這樣：`check(p, ctx)` 傳回 `true` 或 `false`。但那會立刻遇到一個問題：**怎麼知道這個證明項證明了什麼？** 規則 `impE` 的檢查需要知道被消去的函數的前提與結論分別是什麼命題；規則 `andI` 需要知道兩半各是什麼。如果核心只回傳布林值，那所有這些資訊都必須另外找出來——通常做法是「檢查兩次」，第一次問「對不對」，第二次問「證明了什麼」。這不只浪費，也會讓兩次檢查可能不一致。

把回傳值改成命題之後，型別資訊就**沿著遞迴呼叫自然地傳回來**。`C(p.p)` 檢查完子項之後，回傳的就是那個子項的型別；`impE` 拿到 `i = need(C(p.f), 'imp', '→ 消去')`，`i.l` 就是前提、`i.r` 就是結論，於是 `eq(i.l, C(p.a))` 就是在檢查「餵進去的東西型別對不對」。**檢查與推導是同一個動作**——這正是 Curry–Howard 對應的實踐意義：型別檢查器（type checker）從項推出型別，證明檢查器從證明項推出命題，兩者是同一件事。

而且核心回傳的命題還要和 theorem 宣告再比一次：

```js
    const pf = inst(S.assign[g0.id], S.assign), fl = {};
    if (!eq(check(pf, ctx, fl), F)) throw new Error('核心推出的命題與宣告不符');
    r.status = fl.sorry ? 'sorry' : 'done'; r.term = sx(pf);
  } catch (e) { r.status = 'kernel'; r.detail = e.message; }
```
（`lean-prover/src/lean.js:209-212`）

這兩行的分工非常清楚。`check()` 相信證明項，回傳「它證明了什麼」；`eq()` 把它和宣告的結論比一比。兩者不一致就是 `kernel` 狀態——注意 `kernel` 這個詞的份量：它不是「腳本寫錯了」，而是「**核心拒絕了這個證明**」。使用者寫了一堆合法的策略，系統一路綠燈，最後被核心翻臉，這正是可信核心存在的意義。

## 3.3.2 逐條規則巡禮

核心的規則表就是一個 `switch`。我們按「邏輯角色」分組來看。

### 引用與綁定

```js
    case 'hyp': return look(ctx, p.n) || bad('找不到假設 ' + p.n);
    case 'sorry': fl.sorry = true; return p.f;
    case 'meta': return bad('仍有未解決的目標');
    case 'let': return C(p.q, [...ctx, [p.n, C(p.p)]]);
```
（`lean-prover/src/lean.js:85-88`）

`hyp` 是最簡單的規則：在上下文裡找到假設 `p.n`，它的命題就是這個證明項的型別。對應的自然演繹規則是「假設引用」，對應的 Curry–Howard 讀法是「變數」。它的型別推導是：

$$
\frac{x : A \in \Gamma}{\Gamma \vdash \mathrm{hyp}\ x : A}
$$

`let` 是給 `cases` 與 `have` 用的局部綁定。它的型別推導是：

$$
\frac{\Gamma \vdash p_p : A \qquad \Gamma,\, x : A \vdash p_q : B}{\Gamma \vdash \mathrm{let}\ x\ p_p\ p_q : B}
$$

注意實作上的順序：先檢查 `p_p` 拿到它的型別 `A`，把它加進上下文，然後在擴充後的上下文裡檢查 `p_q`。這是「先算值再綁定」的順序，也是 `have` 語意的基礎。

`sorry` 是唯一的作弊通道：它不檢查任何東西，直接回傳 `p.f`（宣稱的型別），但在旗標物件上留一個記號。`runThm()` 最後看這個旗標決定回報 `done` 還是 `sorry`。這裡的設計值得稱讚：**`sorry` 是一個被標記的、有名有姓的逃生門**，不是「悄悄地把命題當成已證」。

`meta` 是「還沒填的洞」。核心遇到它就報錯——這是必然的，因為 `inst()` 應該在呼叫 `check()` 之前就把所有洞填滿。核心在這裡拒絕，是「核心不假設任何關於策略層的東西」這個原則的最後一道保險。

### 合取與析取

```js
    case 'andI': return { t: 'and', l: C(p.a), r: C(p.b) };
    case 'andE1': return need(C(p.p), 'and', '∧ 消去').l;
    case 'andE2': return need(C(p.p), 'and', '∧ 消去').r;
    case 'orI1': return { t: 'or', l: C(p.p), r: p.f };
    case 'orI2': return { t: 'or', l: p.f, r: C(p.p) };
```
（`lean-prover/src/lean.js:89-93`）

`andI` 是「把兩個證明組成一個」，`andE1`/`andE2` 是「拆出其中一半」。`orI1`/`orI2` 是「選一邊」。注意 `orI1` 回傳的 `r: p.f` 不是檢查出來的——`orI1` 的另一邊根本不需要證明，目標型別裡它已經寫在那裡了。這是 `orI1` 與 `andI` 的一個結構差異：`andI` 的兩半都要證明，`orI1` 只需要證明一半、另一半由型別提供。

`orE` 是析取消去，也是整個核心裡最複雜的一條：

```js
    case 'orE': { const o = need(C(p.p), 'or', '∨ 消去'), a = C(p.a, [...ctx, [p.x, o.l]]), b = C(p.b, [...ctx, [p.y, o.r]]); return eq(a, b) ? a : bad('∨ 消去的兩個分支結論不同'); }
```
（`lean-prover/src/lean.js:94`）

它的型別推導是：

$$
\frac{\Gamma \vdash p_d : A \vee B \qquad \Gamma,\, x : A \vdash p_a : C \qquad \Gamma,\, y : B \vdash p_b : C}{\Gamma \vdash \mathrm{orE}\ p_d\ p_a\ p_b : C}
$$

這裡有兩個特徵值得停下來看。

**第一，兩個分支各自擴充上下文。** 左分支拿到 `x : A`，右分支拿到 `y : B`，兩邊的擴充是**平行**的，互不影響。這是自然演繹的標準做法：`cases` 策略產生兩個新目標，每個目標有自己的 `ctx`（3.1 節的 Goal 結構正好承載這件事）。

**第二，兩個分支的結論必須相同。** 這就是 `eq(a, b) ? a : bad('∨ 消去的兩個分支結論不同')`。這是第 2.3 節提到的三個「側條件」之一，也是最容易被誤用的一條：直覺會告訴你「左邊推出 $C$ ，右邊推出 $D$ ，那就得到 $C \vee D$ 」——但那是從 $C$ 與 $D$ 得到 $C \vee D$ ，而析取消去要的是**兩邊都指向同一個 $C$ **。核心在這裡擋下來，是必要的：否則就可以從 $\Gamma \vdash A$ 與 $\Gamma \vdash B$ 推出 $\Gamma \vdash A \vee B$ ，那會讓整個系統的邏輯變成完全不同的東西。

### 蘊含

```js
    case 'impI': return { t: 'imp', l: p.f, r: C(p.p, [...ctx, [p.h, p.f]]) };
    case 'impE': { const i = need(C(p.f), 'imp', '→ 消去'); return eq(i.l, C(p.a)) ? i.r : bad('→ 消去的前提不吻合'); }
```
（`lean-prover/src/lean.js:95-96`）

`impI` 是引入：

$$
\frac{\Gamma \vdash p : B \qquad [x : A \in \Gamma]}{\Gamma \vdash \mathrm{impI}\ x\ p : A \to B}
$$

注意型別的左邊 `p.f` 是**直接拿證明項裡記錄的命題**，不是從子證明推出來的——子證明 `p` 的型別是 $B$ ，不是 $A$ 。所以 $A$ 這個資訊必須由證明項自己攜帶。這是一個重要的設計決定：**證明項必須自足**。如果 $A$ 只能從上下文推導，那麼上下文與命題之間的對應就變成了隱式的約定，核心要嘛信任它、要嘛重新推導它。把它寫進證明項（`impI` 節點的 `f` 欄位）讓核心的檢查變成純粹的局部動作。

`impE` 是消去，也就是 modus ponens：

$$
\frac{\Gamma \vdash p_f : A \to B \qquad \Gamma \vdash p_a : A}{\Gamma \vdash \mathrm{impE}\ p_f\ p_a : B}
$$

實作上只有一行：檢查 `p_f` 的型別是 `imp`，取出它的前提 `i.l`，然後檢查 `p_a` 的型別 `eq(i.l, C(p.a))` 是否吻合；吻合就回傳結論 `i.r`。注意 `C(p.a)` 被**重新檢查**了一遍——不是去問「`p.a` 是不是某個已知的東西」，而是遞迴檢查它、算出它的型別、再比較。這是「核心只有一種權威的型別推導方式」的體現。

### 底、否定與古典性

```js
    case 'botE': need(C(p.p), 'bot', '⊥ 消去'); return p.f;
    case 'dne': { const f = need(C(p.p), 'imp', '反證'); return f.r.t === 'bot' && f.l.t === 'imp' && f.l.r.t === 'bot' ? f.l.l : bad('反證需要 ¬¬A'); }
```
（`lean-prover/src/lean.js:97-98`）

`botE` 是爆炸律：

$$
\frac{\Gamma \vdash p : \bot}{\Gamma \vdash \mathrm{botE}\ p : A}
$$

注意回傳的是 `p.f`——**結論是證明項自己宣告的**，而不是核心推導出來的。核心在這裡只做一件事：確認前提真的是 $\bot$ 。這是合理的，因為從 $\bot$ 可以推出任何東西，核心沒有能力也沒有必要去「推導」那個結論是什麼。

`dne` 是雙重否定消去，也就是古典邏輯的那條規則：

$$
\frac{\Gamma \vdash p : \neg\neg A}{\Gamma \vdash \mathrm{dne}\ p : A}
$$

它的實作是三次形狀檢查：`f.r.t === 'bot'`（外層是 $\neg$ ）、`f.l.t === 'imp'`（內層也是蘊含）、`f.l.r.t === 'bot'`（內層的結論是 $\bot$ ）。三次都對，才從 `f.l.l` 取出那個 $A$ 。

**這三次檢查是整個核心裡最值得玩味的地方。** 在直觀主義邏輯裡， $\neg\neg A \to A$ 是不可推導的；而這裡核心「接受」一個形狀為 $\neg\neg A$ 的前提，然後給出 $A$ 。換句話說，核心裡多了一條規則。這不是 bug，是明確的設計選擇：**古典性不必藏進每一條規則裡，只要被命名為一條獨立的規則，它就能被辨識、被移除、被討論。** 第 6.3、6.4 節會回到這個選擇的代價；README 裡的限制段落也明說了「古典邏輯，`by_contra` 使用雙重否定消去規則」。

順帶說明：`dne` 之所以能在核心裡存在而沒有破壞 Curry–Howard 對應，是因為它並沒有對應到 λ 演算裡的什麼東西——它是一條**額外的、與 Curry–Howard 無關的規則**。這提醒我們 Curry–Howard 對應描述的是「直觀主義命題邏輯」，任何超出它的規則都必須被明確標示。

### 量詞

```js
    case 'allI': { if (ctx.some(([, f]) => fv(f).has(p.v))) bad(`變數 ${p.v} 出現在假設中,不能一般化`); return { t: 'all', v: p.v, f: C(p.p) }; }
    case 'allE': { const a = need(C(p.p), 'all', '∀ 消去'); return sub(a.f, a.v, p.t); }
    case 'exI': return eq(C(p.p), sub(p.f, p.v, p.t)) ? { t: 'ex', v: p.v, f: p.f } : bad('∃ 引入的見證不吻合');
    case 'exE': {
      const e = need(C(p.p), 'ex', '∃ 消去'), r = C(p.q, [...ctx, [p.h, sub(e.f, e.v, { v: p.x })]]);
      if (fv(r).has(p.x) || fv(e).has(p.x) || ctx.some(([, f]) => fv(f).has(p.x))) bad(`變數 ${p.x} 不夠新`);
      return r;
    }
```
（`lean-prover/src/lean.js:99-106`）

`allI` 是 ∀ 引入，型別推導是：

$$
\frac{\Gamma \vdash p : B \qquad x \notin FV(\Gamma)}{\Gamma \vdash \mathrm{allI}\ x\ p : \forall x . B}
$$

側條件 `x \notin FV(\Gamma)` 就是那個「變數不得出現在任何未消去的假設中」——如果上下文裡有 `P(x)`，那麼從 `P(x)` 推出 $\forall x . P(x)$ 是錯的（那會斷言每個東西都滿足 $P$ ）。核心用 `fv()` 檢查上下文裡每個假設的自由變數集合，`fv()` 的細節留到 3.5 節。

`allE` 是 ∀ 消去（實例化）：

$$
\frac{\Gamma \vdash p_f : \forall x . A}{\Gamma \vdash \mathrm{allE}\ p_f\ t : A[t/x]}
$$

實作上，它取出全稱公式的主體 `a.f` 與綁定變數 `a.v`，然後用 `sub()` 做代換。

`exI` 是 ∃ 引入（提供見證）：

$$
\frac{\Gamma \vdash p : A[t/x]}{\Gamma \vdash \mathrm{exI}\ t\ p : \exists x . A}
$$

實作上它比較「`p` 實際證明的東西」和「把 `p.f` 裡的 $x$ 換成見證 `p.t` 之後的東西」，兩者必須相等（`eq` 比較的是 α 等價）。這個比較是必要的：見證與命題必須對得上。

`exE` 是 ∃ 消去，型別推導是：

$$
\frac{\Gamma \vdash p_e : \exists x . A \qquad \Gamma,\, y : A[y/x] \vdash p_q : C \qquad x \notin FV(\Gamma) \cup FV(C)}{\Gamma \vdash \mathrm{exE}\ p_e\ p_q : C}
$$

這個側條件「 $x$ 不夠新」是三個地方共同檢查的：`fv(r).has(p.x)`（結論裡不能洩漏見證變數）、`fv(e).has(p.x)`（被消去的存在公式本身不能洩漏）、`ctx.some(...)`（上下文裡不能有見證變數）。三個條件缺一不可：只要結論或上下文裡還留著見證變數，這個證明就會「洩漏」——從 $\exists x . P(x)$ 推出的東西裡還帶著 $x$ ，那它其實是對某個特定 $x$ 的斷言，而不是對存在者的斷言。

第 3.5 節會回到這個檢查，因為它是「α 等價與變數捕獲」這條線在核心裡的落點。

## 3.3.3 三個輔助工具

核心的規則表要靠三個小工具才寫得這麼短。

**`need()`** 是形狀檢查：

```js
  const need = (f, t, m) => f.t === t ? f : bad(m + ' 的對象形狀不對');
```
（`lean-prover/src/lean.js:83`）

它不只是「檢查」：它**回傳那個被檢查的公式**。這就是 `andE1` 能寫成一行的原因：

```js
    case 'andE1': return need(C(p.p), 'and', '∧ 消去').l;
```

先確認型別是 `and`，然後取左半。檢查與取值合成一步，規則表因此變得非常緊湊。

**`eq()`** 是命題相等：

```js
const eq = (a, b) => key(a) === key(b);
```
（`lean-prover/src/lean.js:57`）

它建立在 `key()` 之上，而 `key()` 是一個做 α 等價正規化的函式（3.5 節詳述）。核心在多處需要它：`impE` 比對前提型別、`orE` 比對兩分支結論、`exI` 比對見證前後。

**`look()`** 是查假設：

```js
const look = (ctx, n) => { for (let i = ctx.length; i--; ) if (ctx[i][0] === n) return ctx[i][1]; };
```
（`lean-prover/src/lean.js:77`）

從後往前找，所以同名重新綁定時後者獲勝（3.1 節提過的設計）。

## 3.3.4 核心完全不依賴策略層

現在可以明確地說出這個架構最重要的性質。

核心的 `check(p, ctx, fl)` 裡，沒有任何一行提到策略、 tactic、腳本、洞或 `S.assign`。它只認得**證明項的形狀**與**公式的形狀**。它不知道證明項是怎麼來的——可能是 `intro` 產生的，可能是使用者手寫塞進去的，也可能是一個精心構造的偽造。

這帶來一個非常實際的後果：**策略層的任何 bug 都不可能讓一個錯誤的證明通過。** 策略可能產生形狀不對的證明項——那會被核心拒絕；策略可能產生型別不對的證明項——同樣被拒絕；策略可能陷入無窮迴圈或當掉——那只是體驗問題，不影響正確性。

第 7.1 節會把這件事正式稱為 **de Bruijn 準則**：一個可信核心必須小到可以被完整地審查，而且必須與所有「可能出錯」的部分隔離。`lean-prover` 的 `check()` 大約三十行有效程式碼，剝掉策略層與解析層之後，它小到可以逐行唸出來確認每一個 `case` 對應的是哪條自然演繹規則。

這也解釋了為什麼核心的**錯誤訊息**要加前綴：

```js
  const bad = m => { throw new Error('核心檢查失敗:' + m); };
```
（`lean-prover/src/lean.js:82`）

「核心檢查失敗」這五個字是一個標籤：它告訴使用者「這不是你的腳本寫錯了，而是我（系統）構造出來的證明項不對」——通常是策略層有 bug。策略層的錯誤則長這樣：

```js
  const is = (t, m) => { if (f.t !== t) throw new Error(`${name} 不適用:目標是 ${fm(f)}${m || ''}`); };
```

## 3.3.5 三欄對照表

把紙上的自然演繹規則、程式裡的規則名、以及 Curry–Howard 對應放在一起：

| 自然演繹規則 | 核心規則名 | Curry–Howard 讀法 |
|---|---|---|
| 假設引用 $\dfrac{x:A\in\Gamma}{\Gamma\vdash x:A}$ | `hyp` | 變數 |
| → 引入 | `impI` | λ-抽象 |
| → 消去（modus ponens） | `impE` | 函數應用 |
| ∧ 引入 | `andI` |  Curry–Howard 對應在命題邏輯層沒有直接對應（需 Church 編碼，見 5.6 節） |
| ∧ 消去 | `andE1` / `andE2` | 投影（需 Church 編碼） |
| ∨ 引入 | `orI1` / `orI2` | 需 Church 編碼 |
| ∨ 消去 | `orE` | 需 Church 編碼 |
| ⊥ 消去 | `botE` | 空型別的消去 |
| ∀ 引入 | `allI` | Π-抽象（多態的抽象） |
| ∀ 消去 | `allE` | Π-消去（實例化） |
| ∃ 引入 | `exI` | Σ-構造子 |
| ∃ 消去 | `exE` | Σ-消去 |
| 雙重否定消去（**古典**） | `dne` | **無對應**（直觀主義 λ 演算沒有這條規則） |
| — | `let` | 局部綁定（let-polymorphism 的雛形） |
| — | `sorry` | 無對應（被標記的逃生門） |
| — | `meta` | 無對應（未填的洞，核心一律拒絕） |

這個表有三個「無對應」值得留意：`dne` 是古典性的標記，`meta` 與 `sorry` 是工程性的機制。其餘每一列在 Curry–Howard 之下都有自然的讀法——`impI`/`impE` 是 λ 抽象與應用，`allI`/`allE` 是 Π 型別的抽象與消去，`exI`/`exE` 是 Σ 型別的構造與消去。第 5 章會把這個表填滿到 λ-Cube 的所有八個系統。

## 3.3.6 小結與交棒

`check()` 用一句話概括：**給定一個證明項與一個上下文，遞迴地推導出它證明的命題，任何形狀不對或側條件不滿足的地方就丟出例外。**

它有三個特徵值得帶走：

1. **回傳命題而不是布林值**，所以檢查與型別推導是同一個動作，資訊不需要被推導兩次。
2. **核心完全不依賴策略層**，所以策略層的 bug 只會讓證明失敗，不會讓錯誤的證明通過——這是 de Bruijn 準則在這個 243 行程式裡的全部內涵。
3. **側條件集中在三個地方**：`orE` 的兩分支同結論、`allI` 的變數不外洩、`exE` 的見證變數新鮮。核心的每一個 `bad()` 都是這三條的表達。

但核心只是**驗收**的環節。真正困難的工作——「使用者只給了一個結論，怎麼把證明找出來」——是由策略層負責的。策略層是整個系統裡最長、最有智慧、也最容易出錯的部分。

下一節就進入策略層：看它如何把一個目標逐步換成新的目標，同時產生一棵帶洞的證明項。
