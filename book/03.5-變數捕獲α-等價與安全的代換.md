# 3.5 變數捕獲、α 等價與安全的代換

前四節把系統從頭到尾走了一遍：字串變成 AST、AST 變成目標、策略把目標換成目標、最後核心驗證證明項。在這條鏈路上，有一個環節一直被我輕輕帶過：**量詞裡的變數綁定**。

它之所以值得單獨一節，是因為它帶來的錯誤**不會被系統抓到**。策略寫錯、型別不吻合、上下文缺假設——這些都會被核心擋下來，回一句「核心檢查失敗」。但如果變數綁定處理得半對半錯，核心會安安靜靜地通過：因為核心檢查的是「證明項確實證明了某個命題」，而那個命題可能根本不是使用者想證的。

## 3.5.1 一個會出事的例子

先看捕獲（capture）是怎麼發生的。

考慮要把一個自由變數 $x$ 換成某個項 $u$ ，而 $u$ 裡含有一個自由變數 $y$ ；同時，被替換的公式裡有一個量詞綁著 $y$ 。公式是 $\forall y . R(x)$ ，要代入的項是 $y$ （把 $y$ 當成一個項變數）。天真的代換會得到：

$$
\forall y . R(y)
$$

但這是**錯的**。原來的 $R(y)$ 中，被綁定的 $y$ 與項裡的自由 $y$ 是兩個不同的東西；代換之後它們重合了，量詞把項裡那個本該自由的 $y$ 綁了起來——這就是「變數捕獲」。 $\forall y . R(y)$ 說的是「對每個 $y$ ， $R$ 對 $y$ 成立」，而我們原本要表達的是「對每個 $y_0$ ， $R$ 對那個特定的 $y$ 成立」。兩者的強度完全不同。

這個例子在本專案裡不是假想的：`intro` 在處理 $\forall$ 目標時做的正是「改名 + 代換」（3.4 節），`cases` 在處理 $\exists$ 目標時做的也是同一件事（3.4 節）。如果這套機制錯了，`intro x` 與 `cases h with x hx` 就會悄悄產生錯的目標。

順帶一提，本專案的 `intro` 對 $\forall$ 做的其實是**改名**而不是代換：它把綁定變數 $x$ 換成一個新名字 $h$ ，得到 $\forall h . A(h)$ ，然後把主體裡的 $x$ 換成 $h$ 。這個操作天然就要求 $h$ 是個全新的名字，否則就會重演捕獲。

## 3.5.2 key()：把綁定變數換成位置編號

解決問題有兩條路：**避免捕獲**（代換時小心改名）與**正視捕獲**（用某種指標系統，讓捕獲在原理上不可能發生）。本專案走的是第一條路，而它的基礎設施是 `key()`。

```js
const kt = (t, e) => t.v !== undefined ? (e[t.v] || 'v:' + t.v) : t.f + '(' + t.a.map(x => kt(x, e)).join(',') + ')';
const key = (f, e = {}, d = 0) => f.t === 'bot' ? '⊥' : f.t === 'atom' ? f.n + '(' + f.a.map(t => kt(t, e)).join(',') + ')'
  : f.t === 'all' || f.t === 'ex' ? f.t + '.' + key(f.f, { ...e, [f.v]: '#' + d }, d + 1) : f.t + '(' + key(f.l, e, d) + ',' + key(f.r, e, d) + ')';
const eq = (a, b) => key(a) === key(b);
```
（`lean-prover/src/lean.js:54-57`）

`key()` 把一個公式轉成一個字串，**使得兩個公式 α 等價當且僅當它們的字串相同**。做法是：走訪公式，遇到量詞就把被綁定的變數記成 `#d`（其中 $d$ 是巢狀深度計數），並且用一個環境 `e` 把這個對應關係往下傳。

`kt()` 是項的部分：`e[t.v]` 查得到就說這個變數是**被綁定的**，用 `#d` 表示；查不到就是**自由的**，用 `v:名字` 表示。

所以：

| 公式 | `key()` | 說明 |
|---|---|---|
| $\forall x . P(x)$ | `all.P(#0)` | 與下一行 α 等價 |
| $\forall y . P(y)$ | `all.P(#0)` | 與上一行 α 等價 |
| $P(x)$ | `P(v:x)` | $x$ 是自由變數 |
| $P(y)$ | `P(v:y)` | $y$ 是自由變數，與上一行**不等價** |
| $\forall x . \forall y . P(x,y)$ | `all.all.P(#0,#1)` | 與下一行 α 等價 |
| $\forall y . \forall x . P(y,x)$ | `all.all.P(#0,#1)` | 與上一行 α 等價 |
| $\forall y . \forall x . P(x,y)$ | `all.all.P(#1,#0)` | 與上一行**不等價** |

前兩行相同，表示 $\forall x . P(x)$ 與 $\forall y . P(y)$ 被判定為相等——它們確實 α 等價（改名而已）。第三、四行不同，表示自由變數**不會**被混淆： $P(x)$ 與 $P(y)$ 是不同的命題。這正是要的行為。

第六、七行是同一件事的兩面，值得多看一眼，因為它顯示「位置編號」不只是換個名字那麼簡單。用**深度**編號的好處是：它能把「只是改名」和「交換了位置」區分開。 $\forall x . \forall y . P(x,y)$ 與 $\forall y . \forall x . P(y,x)$ 說的是同一件事（對所有有序對），所以 key 相同 ✓。但 $\forall y . \forall x . P(x,y)$ 與 $\forall x . \forall y . P(x,y)$ **不是**同一件事——前者是「對每個 $y$ ，對每個 $x$ ， $P(x,y)$ 」，後者是「對每個 $x$ ，對每個 $y$ ， $P(x,y)$ 」——所以 key 不同 ✓。如果這裡只是把綁定變數換成它的名字， $P(x,y)$ 與 $P(y,x)$ 就會被誤判為相等，整個系統的量詞推理會出大錯。

`eq()` 就是 `key(a) === key(b)`。它被核心用在四個地方：`impE` 比對前提型別、`orE` 比對兩分支結論、`exI` 比對見證前後、以及策略層的 `exact`、`show`、`app`。

**這裡有一個值得體會的設計對比**：`key()` 用的是「深度編號 + 名字表」，而 5.7 節的 de Bruijn 索引用的是「相對索引」。兩者都在做「把綁定變數正規化」這件事，但 de Bruijn 索引把綁定關係直接編進資料結構，不需要每次比較時重新正規化。`key()` 每次比較都要走一遍樹，對這個玩具系統完全夠用，但在一個大到需要快取公式相等性的系統裡就會變成瓶頸。

## 3.5.3 sub()：三個步驟的代換

現在來看 `sub()`，也就是真正做代換的函式：

```js
const st = (t, x, u) => t.v !== undefined ? (t.v === x ? u : t) : { f: t.f, a: t.a.map(y => st(y, x, u)) };
function sub(f, x, u) {
  if (f.t === 'bot') return f;
  if (f.t === 'atom') return { ...f, a: f.a.map(t => st(t, x, u)) };
  if (f.t === 'all' || f.t === 'ex') {
    if (f.v === x) return f;
    let v = f.v, b = f.f;
    if (fvt(u).has(v)) { const bad = new Set([...fvt(u), ...fv(f.f), x]); let n = v; while (bad.has(n)) n += "'"; b = sub(b, v, { v: n }); v = n; }
    return { t: f.t, v, f: sub(b, x, u) };
  }
  return { t: f.t, l: sub(f.l, x, u), r: sub(f.r, x, u) };
}
```
（`lean-prover/src/lean.js:65-76`）

先看 `st()`：它在**項**裡面做代換，把項中的變數 $x$ 換成項 $u$ 。項裡沒有綁定（項只有變數與函數應用，沒有量詞），所以**項層級不可能發生捕獲**。捕獲只可能發生在公式層級，因為只有公式才有量詞。這個分工是清楚的：`st` 管項，`sub` 管公式。

再看 `sub()` 的三個分支：

**原子公式**（`atom`）：把每個參數項交給 `st()`。因為項不捕獲，這裡是安全的。

**量詞公式**（`all` / `ex`）——這裡有兩個判斷，順序很重要：

第一個判斷 `if (f.v === x) return f;`：如果正要代入的變數 $x$ **就是**這個量詞綁定的變數，那麼 $x$ 在這裡是綁定的，不是自由的，**不該被代入**。整棵子樹原封不動地返回。這是「代入只作用於自由變數」的規則。

第二個判斷就是捕獲的防護：

```js
    if (fvt(u).has(v)) { const bad = new Set([...fvt(u), ...fv(f.f), x]); let n = v; while (bad.has(n)) n += "'"; b = sub(b, v, { v: n }); v = n; }
```

如果代入項 $u$ 的自由變數集合裡有 $v$ （也就是這個量詞綁定的名字），那麼這個綁定就會**捕捉** $u$ 裡的變數。防護措施是：**先把綁定變數改名**。新的名字 $n$ 從 $v$ 開始，不斷加撇號，直到它不在 `bad` 集合裡為止。`bad` 包含三樣東西：

- `fvt(u)`：代入項的所有自由變數——新名字不能撞上它們。
- `fv(f.f)`：量詞主體的自由變數——新名字不能撞上它們。
- `x`：正要代入的變數本身。

然後 `b = sub(b, v, { v: n })` 這一步是**把主體裡綁定變數的出現一併改名**，最後 `v = n` 把綁定本身也換掉。

回到 3.5.1 的例子： $\forall y . R(x)$ 代入項 $y$ 。`fvt(u) = {'y'}` 包含綁定變數 `y`，所以觸發改名：`bad = {'y'} ∪ fv(R(x)) ∪ {'x'} = {'y','x'}`；`n` 從 `'y'` 開始，但 `'y'` 在 `bad` 裡，所以變成 `"y'"`；`"y'"` 不在 `bad` 裡，於是綁定變數被改名成 $y'$ 。結果是：

$$
\forall y' . R(y)
$$

$u$ 裡的 $y$ 依然是自由的，正確。

還有一個細節值得注意：改名時用的是 `sub(b, v, { v: n })`，也就是**用同一個代換機制去做改名**。這個「自我引用」是安全的，因為 `sub` 對綁定變數有 `if (f.v === x) return f;` 這條規則擋著：內層如果又有同名綁定，那個綁定的作用域裡的出現就**不會**被改名——這正是正確的行為（被遮蔽的出現本來就不屬於外層綁定）。

不過這套機制並非完美。用一個會產生**遮蔽**（shadowing）的例子：把 $x$ 代入 $\forall y . \forall y . R(x)$ ，代入項為 $y$ 。實測結果是 $\forall y' . \forall y' . R(y)$ ——內層與外層的綁定被改名成同一個名字 $y'$ 。語意上這是無害的（內層遮蔽外層，而 $R(y)$ 裡的 $y$ 仍然是自由的），但它顯示「用名字而不是用索引」的方案在巢狀同名綁定時是多麼吃力：它靠「不斷加撇號」這個啟發式規則闖關，而不是靠結構性的保證。第 5.7 節的 de Bruijn 索引就是結構性保證的答案。

## 3.5.4 fv() 與 fvt()：自由變數集合

`sub()` 用到的兩個自由變數函式是：

```js
const fvt = (t, s = new Set()) => { t.v !== undefined ? s.add(t.v) : t.a.forEach(x => fvt(x, s)); return s; };
function fv(f, s = new Set(), b = []) {
  if (f.t === 'atom') f.a.forEach(t => fvt(t).forEach(v => b.includes(v) || s.add(v)));
  else if (f.t === 'all' || f.t === 'ex') fv(f.f, s, [...b, f.v]);
  else if (f.t !== 'bot') { fv(f.l, s, b); fv(f.r, s, b); }
  return s;
}
```
（`lean-prover/src/lean.js:58-64`）

`fvt()` 是項的自由變數：項裡的變數全部自由（因為項沒有綁定），函數應用則遞迴到參數。

`fv()` 是公式的自由變數，它多了一個參數 `b`：**綁定變數清單**。走訪時：

- 遇到原子：把參數項的自由變數加進結果，但**跳過**在綁定清單裡的。
- 遇到量詞：把綁定變數加進清單（`[...b, f.v]`），再走訪主體。
- 遇到蘊含／合取／析取：兩邊共用同一份綁定清單。

實測結果：

| 公式 | `fv()` |
|---|---|
| $\forall x . P(x)$ | $\varnothing$ |
| $\exists x . P(x)$ | $\varnothing$ |
| $\forall x . P(x) \wedge Q(y)$ | $\{y\}$ |
| $P(x)$ | $\{x\}$ |

第一、二行是重點：**量詞裡綁定的變數不算自由變數**。這直接決定了核心的 `allI` 檢查會不會誤判（下一小節）。

## 3.5.5 核心裡的新鮮性檢查

有了 `fv()`，核心就能做那三個側條件檢查了。

**`allI` 的「不能一般化」檢查**：

```js
    case 'allI': { if (ctx.some(([, f]) => fv(f).has(p.v))) bad(`變數 ${p.v} 出現在假設中,不能一般化`); return { t: 'all', v: p.v, f: C(p.p) }; }
```
（`lean-prover/src/lean.js:99`）

條件是：變數 $x$ 不能**自由地**出現在任何假設裡。檢查 `fv(f).has(p.v)` 正好問的是「 $x$ 是不是這個假設的自由變數」。

這裡有個容易誤會的點：假設 $\forall y . P(y)$ 的自由變數集合是**空的**，所以拿 $y$ 去 `allI` 是**允許**的，而且這是對的——因為那個 $y$ 是綁定的，沒有束縛任何自由的 $y$ 。反過來，假設 $P(y)$ （其中 $y$ 自由）就會擋下來。判準的精確性完全取決於 `fv()` 分不分辨自由與綁定。

**`exE` 的「見證變數要夠新」檢查**：

```js
      if (fv(r).has(p.x) || fv(e).has(p.x) || ctx.some(([, f]) => fv(f).has(p.x))) bad(`變數 ${p.x} 不夠新`);
```
（`lean-prover/src/lean.js:104`）

三個條件：結論 $r$ 裡不能有見證變數、被消去的存在公式裡不能有見證變數、上下文裡不能有見證變數。

第三個條件最容易被忽略，但它是對的：假設上下文裡有 `P(x)`（其中 $x$ 自由），而我們從 $\exists y . Q(y)$ 消去出 $x$ ，那個 $x$ 是從外面來的，跟見證變數同名只是巧合——把它擋下來雖然保守，但安全。

第一個條件是「不能洩漏」：從 $\exists x . P(x)$ 推出的結論裡如果還帶著 $x$ ，那這個結論其實是「存在某個特定的 $x$ 使 $P(x)$ 」，而不是「存在某個 $x$ 使 $P(x)$ 」。這不是同一件事。

**`cases` 裡的新鮮變數**：

```js
      if (A.t === 'ex') { fresh(a); if (fv(A).has(a)) throw new Error(`變數名 ${a} 已被使用`); const n = ng([...ctx, [b, sub(A.f, A.v, { v: a })]], f, [...g.vars, a]); return solve({ r: 'exE', p: H, x: a, h: b, q: M(n) }, [n]); }
```
（`lean-prover/src/lean.js:162`）

策略層在這裡先做一次 `fresh(a)`，再做一次 `fv(A).has(a)` 的檢查。兩次的分工是：`fresh` 檢查目標與上下文（`fv(f)` 與 `ctx`），後者檢查存在公式本身。第二個檢查其實是必要的，因為存在公式的**綁定變數**雖然不算自由變數，但見證變數與它同名會讓人困惑——所以策略層額外擋掉。

不過這裡有個有趣的例外正好被系統允許：3.6 節的 `ex_not_all` 範例裡，命令是 `cases h with x hx`，而 $h : \exists x . P(x)$ ——見證變數就叫 `x`，和存在公式的綁定變數同名。這個情況能通過，是因為 `fv(A)` 把綁定變數排除在外了。此時 `A.f`（也就是 $P(x)$ ）裡的 $x$ 被換成新的見證名 $x$ （同名但不同作用域），得到的假設 `hx : P(x)` 裡的 $x$ 指向的是新的見證變數。整個過程之所以安全，靠的是 α 等價： $\exists x . P(x)$ 與 $\exists x' . P(x')$ 是同一個命題。

## 3.5.6 策略層的 fresh()：把錯誤變得友善

核心的檢查是「一切照規矩，最後才發現錯了」；策略層的檢查則是「一開始就擋下來，並且解釋清楚」。`fresh()` 是後者的代表：

```js
  const fresh = x => { if (fv(f).has(x) || ctx.some(([, h]) => fv(h).has(x))) throw new Error(`變數名 ${x} 已被使用,請換一個名稱`); };
```
（`lean-prover/src/lean.js:137`）

它的檢查對象是**目標公式**與**上下文**：新變數名不能是它們任何一個的自由變數。這正是 `intro` 在處理 $\forall$ 目標時需要的保證——把 $\forall x . A(x)$ 改名成 $\forall h . A(h)$ 的前提是 $h$ 真的是新的。

順帶說明 `intro` 的預設名稱：目標是 $\forall$ 時預設用 `x`，否則用 `h`。而 `intro x` 在目標是 $\forall y . P(y)$ 時**會被拒絕**，因為 $x$ 已經是 $y$ 的主體裡的自由變數（ $P(y)$ 裡的 $y$ 是自由的）。使用者必須換一個名字。這正是 3.2 節那個 `¬` 顯示問題的同一類困擾：**變數命名在這裡是一個使用者必須參與的推理步驟**，不是系統可以自動解決的細節。

`fresh()` 的存在也讓我們看清一件事：如果核心的 `allI` 檢查和策略層的 `fresh()` 都不存在，會發生什麼？核心的檢查是**最後一道防線**：策略可能產生一個把變數錯誤一般化的證明項，核心會把它擋下來。策略層的檢查是**第一道防線**：它讓錯誤在使用者剛打完指令時就以一句人話回報（「變數名 x 已被使用,請換一個名稱」），而不是在幾十行之後以一句核心錯誤回報。

兩道防線都要有。這是第 7 章「策略層設計」主題的具體樣本：**友善的策略層 + 嚴格的核心**。

## 3.5.7 這套辦法的代價

把 `key()` / `sub()` / `fv()` 這套「用名字 + 啟發式改名」的做法，和第 5 章的 de Bruijn 索引對照一下：

| | 名字 + 啟發式改名（本專案） | de Bruijn 索引（第 5 章） |
|---|---|---|
| 綁定的表示 | 變數名 + 綁定結構 | 索引（相對距離） |
| 避免捕獲 | 代換時手動改名（加撇號） | **結構上不可能** |
| α 等價比較 | 每次比較都重新正規化成字串 | 索引相同即 α 等價 |
| 缺點 | 啟發式；巢狀同名綁定會產生遮蔽；`key()` 每次比較都要走樹 | 公式不再是人讀的形狀，錯誤訊息難寫 |

`lean.js` 選了前者，是因為它只有 243 行，而且使用者要直接閱讀錯誤訊息——「變數 x 不夠新」比「索引 3 與索引 7 不匹配」有用得多。`cube.js` 選了後者，因為它要處理的是**項**而不是命題，而項裡的綁定（λ 抽象）出現得極其頻繁，每次比較都重新正規化是不可接受的。

**這個取捨本身就是一課**：資料表示的選擇不是「哪個更聰明」，而是「哪個的失敗模式更可以接受」。名字方案的失敗模式是「多繞一個彎還算對」；索引方案的失敗模式是「使用者完全看不懂系統在說什麼」。

## 3.5.8 小結與交棒

本節的主題可以濃縮成三句話：

1. **捕獲是必須防範的**：量詞的綁定與代入項的自由變數撞名，就會把自由變數綁走。`sub()` 的防線是「綁定變數改名成 $v', v'', \ldots$ 」，並且用 `bad` 集合保證新名字與代入項、主體、待代入變數都不撞。
2. **α 等價要能判**：核心在多處需要「兩個命題是不是同一個」，`key()` 把綁定變數換成位置編號，使得 $\forall x . P(x) \equiv \forall y . P(y)$ 而 $P(x) \not\equiv P(y)$ 。
3. **新鮮性是雙向的**：核心在 `allI` 與 `exE` 做嚴格的形式檢查，策略層的 `fresh()` 做友善的預警檢查；兩者不可互相取代。
