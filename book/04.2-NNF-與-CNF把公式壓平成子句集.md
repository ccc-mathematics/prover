# 4.2 NNF 與 CNF：把公式壓平成子句集

第 4.1 節把整個 ATP 的分工講清楚了：人給前提與結論，機器自己找矛盾。當時我們把「子句化」整包當成 ATP 的第一根支柱，只看了它的一行入口：

```js
const clausify = f => cnf(skolem(nnf(f, true), {}, []));
```

（`theorem-prover/src/prover.js:74`）

一行之內串了三個轉換：NNF、Skolem 化、CNF。本節要把前兩步中的第一步（NNF）與第三步（CNF）拆開，並回答一個更前面的問題：**人類寫的公式長什麼樣子？為什麼必須先被改寫成某種特定形狀，歸結法才肯吃？**

答案藏在一個很实际的細節裡：歸結法的推理規則是「兩個子句，各取一個文字，若互為否定且能合一，就產生一個新子句」。這條規則裡出現的每一個詞——「子句」「文字」「互為否定」——都預設了公式已經被壓平成「文字的析取」。壓平的工作，就是本節的主題。

## parse()：把字串變成樹

`parse()`（`theorem-prover/src/prover.js:7-42`）是一個手寫的遞迴下降解析器。它的第一件事是換詞與斷詞：

```js
const T = src.replace(/[∀∃¬∧∨→↔⊃]/g, c => SYM[c]).match(/<->|->|!=|[A-Za-z_][\w']*|\S/g) || [];
```

（`theorem-prover/src/prover.js:8`）用戶可以打全形符號 `∀ ∃ ¬ ∧ ∨ → ↔`，第一個 `replace` 把它們統一換成 ASCII 形式（映射表在第 4 行，`⊃` 也被當成 `->`）。第二個 `match` 用正規表達式切出詞元，注意交替的順序：`<->` 必須排在 `->` 前面，否則 `<->` 會被切成 `<` 加 `->`；`!=` 排在識別字之後，但因為識別字不會以 `!` 開頭，順序無礙。識別字樣式 `[A-Za-z_][\w']*` 允許出現撇號，所以 `x'` 是一個合法的變數名——這是邏輯學傳統中表示「下一個變數」的寫法。

斷完詞之後，解析器用一組互相巢狀的函式表達優先序（`theorem-prover/src/prover.js:16-19`）：

```js
const iff = () => { let l = imp(); while (peek() === '<->') { p++; l = { t: 'iff', l, r: imp() }; } return l; };
const imp = () => { const l = or(); if (peek() === '->') { p++; return { t: 'imp', l, r: imp() }; } return l; };
const or = () => { let l = and(); while (peek() === '|') { p++; l = { t: 'or', l, r: and() }; } return l; };
const and = () => { let l = un(); while (peek() === '&') { p++; l = { t: 'and', l, r: un() }; } return l; };
```

這四行的排列順序就是優先序：`iff` 最鬆、`imp` 次之、`or` 再次、`and` 最緊。實作上最容易出錯的地方是 `imp` 用了右遞迴（`imp()` 而不是 `or()`），這讓 `P -> Q -> R` 解析成 `P -> (Q -> R)`，符合數學慣例的右結合。`iff`、`or`、`and` 則用迴圈處理左結合，讓 `P & Q & R` 變成 `(P & Q) & R`。

### 變數與常數的分界線

一階邏輯裡 `x` 與 `a` 的差別不在字面，而在「有沒有人綁定它」。這個解析器用一個叫 `bound` 的堆疊記錄當前被量詞綁定的名字：

```js
const term = () => { const n = ident(); if (peek() === '(') { p++; return { f: n, a: args(term) }; } return bound.includes(n) ? { v: n } : { f: n, a: [] }; };
```

（`theorem-prover/src/prover.js:15`）三種項（term）因此有三種表示法：帶引數的是 `{ f: 名稱, a: 引數 }`，被綁定的是 `{ v: 名稱 }`，其餘是 `{ f: 名稱, a: [] }`（常數）。`bound` 是一個陣列，在遇到量詞時壓入、離開量詞範圍時彈出（`theorem-prover/src/prover.js:26`）：

```js
p++; bound.push(...vs); const f = iff(); bound.length -= vs.length;
```

所以 `forall x. P(x) & Q(x)` 裡的 `x` 是變數，而 `Man(socrates)` 裡的 `socrates` 永遠是常數——`bound` 裡沒有它。

### 等式的解析

等式 `a = b` 與不等式 `a != b` 在第 32-36 行被特別處理：

```js
if (peek() === '=' || peek() === '!=') { // 等式:t1 = t2 或 t1 != t2
  const neg = T[p++] === '!=', l = a.length || !bound.includes(n) ? { f: n, a } : { v: n };
  const e = { t: 'atom', n: '=', a: [l, term()] };
  return neg ? { t: 'not', f: e } : e;
}
```

（`theorem-prover/src/prover.js:32-36`）三個設計決定值得留意。第一，等式被表示成一個**名字為 `=` 的原子式**，而且它的兩個引數分別是左右兩邊——所以 `=` 與其他謂詞在資料結構上完全平權，這讓後面的合一與代換不必為等式開特例。第二，左右兩邊的處理不對稱：左邊只能是一個名字（可能帶引數），右邊則走完整的 `term()`，因此 `x = f(y)` 合法，但 `f(y) = x` 裡左邊的 `f(y)` 也會被 `a.length` 分支接受。第三，`a != b` 不是獨立的節點，而是 `not(= a b)`。這個決定在第 4.7 節會回報利息：`eqres` 規則要偵測的「否定等式」，到處都寫成「`s` 為假的 `=` 文字」，不需要另一套資料結構。

## nnf()：把否定推到最內層

解析完只是一棵樹，樹上還有 `imp`、`iff`、`not` 三種結構。NNF（Negation Normal Form，否定正規形）要求：**否定只能出現在文字層**——也就是說，一個公式要嘛是非負的原子式，要嘛是 `not` 包住的原子式，要嘛是原子式的 ∧ 或 ∨ 組合。

實作只有六行：

```js
function nnf(f, pos) {
  switch (f.t) {
    case 'atom': return pos ? f : { t: 'not', f };
    case 'not': return nnf(f.f, !pos);
    case 'and': case 'or': return { t: (f.t === 'and') === pos ? 'and' : 'or', l: nnf(f.l, pos), r: nnf(f.r, pos) };
    case 'imp': return nnf({ t: 'or', l: { t: 'not', f: f.l }, r: f.r }, pos);
    case 'iff': return nnf({ t: 'and', l: { t: 'imp', l: f.l, r: f.r }, r: { t: 'imp', l: f.r, r: f.l } }, pos);
    default: return { t: (f.t === 'all') === pos ? 'all' : 'ex', v: f.v, f: nnf(f.f, pos) };
  }
}
```

（`theorem-prover/src/prover.js:50-59`）

`pos` 是一個布林旗標，意思是「我現在處於正polarity 還是負 polarity」。這個技巧把「否定」從一個需要到處傳遞的旗標變成不需要的字串操作——每次遇到 `not` 就把旗標翻轉（`case 'not'`），然後用旗標決定要產生什麼節點。

四個關鍵轉換：

**蘊含**。`case 'imp'` 先把 `P -> Q` 改寫成 `¬P ∨ Q`，再交給 NNF 遞迴處理。所以 `¬(P -> Q)` 會變成 `¬(¬P ∨ Q)`，在 `pos = false` 的情況下 `case 'and'`/`case 'or'` 的德摩根律把它變成 `¬P ∧ ¬Q`。整個過程只多了一層巢狀。

**雙條件**。`P <-> Q` 被改寫成 `(P -> Q) ∧ (Q -> P)`，再各自變成 NNF。這一步在第 3 章的 ITP 裡也出現過——`lean.js` 的解析器在第 17 行做了完全相同的展開。兩邊一致不是巧合：`A ∧ B` 與 `A ↔ B` 在命題邏輯裡本來就同義。

**量詞**。`case 'default'` 處理 `all` 與 `ex`：`(f.t === 'all') === pos ? 'all' : 'ex'`。這一行的意思是——原本是 `∀`，而現在是正 polarity，就維持 `∀`；原本是 `∀` 而現在是負 polarity（公式被否定過），就變成 `∃`。這就是量詞的對偶律：

$$
\neg \forall x\, P(x) \;\equiv\; \exists x\, \neg P(x)
$$

**原子式**。`case 'atom'` 是整個函式的出口：正 polarity 下原子式原樣保留，負 polarity 下包一層 `not`。

### 為什麼一定要 NNF

把否定推到最內層，換來的是一個非常小的「合法文字」集合。NNF 之後，每個文字只可能是 `P(t1, ..., tn)` 或 `¬P(t1, ..., tn)` 兩種形狀；資料結構上則被壓成三個欄位 `{ s: 布林正負號, n: 謂詞名, a: 引數陣列 }`。

這個壓縮是必要的，因為歸結規則要回答兩個問題：**兩個文字是不是互為否定？**（看 `s` 與 `n` 是否相反）以及**它們的引數能不能對齊？**（呼叫 `unifyL`，見第 4.4 節）。如果文字可以是 `¬(P ∧ Q)` 這種形狀，「互為否定」就沒有明確定義，歸結規則得改寫成一堆特殊情形。NNF 把一個可能無窮的公式形狀壓成兩種，歸結規則因此可以用三行寫完：

```js
const unifyL = (a, b, s) => {
  if (a.n !== b.n || a.a.length !== b.a.length) return null;
  for (let i = 0; i < a.a.length && s; i++) s = unify(a.a[i], b.a[i], s);
  return s;
};
```

（`theorem-prover/src/prover.js:87-91`）謂詞名要一樣、元數要一樣、引數要能合一——三個條件就是「這兩個文字是互為否定且可對齊」的全部內容。

## cnf()：分配律的笛卡兒積

NNF 處理完，公式是 `∧` 與 `∨` 的樹。CNF（Conjunctive Normal Form，合取正規形）要求：**整個公式變成若干子句的合取**，每個子句是若干文字的析取。

`cnf()` 是這章最短的函式：

```js
function cnf(f) {
  if (f.t === 'lit') return [[f]];
  const L = cnf(f.l), R = cnf(f.r);
  if (f.t === 'and') return L.concat(R);
  const o = []; for (const a of L) for (const b of R) o.push(a.concat(b)); return o;
}
```

（`theorem-prover/src/prover.js:68-73`）

函式的回傳型別是「子句的陣列」，而每個子句是「文字的陣列」。遞迴基準是 `lit`（一個文字）——回傳 `[[f]]`，即「只有一個子句，其中一個文字」。遞迴步驟對應兩條分配律：

- `A ∧ B`：兩個 CNF 直接串接，`L.concat(R)`。這是正確的，因為

$$
(A_1 \wedge \cdots \wedge A_m) \wedge (B_1 \wedge \cdots \wedge B_n) \;\equiv\; A_1 \wedge \cdots \wedge A_m \wedge B_1 \wedge \cdots \wedge B_n
$$

- `A ∨ B`：做笛卡兒積。

$$
(A_1 \vee \cdots \vee A_m) \vee (B_1 \vee \cdots \vee B_n) \;\equiv\; \bigwedge_{i,j} (A_i \vee B_j)
$$

這就是分配律。

回傳型別的設計讓 `cnf` 的結果天然就是子句集：外層陣列的每個元素是一個子句，內層陣列的每個元素是一個文字。第 4.5 節的搜尋迴圈之所以能只處理「文字的陣列」，全部的功勞都在這個型別。

## 三步串成一條線

`clausify` 把三步接起來：

```js
const clausify = f => cnf(skolem(nnf(f, true), {}, []));
```

（`theorem-prover/src/prover.js:74`）

順序值得停下來想一想：**為什麼是 NNF → Skolem → CNF，而不是 NNF → CNF → Skolem？**

因為 Skolem 化必須在「存在量詞還停在原位」時進行。一個公式裡的 `∃x` 只出現一次，但它的束縛範圍可能跨越多個分支；先做分配律，就會把同一個 `∃x` 複製成好幾份，而每一份都需要用到**同一個** Skolem 項（否則語意就變了）。先做 Skolem 化再分配，Skolem 項只被建立一次，分配時自然地被複製到各個分支，語意自動保持一致。這個「先量化消除、後分配」的順序，是一階邏輯裡一個眾所周知但很容易寫錯的細節。

NNF 的位置也一樣重要：Skolem 化要判斷「這個 `∃` 在不在某個 `∀` 的底下」，而 NNF 會把否定翻轉量詞，所以必須先確定量詞的最終形狀。

整條管線的資料流是這樣的：

```mermaid
flowchart LR
  A["公式字串"] --> B["parse<br/>AST"]
  B --> C["nnf<br/>否定正規形"]
  C --> D["skolem<br/>消去量詞"]
  D --> E["cnf<br/>子句的陣列"]
  E --> F["子句集<br/>第 4.5 節的搜尋空間"]
```

四個階段的輸出型別是刻意遞減的：字串 → 樹 → 樹 → 樹 → 陣列的陣列。越往右，程式碼能做的選擇就越少，而搜尋空間的結構就越整齊。

## 手算：蘇格拉底三段論

現在把 `examples/socrates.txt` 的三行輸入完整走一遍。第一行是 `forall x. (Man(x) -> Mortal(x))`：

1. **parse**：得到 `all(x, imp(Man(x), Mortal(x)))`。
2. **nnf**：`imp` 變成 `¬Man(x) ∨ Mortal(x)`，量詞維持 `all`。結果是 `all(x, or(not Man(x), Mortal(x)))`。
3. **skolem**：`∀x` 被換成一個新鮮變數（實作裡是 `_1` 之類的內部名稱），量詞消失，兩個文字共享這個變數。
4. **cnf**：`or` 節點左右各是一個文字，笛卡兒積得到一個子句。

第二行 `Man(socrates)` 與第三行 `~Mortal(socrates)`（否定結論）則各自產生一個單文字子句。最終的子句集是：

```
~Man(X2) | Mortal(X2)
Man(socrates)
~Mortal(socrates)
```

這正是第 4.1 節看到的輸出。整個過程中值得停下來的最後一件事是：**「否定結論」與「前提」在子句化之後完全沒有分別**。第 4.1 節說過，`prove()` 把否定結論塞進 `items` 陣列之後，三者一起被 `clausify`。這就是歸結法的哲學：既然要找的是矛盾，那麼「前提」與「結論的否定」在搜尋期間只是同一堆子句。

## CNF 爆炸：ATP 的先天代價

CNF 轉換有一個著名的壞處：**它可能讓公式膨脹到指數級**。原因出現在 `cnf()` 的 `or` 分支：每次遇到 `∨`，子句數就乘上另一邊的子句數。

舉一個具體的例子。公式 `((P & Q) | (R & S))` 展開後會變成四個子句：`P | R`、`P | S`、`Q | R`、`Q | S`。如果再多套一層：

```
(((P & Q) | (R & S)) | ((T & U) | (V & W)))
```

子句數就變成十六個。每一層「析取套合取」都讓數字翻一倍。翻倍兩次是十六，翻倍十次就是一千零二十四。

這意味著什麼？意味著**歸結法先天無法處理某些寫法的公式**。命題邏輯裡每一個命題都等價於一個 CNF，但等價的代價可能是指數級的子句數。更糟的是，即使子句數不爆炸，子句的**大小**也會膨脹——原本一個簡潔的公式，轉出來的每個子句都含有一大堆重複的文字。

現代 ATP 對付這個問題有兩招。第一招是**子句化時就選好策略**：不追求最小 CNF，而是用一套「不爆」的轉換（例如 Tseitin 轉換，把每個子公式引入一個新的命題字母，把大小壓到多項式，代價是子句形式不再等價而只是可滿足性等價）。第二招是**不在 CNF 空間裡窮舉**，而是用像 DPLL 這類的 SAT 求解器——它直接工作在子句上，量詞只出現在少數幾個地方。

本實作走的是最古典的路：忠實地把公式轉成 CNF，然後在子句集上做歸結。這條路的優點是簡單、而且轉換本身是**等價的**（不只是可滿足性等價），代價則是題目一寫不好就會爆炸。README 的「限制」段落提到複雜代數題可能逾時，有一部分原因就在這裡。

## 與 ITP 的對照：保留結構 vs 摧毀結構

第 3 章的 `lean-prover` 也做公式轉換，但它做的剛好相反的事。`lean.js` 在第 23 行把 `~A` 展開成 `A → ⊥`，在第 17 行把 `A ↔ B` 展開成 `(A → B) ∧ (B → A)`——和 ATP 一模一樣的兩個展開。

但目的完全相反。ITP 之所以要展開，是因為它的**策略**需要以「可以逐一處理」的形狀看到公式：`intro` 要看到頂端是 `→` 或 `∀`，`cases` 要看到頂端是 `∧` 或 `∨`，`apply` 要把結論一路拆到底。展開讓這些策略有東西可拆，但公式的**主結構**（蘊含、量詞、析取）必須被保留，否則 `intro` 與 `apply` 就無從下手。

ATP 反過來：它不需要策略，因為它不需要「理解」公式——它只需要把公式拆成一堆可以互相消耗的零件。第 4.1 節說過「子句是歸結的最小操作單位」，這句話的深意就在這裡。摧毀結構不是缺陷，而是為了讓推理規則可以用三行寫完的代價。

順帶一提，兩邊都有的 `iff` 展開說明了一件更根本的事： $\leftrightarrow$ 在兩種邏輯裡都不是基本運算，它只是 $\wedge$ 與 $\to$ 的糖。差別在於 ITP 把它展開之後**記得它是什麼**（靠 `constructor` 策略反推），而 ATP 展開之後就再也認不出來了——它只認得一堆文字。

## 下一節

NNF 與 CNF 把公式壓平了，但量詞還沒處理。`forall x. (Man(x) -> Mortal(x))` 轉出來的子句裡，`x` 變成了一個自由的變數——這件事在語意上完全正確，因為子句裡的變數本來就隱含全稱。但「隱含全稱」只處理了 `∀`，那些 `∃` 呢？

第 4.3 節要處理的就是這個問題，以及它帶來的一個關鍵取捨：**Skolem 化可以讓「證明存在」變成「證明矛盾」，但代價是這個轉換在語意上不可逆**。
