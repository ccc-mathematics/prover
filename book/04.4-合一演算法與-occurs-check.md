# 4.4 合一演算法與 occurs check

Skolem 化之後，子句裡只剩下三樣東西：謂詞名、參數、變數。第 4.1 節留下的問題現在到了最尖銳的形狀——**兩個子句要歸結，必須先「對齊」**：

```
~Man(X2) | Mortal(X2)
~Mortal(socrates)
```

這兩個子句一個是變數 `X2`，一個是常數 `socrates`。要把它們配成對，機器必須自己發現：「`X2` 就是 `socrates`」。這個「自己發現」的動作，就是**合一**（unification）。

本節要拆四個函式：`unify`、`unifyL`、`match`、`apply`。它們彼此相似，卻服務於三個不同的用途——**對齊兩個項**（合一）、**把樣式套到具體值上**（匹配）、**把綁定結果套回公式**（套用）。混用這三者是歸結法實作最常見的 bug 來源，所以值得攤開來看。

## 資料結構：替換是什麼樣子

在談演算法之前，先看資料結構。合一過程中的「目前已知綁定」是一個**從變數名到項的映射**，以一個純物件表示：

```js
const isV = t => t.v !== undefined;
```

（`theorem-prover/src/prover.js:47`）一個項要嘛是變數 `{ v: 名稱 }`，要嘛是函數或常數 `{ f: 名稱, a: 引數陣列 }`。`isV` 就是分辨這兩者的唯一依據——**靠欄位存在與否，而不是靠名稱是否以底線開頭**。這一點很重要：使用者可以自由地取名為 `x`、`foo`、`socrates`，程式碼不需要（也不該）猜。

綁定 `s` 的型別是 `{ "x": 項 }`。每次新增綁定都用物件展開 `{ ...s, [a.v]: b }` 產生新物件，而不是就地修改。這樣一來，合一過程中的每個分支都擁有自己的綁定快照，分支失敗時丟棄即可，不必回溯——這是純函式風格帶來的免費回溯機制。

## walk()：解開綁定鏈

```js
const walk = (t, s) => { while (isV(t) && s[t.v]) t = s[t.v]; return t; };
```

（`theorem-prover/src/prover.js:77`）

`walk` 做的事只有一件：**跟著綁定鏈往下走，直到碰到一個非變數的項，或者碰到一個還沒被綁定的變數**。

為什麼需要它？因為綁定可能是鏈式的。合一 `x` 與 `y` 得到 `{ x: y }`；之後再合一 `y` 與 `a` 得到 `{ x: y, y: a }`。此時 `x` 的真正值是 `a`，不是 `y`。`walk(x, s)` 會一路走到 `a`。

注意 `while` 這個細節：`walk` **只追蹤最外層**。如果 `x` 被綁到 `f(y)`，而 `y` 又被綁到 `a`，`walk(x, s)` 只會回傳 `f(y)`，不會遞迴地把 `y` 換成 `a`。這是正確的——`f(y)` 是一個**複合項**，它的內部綁定要在之後由 `apply` 處理。`walk` 與 `apply` 的分工是：`walk` 解開最外層的代換，`apply` 深入到所有子項。

## unify()： Robinson 合一

```js
function unify(a, b, s) {
  a = walk(a, s); b = walk(b, s);
  if (isV(a)) { if (isV(b) && a.v === b.v) return s; return occ(a.v, b, s) ? null : { ...s, [a.v]: b }; }
  if (isV(b)) return unify(b, a, s);
  if (a.f !== b.f || a.a.length !== b.a.length) return null;
  for (let i = 0; i < a.a.length && s; i++) s = unify(a.a[i], b.a[i], s);
  return s;
}
```

（`theorem-prover/src/prover.js:79-86`）

八行，涵蓋了合一的所有情況：

**情況一：兩邊都是變數。** 若 `a.v === b.v`，兩者本來就是同一個變數，回傳原綁定即可。若不同（`x` 對 `y`），就綁定 `x ↦ y`。注意綁定的方向是任意的——`{ x: y }` 與 `{ y: x }` 等價，實作選了前者。

**情況二：一邊是變數。** 綁定變數到另一邊。這裡是 occurs check 發揮作用的地方。

**情況三：兩邊都是複合項。** 必須 `a.f === b.f`（函數名相同）且 `a.a.length === b.a.length`（元數相同），否則立即失敗。通過之後逐個引數遞迴合一，並把綁定一路串下去。迴圈裡的 `&& s` 是一個小細節：一旦某個引數 unification 失敗（`s` 變成 `null`），迴圈就提前結束，`s` 保持 `null`，整個合一失敗。

最後一行 `return s` 回傳的可能是 `null`（失敗），也可能是一個綁定物件（成功）。**失敗用 `null` 表示，而不是丟出例外**——因為在歸結搜尋裡，「這兩個文字對不上」是極其平常的事件，不是錯誤。

舉幾個實際的結果：

- `unify(x, a)` 得到 `{ x: a }`。
- `unify(x, y)` 得到 `{ x: y }`。
- `unify(f(x), f(a))` 得到 `{ x: a }`（先通過名稱與元數檢查，再遞迴到引數）。
- `unify(f(a), g(a))` 得到 `null`（函數名不同）。
- `unify(x, f(x))` 得到 `null`——**這就是 occurs check 的作用**，下面單獨談。

## 為什麼需要 occurs check

如果沒有 occurs check，`unify(x, f(x))` 會回傳 `{ x: f(x) }`。這個綁定是循環的：`x` 的值是 `f(x)`，而 `f(x)` 裡又含有 `x`。它代表的是一個**無限項**（rational tree）：

$$
x = f(x) \;\Longrightarrow\; x = f(f(x)) = f(f(f(x))) = \cdots
$$

在數學上，這種項是合法的（叫「有理樹」），但在這個實作裡會直接炸掉。理由在 `apply`：

```js
const apply = (t, s) => { t = walk(t, s); return isV(t) ? t : { f: t.f, a: t.a.map(x => apply(x, s)) }; };
```

（`theorem-prover/src/prover.js:92`）套用 `{ x: f(x) }` 到 `f(x)` 本身時，`apply` 會遞迴進入引數 `x`，`walk(x, s)` 又回傳 `f(x)`，然後再對 `f(x)` 遞迴……**無限遞迴，呼叫堆疊爆掉**。

所以 occurs check 不是可有可無的「安全帽」，它是「有限項」這個假設的守門人：

```js
const occ = (v, t, s) => { t = walk(t, s); return isV(t) ? t.v === v : t.a.some(x => occ(v, x, s)); };
```

（`theorem-prover/src/prover.js:78`）它檢查變數 `v` 是否出現在項 `t` 裡；出現的話，綁定 `v ↦ t` 會造成循環，合一失敗。

在 `unify` 裡，它出現在最關鍵的那一行：

```js
return occ(a.v, b, s) ? null : { ...s, [a.v]: b };
```

也就是說：**綁定之前先確認不會自噬**。這個實作取的是「最一般合一子」（most general unifier, MGU）——回傳的綁定對所有可能的解都是一般的。這是 Robinson 1965 年那篇論文的技術核心，第 2.4 節會回頭談它的歷史地位。

有一個值得玩味的思想點：occurs check 讓合一在**有限項的宇宙**裡運作，放棄了無限項這個更一般但更難處理的領域。理論上，有限項的合一已經足以讓歸結法完備，所以這個取捨是划算的。

## unifyL()：文字層級的合一

```js
const unifyL = (a, b, s) => {
  if (a.n !== b.n || a.a.length !== b.a.length) return null;
  for (let i = 0; i < a.a.length && s; i++) s = unify(a.a[i], b.a[i], s);
  return s;
};
```

（`theorem-prover/src/prover.js:87-91`）

`unifyL` 是給**文字**用的版本。它比 `unify` 少了「一邊是變數」的分支——因為文字的**謂詞名與元數**必須完全相同，文字本身不可能是一個待綁定的變數。至於引數，則交給 `unify` 逐個處理。

回顧第 4.2 節的設計：NNF 之後，一個文字被壓成 `{ s: 正負號, n: 謂詞名, a: 引數陣列 }`。歸結規則要問「這兩個文字是不是互為否定」，`unifyL` 回答的是「這兩個文字**除了正負號以外**是否相容」。兩者搭配起來就是完整的歸結前提：

- 歸結（第 4.5 節第 179-183 行）：`a.s !== b.s` 且 `unifyL(a, b)` 成功。
- 因子化（第 166-170 行）：`a.s === b.s` 且 `unifyL(a, b)` 成功。

正負號由呼叫端判斷，謂詞名與元數由 `unifyL` 判斷，引數由 `unify` 判斷——三層分工，乾淨俐落。

## match()：單向匹配

```js
function match(p, t, s) { // 單向匹配:只綁定 p 的變數
  if (isV(p)) { const b = s[p.v]; return b ? (ts(b) === ts(t) ? s : null) : { ...s, [p.v]: t }; }
  if (isV(t) || p.f !== t.f || p.a.length !== t.a.length) return null;
  for (let i = 0; i < p.a.length && s; i++) s = match(p.a[i], t.a[i], s);
  return s;
}
```

（`theorem-prover/src/prover.js:98-103`）

`match` 與 `unify` 最重要的差別是**綁定的方向**：`match(p, t, s)` **只綁定 `p`（樣式端）的變數**，`t`（目標端）的變數永遠不被綁定。

這個限制帶來兩個行為上的差異。第一，目標端若是變數而樣式端不是，**直接失敗**（第二行的 `isV(t)` 判斷）。用 `unify` 的話，`unify(a, x)` 會回傳 `{ x: a }`；用 `match` 的話，`match(a, x)` 回傳 `null`。第二，樣式端的變數若已經被綁過，綁定值必須與目標**字面上相同**（第一行的 `ts(b) === ts(t)`），否則失敗。

為什麼要區分這兩者？因為兩者服務的問題不同：

| | `unify(a, b)` | `match(p, t)` |
|---|---|---|
| 方向 | 雙向 | 單向（只綁定 `p`） |
| 用途 | 讓兩個項**指同一個東西** | 讓一個樣式**套在**具體值上 |
| 典型呼叫 | 歸結時配對兩個文字 | 剪枝時判斷「誰比誰強」 |
| 目標端是變數時 | 綁定它 | 失敗 |

第 4.6 節會看到，剪枝需要判斷「子句 C 的每個文字，是否都能在子句 D 裡找到對應」。這個判斷裡，**C 是樣式、D 是目標**：C 裡的變數是「待代入的樣板」，D 裡的變數是「具體值」。如果允許反向綁定，就會把「D 比 C 弱」判成「C 比 D 弱」，剪枝方向整個反過來——系統會丟掉強的子句、保留弱的子句，證明能力反而下降。

## apply() 與 applyL()：把綁定套回去

```js
const apply = (t, s) => { t = walk(t, s); return isV(t) ? t : { f: t.f, a: t.a.map(x => apply(x, s)) }; };
const applyL = (l, s) => ({ s: l.s, n: l.n, a: l.a.map(t => apply(t, s)) });
```

（`theorem-prover/src/prover.js:92-93`）

`apply` 把綁定套回一個項，`applyL` 把綁定套回一個文字。兩者都是**建構新物件**而不是就地修改——原始子句保持不變，這對歸結法至關重要：母句必須還能拿來跟其他子句做運算。

`apply` 的結構值得與 `walk` 對照：`walk` 只處理最外層，`apply` 遞迴處理所有子項。`apply` 的第一行先 `walk`，所以「變數綁到變數、變數再綁到常數」的情況會被一次解決。

## ATP 也需要防範變數捕獲

第 3 章談 ITP 的時候說過「變數捕獲」是自然演繹裡最陰險的一類 bug：在 `∀x. P(x)` 的作用域內把 `x` 換成一個含 `y` 的項，`y` 會被意外束縛。ATP 避免了這個問題——因為它沒有作用域，量詞早就被 Skolem 化掉了。

但 ATP 有自己的版本：**同一個子句被用兩次時，兩份副本必須先分家**。在歸結迴圈裡，「給定子句」與「與它自己歸結」是一個合法情況（第 4.5 節第 177 行）。如果兩份副本共用同一批變數名稱，一邊的合一結果會污染另一邊。

`ren()` 就是為此存在的：

```js
const ren = lits => { const m = {}; const r = t => isV(t) ? (m[t.v] ??= { v: fresh() }) : { f: t.f, a: t.a.map(r) }; return lits.map(l => ({ s: l.s, n: l.n, a: l.a.map(r) })); };
```

（`theorem-prover/src/prover.js:113`）它把子句裡的每個變數重新取名成全新的變數，兩份副本因此互不相干。順帶一提，`ren` 也是每個新子句被接受時（`norm()` 的最後一行）必然會做的事——這就解釋了為什麼輸出裡的變數編號會一路暴增到 `X4612` 這種數字：每產生一個新子句，它的所有變數都會被重新命名。

## 與 ITP 的對照：兩種「代入」

第 3 章的 `lean-prover` 也有代入，但用途完全不同。看它的 `sub`：

```js
function sub(f, x, u) {
  if (f.t === 'bot') return f;
  if (f.t === 'atom') return { ...f, a: f.a.map(t => st(t, x, u)) };
  if (f.t === 'all' || f.t === 'ex') {
    if (f.v === x) return f;
    let v = f.v, b = f.f;
    if (fvt(u).has(v)) { const bad = new Set([...fvt(u), ...fv(f.f), x]); let n = v; while (bad.has(n)) n += "'"; b = sub(b, v, { v: n }); v = n; }
    return { t: f.t, v, f: sub(b, x, u) };
  }
  return { t: f.t, l: sub(f.l, x, u), r: sub(f.r, x, u) };
}
```

（`lean-prover/src/lean.js:66-76`）`sub(f, x, u)` 的意思是「把公式 `f` 裡的自由變數 `x` 換成項 `u`」。它的關鍵在第三段：若 `u` 裡含有將被束縛的變數 `v`，就**先把 `v` 改名**（加撇號）再代入，避免變數捕獲。

把它和 ATP 的 `unify` 並排看：

| | ITP 的 `sub` | ATP 的 `unify` |
|---|---|---|
| 方向 | 單向：指定哪個變數換成什麼 | 雙向：兩個項對齊成同一個 |
| 對象 | 整個**公式**（含量詞） | 一個**項**或一個**文字** |
| 挑戰 | 避免變數捕獲（需要改名） | 避免無限項（需要 occurs check） |
| 誰決定代入 | 證明者寫的策略 | 機器搜出來的綁定 |

兩個系統都在處理「綁定變數的正確性」，但處理的是兩面：ITP 怕的是**捕獲**（把值代進去時誤傷被綁定的變數），ATP 怕的是**自噬**（把變數綁到含自己的項）。前者用改名解決，後者用檢查解決。兩邊都必須付出代價：ITP 的代價是證明項裡可能出現 `x'` 這種惱人的名字，ATP 的代價是放棄了無限項這個更強的理論領域。
