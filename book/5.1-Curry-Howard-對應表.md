# 5.1 Curry-Howard 對應表

第 2.2 節我們講過 Church 在 1934 年把命題邏輯的連接詞寫成 λ 演算的型別算子；第 2.5 節我們講過 Curry 於 1958 年反過來指出這不是類比而是同一件事。整章都在鋪陳那個「同一件事」到底怎麼落到程式碼上；本章第一節的任务，是把這張對應表攤開，然後指出 lambda-cube 這個實作比教科書上的 Curry–Howard 還要更徹底一步。

## 一句話的對應

Curry–Howard 對應最常被濃縮成四句話。把它們對到 lambda-cube 的原始碼上，會發現每一句都有一個可以指名的實作位置：

| 邏輯說法 | 程式說法 | 在 cube.js 裡的樣子 |
|---|---|---|
| 命題即型別 | 一個命題就是一個型別 | `Pi` 節點就是命題，`Sx('Prop')` 是「命題的空間」 |
| 證明即項 | 一個證明就是一個有該型別的項 | `infer()` 回傳型別的函數就是證明檢查器 |
| 假設即 λ 抽象 | 證明 $P \to Q$ 就是把 $P$ 當成局部假設 | `Lm` 節點；策略 `intro` 產生的正是 `Lm` |
| 結論即函數應用 | 用證明推出結論就是把它套上去 | `Ap` 節點；策略 `apply` 產生的正是 `Ap` |

注意這四句並不是四個獨立的主張。前兩句是本體論的宣告：某個東西「是」某個東西。後兩句是句法學的規定：證明的骨頭必須長成什麼樣子。實作上真正吃重的只有後兩句——它們把「證明」從一個自然語言的對象壓縮成一個可以逐節點遞迴檢查的資料結構。`infer()` 就是那個遞迴。

## 完整對應表

下表左欄是命題邏輯與一階邏輯的寫法，中欄是 Curry–Howard 對應出來的型別，右欄是規則名。規則名一欄刻意寫成兩種語言各一組，這正是第 3 章 `lean-prover/src/lean.js` 的 `check()` 函式與第 5 章 `lambda-cube/src/cube.js` 的 `infer()` 函式各自使用的那一套命名：

| 命題 | 型別 | 自然演繹規則（lean.js） | 型別論規則（cube.js） |
|---|---|---|---|
| 原子命題 $P$ | 原子型別 $A$ | 假設 `hyp`（lean.js:85） | 變數 `v`、常數 `c`（cube.js:96、cube.js:98） |
| $P \to Q$ | $A \to B$ （即 $\Pi (x : A). B$ ） | `impI` / `impE`（lean.js:95-96） | `l` / `a`（cube.js:106、cube.js:107） |
| $P \land Q$ | $A \times B$ | `andI` / `andE1` / `andE2`（lean.js:89-91） | 由 Π 定義（見 5.6） |
| $P \lor Q$ | $A + B$ | `orI1` / `orI2` / `orE`（lean.js:92-94） | 由 Π 定義（見 5.6） |
| $P \leftrightarrow Q$ | $(A \to B) \times (B \to A)$ | 解析期展開成兩個 $\wedge$ （lean.js:17） | 由 Π 定義 |
| $\top$ （真） | 單位型 $1$ | `imp`（lean.js:31 的 `True`） | 由 Π 定義 |
| $\bot$ （假） | 空型 $0$ | `botE`（lean.js:97） | `False := forall (C : Prop), C` |
| $\forall x. P(x)$ | $\Pi (x : A). B(x)$ | `allI` / `allE`（lean.js:99-100） | `p`（cube.js:101） |
| $\exists x. P(x)$ | $\Sigma (x : A). B(x)$ | `exI` / `exE`（lean.js:101-102） | 由 Π 定義（見 5.6） |

這張表最重要的一列是最後三列。 $\forall$ 在 Curry–Howard 對應裡**不是**某個獨立的連接詞，它就是 Π 型別本身；而 $\Pi$ 是 λ 演算裡唯一一個「型別的型別」—— $\Pi (x : A). B$ 本身有型別，而它的型別由 $A$ 與 $B$ 的 sort 決定。於是「量化」這件事，在型別論裡退化成一種型別的形成規則，而不是一種推理規則。這正是我們下一節要仔細看的。

## 與第 3 章的逐項對照

第 3 章的 `check()` 是「檢查一個證明項，回傳它證明了什麼」；本章的 `infer()` 是「推斷一個項的型別」。兩者其實是同一件事的兩種視角：`check()` 從證明項出發回推命題，`infer()` 從項出發正推型別。真正一一對應的是**規則**：

- `impI`（lean.js:95）回傳 `{ t: 'imp', l: p.f, r: C(p.p, [...ctx, [p.h, p.f]]) }`。它做的事是：把 `p.f`（前提）放進上下文，檢查 `p.p`（結論）在新上下文下成立。換成型別論的說法：對 `Pi` 節點的 `ty` 做 `sort()` 檢查，再對 `b` 在擴充後的上下文裡做 `infer()`。也就是 cube.js:106 的 `l` 分支：**先確認定義域是型別，再在綁定變數之下推導函數體，最後把兩者組成一個 Π 型別**。

- `impE`（lean.js:96）檢查 `p.f` 的型別是 `imp`，然後要求 `p.a` 的型別與 `p.f` 的前提相等，結果型別是後件。對應 cube.js:107-112 的 `a` 分支：`tf = whnf(infer(ctx, t.f))`，若 `tf.k !== 'p'` 就報「不是函數」；否則 `ta = infer(ctx, t.a)`，並要求 `conv(ta, tf.ty)` 成立，最後回傳 `inst(tf.b, t.a)`。

- `let`（lean.js:88）回傳 `C(p.q, [...ctx, [p.n, C(p.p)]])`，把值綁成一個新假設再檢查主體。對應到 λ 演算就是 $(\lambda x.\, e_2)\, e_1$ ：cube.js:107-112 的 `a` 分支裡，`tf.k === 'l'` 時走 `inst(tf.b, t.a)`，正是把引數代進 body 並把索引降回來。

這三組對照說明一件事：**lean.js 與 cube.js 做的事情在深層是同一件事，只是分別從證明的方向與型別的方向切入。** cube.js 的好處是規則數量少——`infer()` 的 `switch` 只有七個分支（cube.js:95-114），而 `check()` 的 `switch` 有十四個分支（lean.js:84-107）。這不是精簡的美學偏好，而是有因果的：一旦命題的連接詞全部被定義成 Π 型別，型別層就只剩一種需要處理的結構。

## lambda-cube 的徹底化：核心裡沒有連接詞

這裡有一個必須講清楚的差異。在 `lean-prover/src/lean.js` 裡， $\wedge$ 、 $\lor$ 、 $\exists$ 、 $\bot$ 是 AST 的**內建節點**：lean.js:6 的 `GREEK` 表把它們翻譯成關鍵字，lean.js:89-94 與 lean.js:101-102 為它們各寫了專門的規則。核心核心裡因此塞滿了「形狀檢查」——`need(C(p.p), 'and', '∧ 消去')` 這類斷言，用來確認前提真的是一個合取。

在 `lambda-cube/src/cube.js` 裡，**完全沒有這種節點**。核心只有五種項節點：變數 `v`、sort `s`、應用 `a`、λ 抽象 `l`、Π 型別 `p`（cube.js:7-8 的檔頭註解寫得很清楚：「連接詞全由 Π 型別定義出來」），外加常數 `c`、策略用的洞 `m` 與 `sorry` 的 `z`。`infer()` 的 `switch` 裡找不到任何一個分支是「這是 $\wedge$ 」。

$\wedge$ 、 $\lor$ 、 $\exists$ 、 $\bot$ 在這個實作裡是**使用者寫出來的定義**。第 5.6 節會把它們攤開：

```
def And (A B : Prop) : Prop := forall (C : Prop), (A -> B -> C) -> C
def Or (A B : Prop) : Prop := forall (C : Prop), (A -> C) -> (B -> C) -> C
def Ex (A : Prop) (P : A -> Prop) : Prop := forall (C : Prop), (forall (x : A), P x -> C) -> C
```

這三行是 `cube.js:243`、`cube.js:244`、`cube.js:246` 的內建範例裡一字一句拿出來的。它們的意義是：**Curry–Howard 對應在 lambda-cube 裡不是一個被實作的特性，而是一個被假設的前提。** 核心不知道「合取」是什麼，它只知道 Π 型別；「合取」是用戶在 Π 型別之上定義的一個縮寫。

這是「命題即型別」最徹底的版本。教科書上的 Curry–Howard 對應通常會說「 $\wedge$ 對應到笛卡兒積、 $\lor$ 對應到和型別」，那是把連接詞**翻譯**成型別；lambda-cube 反過來，連接詞**本來就**是 Π 型別的某個特例，翻譯步驟被使用者自己寫出來了。

## 這個對應的實際價值

Curry–Howard 對應常被當成美學上的巧合。它其實有三個非常實用的後果，而且這三個後果正是三個專案共同的工程基礎。

**第一，型別檢查就是證明檢查。** 這不是「像」，是同一個程序。在 cube.js 中，檢查一個 theorem 的最後一步是 cube.js:204：

```js
if (!K.conv(K.infer([], full), decl)) throw new Error('核心推出的型別與宣告不符');
```

核心從證明項推出型別，再檢查這個型別與宣告的型別在 `conv` 下相等；不相等就拒絕。lean.js:210 做的是完全等價的事：

```js
if (!eq(check(pf, ctx, fl), F)) throw new Error('核心推出的命題與宣告不符');
```

兩句話的措辭幾乎一樣，因為它們是同一句話。

**第二，錯誤的證明就是型別不吻合。** 一個把 $P$ 當成 $Q$ 用、或把 $P \land Q$ 的兩邊搞反的證明，在 Curry–Howard 之下不是「邏輯錯誤」，而是**型別錯誤**。lambda-cube 的 `apply` 策略在遇到這種情況時，會在 cube.js:111 丟出：

```
型別不吻合:nil 的型別是 Vec zero,但這裡需要 Vec (succ zero)
```

這句話同時是型別錯誤訊息與邏輯錯誤訊息。對讀者來說，「 $nil$ 不是 `Vec (succ zero)` 的元素」跟「這個推論不成立」是同一件事。

**第三，「不可證」意味著「沒有該型別的項」。** 邏輯學裡的不可證性敘述（某命題不可由前提推出）在 Curry–Howard 之下變成一個**否定性的存在命題**：不存在形如 $t$ 使得 `infer(ctx, t)` 等於目標型別。而更妙的是，要證明不可證，反而可以用 Curry–Howard 把它寫成一個項——證明「所有能填進這個洞的函數都不行」，是一個關於函數的命題，其證明本身是一個函數。這是第 6 章會用到的武器。

## 暗線：兩種「只留一種連接詞」的手段

現在回頭看第 3.2 節。那裡描述了 lean.js 的解析器如何把否定展開：lean.js:23 的 `case 'un'` 裡，`~` 立刻被改寫成 `{ t: 'imp', l: un(), r: BOT }`，而 $\leftrightarrow$ 在 lean.js:17 被展開成兩個 $\wedge$ 。目的是讓**核心只認一種連接詞**（ $\to$ 與 $\bot$ ），把所有複合公式在解析期就拆平。

第 5.6 節的 Church 編碼做的是同一件事，卻用了相反的手段：核心只認 Π 型別，而 $\wedge$ 、 $\lor$ 、 $\exists$ 、 $\bot$ 在**使用者層**被展開成 Π 型別的定義。

| | lean.js（自然演繹） | cube.js（λ-cube） |
|---|---|---|
| 目標 | 核心只認 $\to$ 與 $\bot$ | 核心只認 Π 型別 |
| 手段 | **語法糖展開**（解析期） | **Church 編碼**（使用者寫的 `def`） |
| 誰做這件事 | 解析器自動完成，使用者不覺得 | 使用者明文寫出 `def And ...` |
| 代價 | 量化、 $\wedge$ 的結構在核心裡看不見 | 每個連接詞都要寫一次定義，且無法 O(1) 判斷結構 |
| 好處 | 使用者寫起來自然 | 核心更小、更對稱，連接詞可以自由擴充 |

兩者殊途同歸，理由是同一個：**命題的連接詞比它們共用的骨架更「多」**。 $\to$ 與 $\bot$ 足以表達所有命題邏輯； $\Pi$ 型別同樣足以表達所有命題邏輯，並且還能多表達依賴型別。既然連接詞是可有可無的裝飾品，把裝飾品從核心裡抽出來，就換來一個極小的可信核心——這正是第 7 章要回頭檢視的「De Bruijn 準則」。

本章餘下六節，就是把這個極小的核心攤開來看：核心長什麼樣（5.2）、它怎麼從簡單型別長出多型（5.3）、長出依值型別（5.4）、長出三合一的全能版本（5.5）、被抽出去的那些連接詞如何以 Church 編碼回來（5.6），以及底層那套索引與歸約機制（5.7）。我們先從最小的頂點開始。
