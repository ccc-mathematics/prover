# 5.2 λ→：簡單型別與核心的形狀

上一節我們說 lambda-cube 的核心「不知道 $\wedge$ 是什麼」。這節要把它說得更精確一點：核心到底知道什麼、怎麼知道、以及為什麼知道這麼少就夠了。λ→ 是 λ-cube 八個頂點裡最小的、也是唯一一個「所有東西都住在 $\mathit{Prop}$ 裡」的頂點，所以它是最好的解剖對象。

## 項的形狀：五種節點加三個輔助

`lambda-cube/src/cube.js` 的檔頭註解（cube.js:1-2）就開宗明義：

```js
/* λ-cube 證明助手 — 核心(Node 與瀏覽器共用)
   項只有 5 種節點:變數、sort、應用、λ、Π(內部用 de Bruijn index)。連接詞全由 Π 型別定義出來。 */
```

五種節點的構造子都擠在 cube.js:7-8：

```js
const V = i => ({ k: 'v', i }), Sx = s => ({ k: 's', s }), Ap = (f, a) => ({ k: 'a', f, a }), Cn = n => ({ k: 'c', n }), Mv = id => ({ k: 'm', id });
const Lm = (n, ty, b) => ({ k: 'l', n, ty, b }), Pi = (n, ty, b) => ({ k: 'p', n, ty, b });
```

| 節點 | 構造子 | 意義 | 核心程式碼 |
|---|---|---|---|
| `v` | `V(i)` | 變數，`i` 是 de Bruijn 索引 | cube.js:7 |
| `s` | `Sx(s)` | sort 節點，`s` 是 `'Prop'` 或 `'Type'` | cube.js:7 |
| `a` | `Ap(f, a)` | 應用 | cube.js:7 |
| `l` | `Lm(n, ty, b)` | λ 抽象：`(n : ty) => b` | cube.js:8 |
| `p` | `Pi(n, ty, b)` | Π 型別：`forall (n : ty), b` | cube.js:8 |

另外還有三個輔助節點，都不是「用來表達命題」的：`c`（`Cn(n)`，cube.js:7）代表全域環境 `G` 裡的一個常數；`m`（`Mv(id)`，cube.js:7）代表策略層留下的一個「洞」，等著被填上；`z`（cube.js:99 的 `case 'z'`）代表 `sorry`，是整個系統唯一允許的作弊。`z` 沒有構造子，是直接寫出物件字面量的。

判斷「這是不是一個綁定」用 cube.js:9 的一行輔助：

```js
const bind = t => t.k === 'l' || t.k === 'p';
```

`bind` 之所以值得抽出來，是因為 `shift`、`subst`、`nf` 三處都要對 `l` 與 `p` 做同樣的事：兩個子項是 `ty` 與 `b`，而且 `b` 在綁定之下，遞迴時的索引基準要加一。

## 核心的五個工具

`kernel()` 函式從 cube.js:75 開始，到 cube.js:117 結束，中間只做了五件事。它回傳的物件是 cube.js:116 的 `return { infer, sort, whnf, conv, nf };`。

**`infer(ctx, t)`（cube.js:94-115）** 是型別推導：給定一個上下文 `ctx`（一串 `{ n, ty }`）和一個項 `t`，回傳 `t` 的型別。這是核心的心臟，也是本章唯一需要逐行細讀的函式。

**`sort(ctx, T)`（cube.js:93）** 檢查某個項 `T` 是不是一個型別，並回傳它的 sort：

```js
const sort = (ctx, T) => { const s = whnf(infer(ctx, T)); if (s.k !== 's') throw E(`${show(T, names(ctx))} 不是型別`); return s.s; };
```

它其實是 `infer` 加上一個「結果必須是 sort 節點」的斷言。注意它先 `whnf`：如果 `T` 是一個定義（例如 `And`），`infer` 會回傳 `G['And'].ty`——那是**宣告**的型別，而不是**展開後**的型別；`whnf` 把 `G[t.n].val`（cube.js:79）攤開，才看得到真正的結構。

**`whnf(t)`（cube.js:77-81）** 是弱頭正規形：只把頭部的 β-redex 與 δ-redex 展開，不做遞迴。

**`conv(a, b)`（cube.js:82-90）** 是定義等價判定：兩個項在「展開所有定義、做完所有 β-歸約」之後是否相等。

**`nf(t)`（cube.js:91）** 是完全正規形：遞迴地把每個子項正規化。`eval` 指令（cube.js:184）用它來把一個項印成最簡潔的樣子。

這五個工具的分工是：**`infer` 說「這是什麼型別」，`whnf` 說「這展開後是什麼」，`conv` 說「這兩個是不是同一個東西」，`nf` 說「這最簡是什麼」，`sort` 說「這的型別是什麼 sort」。** 換句話說，除了 `infer` 之外的四個全都是為了讓 `infer` 能正確運作而存在的輔助。

## `infer()` 的七個分支

`infer` 是一個 `switch (t.k)`（cube.js:95）。我們逐條走過。

**`v`：變數（cube.js:96）。**

```js
case 'v': { const e = ctx[ctx.length - 1 - t.i]; if (!e) throw E('自由變數'); return shift(e.ty, t.i + 1); }
```

上下文 `ctx` 是一個陣列，最後一個元素是**最近**綁定的變數。索引 `t.i` 是「從最近綁定往上數第幾層」，所以 `ctx.length - 1 - t.i` 找出對應的綁定。回傳型別時必須 `shift(e.ty, t.i + 1)`：因為我們正站在 `t.i` 層綁定之內，那個綁定的型別裡若有指向更外層的自由變數，索引要整體推開 `t.i + 1` 格。

**`s`：sort（cube.js:97）。**

```js
case 's': if (t.s === 'Prop') return Sx('Type'); throw E('Type 沒有型別(λ-cube 的最頂層)');
```

`Prop` 的型別是 `Type`——這是「命題的集合也是一個型別」的意思，也是 `Type>Prop` 這條規則存在的理由（見 5.3）。但 `Type` 自己沒有型別，核心直接擲出錯誤。這是 λ-cube 的一個**頂點限制**：整個型別論只有兩層，`Prop` 與 `Type`，沒有宇宙階層。第 8 章會回頭處理這個缺陷。

**`c`：常數（cube.js:98）。** `return G[t.n].ty;`——核心不猜測常數的結構，只信任全域環境裡宣告的型別。這就是 5.6 節 Church 編碼能運作的原因：`And` 在核心眼裡只是一個型別為 `Prop → Prop → Prop` 的常數，它究竟是什麼，取決於 `G['And'].val` 裡那個使用者寫下的 Π 型別。

順帶一提，這裡回答了一個容易搞混的問題：** $P$ 本身不是一個型別，它是一個住在 $\mathit{Prop}$ 裡的項。** `infer` 對常數節點只回傳 `G[t.n].ty`，核心從不把 $P$ 當成「型別的結構」來分析。所以 `sort(ctx, P)` 的結果是 `'Prop'`——意思是「 $P$ 是命題」，而不是「 $P$ 的型別是命題」。再往上，`sort(ctx, Prop)` 的結果才是 `'Type'`。

**`z`：`sorry`（cube.js:99）。** `fl.sorry = true; return t.ty;`——`sorry` 假裝自己有任何型別，並且在旗標 `fl.sorry` 上做記號。這個旗標會一路傳到 cube.js:205，讓 theorem 的狀態變成 `'sorry'` 而不是 `'ok'`。這是第 7 章「核心必須拒絕偽造證明」那一節要回頭檢查的地方。

**`m`：未解決的洞（cube.js:100）。** `throw E('仍有未解決的目標');`——洞是策略層的中間產物，一旦證明結束還有洞沒填，核心就拒絕。這一條是「策略寫錯只會失敗，不會讓錯誤的證明通過」的技術保證（`lean-prover/src/lean.js` 的檔頭註解也是這個語氣）。

**`p`：Π 型別（cube.js:101-105）。**

```js
case 'p': {
  const s1 = sort(ctx, t.ty), s2 = sort([...ctx, { n: t.n, ty: t.ty }], t.b);
  if (!rules.has(s1 + '>' + s2)) throw E(`目前的系統不允許這個 Π 型別:定義域屬於 ${s1},值域屬於 ${s2}(缺少規則 ${s1}>${s2}):${show(t, names(ctx))}`);
  return Sx(s2);
}
```

這是整個 λ-cube 的樞紐。第一步 `s1 = sort(ctx, t.ty)` 求出定義域的 sort（例如 `Prop`）；第二步 `s2 = sort([...ctx, {n, ty}], t.b)` 求出**在綁定變數的上下文裡**函數體的 sort（例如 `Prop`）；第三步檢查形成規則集合 `rules` 裡有沒有 `'Prop>Prop'` 這個組合。整個 λ-cube 的八個頂點，差別**只在這個集合裡多了哪幾個字串**。核心的其他部分完全不必改動。

回傳 `Sx(s2)` 表示 Π 型別的型別是它的值域的 sort。

**`l`：λ 抽象（cube.js:106）。**

```js
case 'l': { sort(ctx, t.ty); const T = Pi(t.n, t.ty, infer([...ctx, { n: t.n, ty: t.ty }], t.b)); infer(ctx, T); return T; }
```

三步：先確認宣告的型別 `t.ty` 確實是個型別（`sort` 會擲「不是型別」）；再在**擴充了上下文**的情況下推導函數體 `t.b` 的型別，並且把這個型別組裝成 Π；最後 `infer(ctx, T)` 檢查這個 Π 本身合法——這一步會再次觸發 `p` 分支的形成規則檢查。換句話說，**λ 抽象的型別檢查，本質上就是 Π 型別的型別檢查**；λ 演算與 Π 在核心裡是同一個機制的兩種外觀。

**`a`：應用（cube.js:107-113）。**

```js
case 'a': {
  const tf = whnf(infer(ctx, t.f)), ns = names(ctx);
  if (tf.k !== 'p') throw E(`${show(t.f, ns)} 不是函數,它的型別是 ${show(tf, ns)}`);
  const ta = infer(ctx, t.a);
  if (!conv(ta, tf.ty)) throw E(`型別不吻合:${show(t.a, ns)} 的型別是 ${show(ta, ns)},但這裡需要 ${show(tf.ty, ns)}`);
  return inst(tf.b, t.a);
}
```

四步，也是一條完整的 Curry–Howard 對應：**先推函數的型別並化簡（`whnf`，因為函數的型別可能是個還沒展開的定義）→ 確認它是 Π → 推參數的型別 → 要求參數型別與 Π 的定義域在 `conv` 下相等 → 回傳把參數代進函數體的結果型別 `inst(tf.b, t.a)`**。

最後這一步 `inst` 是 β-歸約在建構「結果型別」時的用法： $((x : A) \to B(x))\, a$ 的型別是 $B(a)$ 。`inst` 的實作在 cube.js:14：

```js
const inst = (b, a) => shift(subst(b, 0, shift(a, 1)), -1);
```

它把參數 `a` 先 `shift` 上去（因為 `b` 是在一個綁定之下，索引空間多了一格），代進 `b` 的第 0 層綁定，最後把整體 `shift` 回去一格。細節留到 5.7 節。

## `whnf()` 與 `conv()`：核心裡唯一的「計算」

`whnf`（cube.js:77-81）是一個無限迴圈：

```js
const whnf = t => { for (;;) {
  if (t.k === 'a') { const f = whnf(t.f); if (f.k === 'l') { t = inst(f.b, t.a); continue; } return Ap(f, t.a); }
  if (t.k === 'c' && G[t.n] && G[t.n].val) { t = G[t.n].val; continue; }
  return t;
} };
```

兩種化簡：**β-redex**（函數位置是 λ 抽象，就把引數代進函數體）與 **δ-redex**（常數有值，就把值攤開）。第二種化簡是 `def` 存在的理由，也是 5.6 節「Church 編碼可以展開成明確的 Π 型別」得以成立的原因。

`conv`（cube.js:82-90）在 `whnf` 之後做結構比較：

```js
const conv = (a, b) => {
  a = whnf(a); b = whnf(b); if (a.k !== b.k) return false;
  switch (a.k) {
    case 'v': return a.i === b.i; case 's': return a.s === b.s; case 'c': return a.n === b.n;
    case 'a': return conv(a.f, b.f) && conv(a.a, b.a);
    case 'l': case 'p': return conv(a.ty, b.ty) && conv(a.b, b.b);
  }
  return false;
};
```

六個分支，分別對應六種節點形狀：變數比索引、sort 比名字、常數比名字、應用遞迴比左右、λ 與 Π 遞迴比型別與函數體。**注意 `l` 與 `p` 共用一個分支**——它們的內部結構一樣（`ty` 與 `b`），所以 Curry–Howard 在資料結構層面根本分不出「函數」與「型別」：兩者都是「一個綁定，一個型別，一個主體」。

這裡沒有 η 等價、沒有宇宙多態、沒有歸納型別。`conv` 就是「展開、比較、再展開」，簡單到可以逐字唸出來。

## 為什麼核心可以這麼小

現在可以回答一個大問題：為什麼不需要型別推斷（type inference）？

因為在 λ→ 裡，**所有的命題都在 $\mathit{Prop}$ 裡，而 $\mathit{Prop}$ 只有一種類型**。要判斷一個項是否有某個型別，核心不需要做 Hindley–Milner 那一套 unification，因為命題本身就是型別、型別就是命題，沒有「型別變數要猜」的問題。`infer` 做的事情嚴格來說是**型別檢查**（checking），不是型別推斷（inference）：每一個項都已經被宣告了它的型別，核心的工作是**驗證**這些宣告彼此吻合。

對照來看：第 3 章的 `check()` 走的正是同一條路——證明項裡的每個規則都指明了自己的前提與結論，核心只負責把形狀對起來。lean.js:83 的 `need` 輔助（「`∧ 消去` 的對象形狀不對」）就是形狀檢查；cube.js:109 的「不是函數，它的型別是 ...」也是形狀檢查。

核心小的第二個原因是**語法糖都在解析期消掉**。cube.js:35 的 `tok` 函式把 `λ`、`Π`、`∀`、`→` 全部換成關鍵字形式，cube.js:52 的 `arrow()` 把 `A -> B` 直接翻譯成 `Pi('_', A, B)`。於是核心從來不必處理 infix 運算、括號優先序、否定展開——這些都在 cube.js:37-72 的 `parser()` 裡做完。

## 手算範例：`fun (x : P) => x`

現在把上面說的一步步攤開。假設全域環境 `G` 裡有 `G['P'] = { ty: Sx('Prop') }`（由 `axiom P : Prop` 產生，cube.js:214）。

我們要檢查的項是 `Lm('x', Cn('P'), V(0))`，也就是 `fun (x : P) => x`。

**第一步，`infer([], Lm)`（cube.js:106）。**

- `sort(ctx, t.ty)`：`t.ty = Cn('P')`。`infer([], Cn('P'))` 走 `c` 分支（cube.js:98），回傳 `G['P'].ty = Sx('Prop')`。`whnf` 之後仍是 `Sx('Prop')`，是 sort 節點，所以 `sort` 回傳 `'Prop'`。✓
- `infer([{n:'x', ty:Cn('P')}], V(0))`：走 `v` 分支（cube.js:96）。`ctx.length - 1 - 0 = 0`，取到 `e = { n:'x', ty: Cn('P') }`。回傳 `shift(Cn('P'), 1)`。`shift` 對 `c` 節點原封不動（cube.js:10-11 只處理 `v`、`a` 與綁定），所以結果還是 `Cn('P')`。
- 於是 `T = Pi('x', Cn('P'), Cn('P'))`。
- `infer(ctx, T)`：走 `p` 分支（cube.js:101）。`s1 = sort(ctx, Cn('P')) = 'Prop'`；`s2 = sort([{n:'x',ty:P}], Cn('P')) = 'Prop'`。規則集合裡有 `'Prop>Prop'`（cube.js:170 的 `rules = new Set(['Prop>Prop', ...CUBE[n]])`），所以檢查通過，回傳 `Sx('Prop')`。
- `infer` 回傳 `T = Pi('x', P, P)`。

**第二步，顯示。** `show` 對 Π 節點先問 `uses(t.b)`（cube.js:28）。`uses(Cn('P'), 0)` 走 cube.js:15 的 `c` 情形——`bind` 為 false，函式體為 false——所以 `uses` 回傳 `false`。於是這個 Π 被顯示成 `P → P` 而非 `∀ (x : P), P`。因為函數體根本不依賴綁定變數 `x`，它其實就是一個非依賴的箭頭型別。

核心輸出：

```
✔ check fun (x : P) => x : P → P
```

**第三步，如果宣告的東西不是型別會怎樣？** 假設全域環境裡有 `axiom f : P`——那麼 `G['f'].ty = Cn('P')`，也就是說 $f$ 是一個**住在 $\mathit{Prop}$ 裡的項**，不是一個型別。此時 `sort(ctx, Cn('f'))` 會呼叫 `infer(ctx, Cn('f'))`，走 `c` 分支得到 `Cn('P')`；`whnf` 之後仍不是 sort 節點，於是 cube.js:93 擲出「`f` 不是型別」。核心在這裡擋下了一個把「項」誤當「型別」用的宣告。

（順帶一提，`axiom P : P` 這種循環宣告會更早就被解析器擋下：cube.js:48 的 `if (G[x]) return Cn(x);` 在 `G['P']` 還不存在時會直接報「未定義的名稱 P」。核心連碰都碰不到。）

順帶一提，同樣是這個 `uses` 機制，讓 `show` 能區分 `A → B` 與 `∀ (x : A), B`：cube.js:28

```js
if (t.k === 'p' && !uses(t.b)) return par(show(t.ty, ns, 2) + ' → ' + show(t.b, [...ns, '_'], 1), q > 1);
```

這是 5.4 節講依值型別時的伏筆：顯示成箭頭還是顯示成 `forall`，取決於函數體**實際上**有沒有用到綁定變數，而不是取決於使用者怎麼寫。

## 小結與交棒

λ→ 的核心形狀現在完整了：**五種項節點、一個 `switch` 七個分支、一個形成規則集合 `rules` 決定哪些 Π 合法、一個 `conv` 用結構比較代替 unification。** 所有的邏輯力量都來自那個 `rules` 集合，而它由 `CUBE` 表（cube.js:5-6）決定。

下一節就從這個集合開始，把它從一個元素擴到兩個：`Type>Prop`。這一條規則會讓「型的型別是命題」變成合法，於是「對命題做量化」——也就是多型——出現了。
