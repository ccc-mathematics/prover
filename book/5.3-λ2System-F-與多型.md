# 5.3 λ2：System F 與多型

上一節我們把 λ→ 的核心拆開，結論是：整個 λ-cube 的邏輯力量只由一個集合 `rules` 決定，八個頂點的差別僅僅是這個集合裡多了哪幾個字串。這節我們做最小的一步擴充——加上一條 `Type>Prop`——看一個只有一條規則的差距，能生出多高的表達力。

## 一條規則的差距

`CUBE` 表在 `lambda-cube/src/cube.js` 的 cube.js:5-6：

```js
const CUBE = { 'λ→': [], 'λ2': ['Type>Prop'], 'λP': ['Prop>Type'], 'λω_': ['Type>Type'], 'λP2': ['Type>Prop', 'Prop>Type'],
  'λω': ['Type>Prop', 'Type>Type'], 'λPω_': ['Prop>Type', 'Type>Type'], 'λC': ['Type>Prop', 'Prop>Type', 'Type>Type'] };
```

注意 `λ→` 的陣列是**空的**。這看起來奇怪，但讀 cube.js:170 就會明白：

```js
const setSys = n => { if (!CUBE[n]) throw new Error(`未知的系統 ${n},可用:${Object.keys(CUBE).join(' ')}`); sys = n; rules = new Set(['Prop>Prop', ...CUBE[n]]); K = kernel(G, rules, fl); };
```

`Prop>Prop` 是**基底規則**，永遠都在；`CUBE` 表記錄的是各個系統相對基底**額外**允許的規則。所以 `λ→` 的規則集合是 `{Prop>Prop}`，`λ2` 是 `{Prop>Prop, Type>Prop}`。兩者相差一個字串。

而 `Type>Prop` 這一個字串的實際效果，用 `check` 一試便知：

```
system λ→
✔ axiom P : Prop
✘ check
    目前的系統不允許這個 Π 型別:定義域屬於 Type,值域屬於 Prop(缺少規則 Type>Prop):∀ (B : Prop), B → B
```

```
system λ2
✔ check ∀ (B : Prop), B → B : Prop
```

在 λ→ 裡，**「對所有命題做量化」這個型別根本寫不出來**。`∀ (B : Prop), B → B` 連自己的型別都沒有——它不是一個錯誤的證明，而是一個連語法層面都無法接受的型別。而在 λ2 裡它立刻變成一個合法的命題：`∀ (B : Prop), B → B : Prop`。

## `Type>Prop` 到底說了什麼

回到 5.2 節讀過的 Π 形成規則（cube.js:101-104）：

```js
const s1 = sort(ctx, t.ty), s2 = sort([...ctx, { n: t.n, ty: t.ty }], t.b);
if (!rules.has(s1 + '>' + s2)) throw E(...);
return Sx(s2);
```

規則 `s1 > s2` 的意思是：**「一個定義域的 sort 是 $s_1$ 、值域的 sort 是 $s_2$ 的 Π 型別是合法的，而且它的型別是 $s_2$ 。」**

`Type>Prop` 因此讀作：「**定義域本身是一個型別（sort 為 $\mathit{Type}$ ）、值域是命題（sort 為 $\mathit{Prop}$ ）的 Π 型別是合法的，而且它本身也是一個命題。**」

這句話為什麼重要？看 `∀ (B : Prop), B → B` 這個型別的兩部分：

- 定義域寫的是 `Prop` 這個常數。`Prop` 自己的型別是 `Type`（cube.js:97：`case 's': if (t.s === 'Prop') return Sx('Type');`），所以 `sort(ctx, Prop) = 'Type'`。因此 $s_1 = \mathit{Type}$ 。
- 值域是 `B → B`，其中 `B` 是個變數，型別是 `Prop`，所以 $s_2 = \mathit{Prop}$ 。

於是形成規則需要 `Type>Prop`。有了它，這個 Π 的型別是 $\mathit{Prop}$ ——也就是說，**「對所有命題做量化」這件事本身是一件命題**。這正是多型所需要的。

在型別論的語言裡，這句話可以寫成：

$$
\mathit{Prop} : \mathit{Type}, \qquad \Pi (X : \mathit{Prop}).\, B(X) : \mathit{Prop}
$$

第一個式子是基底（cube.js:97），第二個式子是 `Type>Prop` 這條規則的後果。第二式子讓「 $X$ 是一個命題」成為可以量化的事情。λ2 的多型就是從這裡來的。

## 多型恆等函數

cube.js:242 的內建範例是整個 λ-cube 的招牌：

```js
{ name: '多型恆等函數 λ2', src: 'system λ2\ndef id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x\ncheck id\n-- 把 id 套用在它自己的型別上(impredicative)\neval id (forall (B : Prop), B -> B) id' },
```

跑出來是：

```
✔ def id : ∀ (A : Prop), A → A
✔ check id : ∀ (A : Prop), A → A
✔ eval fun (A : Prop) => fun (x : A) => x : ∀ (B : Prop), B → B
```

`id` 的宣告 `forall (A : Prop), A -> A` 在 λ→ 裡會被拒絕（這是 5.3 末尾的錯誤示範），但在 λ2 裡完全合法。它的意思是：「給我一個命題 $A$ ，給我一個 $A$ 的元素，我給你一個 $A$ 的元素。」**注意 $A$ 是「一個命題」，不是「某個特定的命題」**——這就是多型。

用第 5.1 節的 Curry–Howard 語言說：`id` 不是一個「從 $A$ 到 $A$ 的函數」，而是一個**構造這類函數的函數**。`check id` 的輸出是 `∀ (A : Prop), A → A`，它是 `Prop` 的元素；`id` 本身的值是 `fun (A : Prop) (x : A) => x`，它是一個二元的 λ 抽象。

## Impredicativity：把 id 用在「所有命題的函數型別」上

那個 `eval` 是整段範例的重點：

```
eval id (forall (B : Prop), B -> B) id
```

把它拆成三段讀：

1. `id` 的型別是 `∀ (A : Prop), A → A`。套用在引數 $X = \forall (B : \mathit{Prop}).\, B \to B$ 上，結果型別是 $X \to X$ ，也就是 `∀ (B : Prop), B → B`。
2. 第二個引數 `id` 自己，它的型別是 `∀ (A : Prop), A → A`。
3. 關鍵在於： $X \to X$ 與 `id` 的型別 `∀ (A : Prop), A → A` **在 `conv` 下相等**。

第三點為什麼成立？看 5.2 節讀過的 `conv`（cube.js:82-90）：`case 'l': case 'p': return conv(a.ty, b.ty) && conv(a.b, b.b);`——**綁定變數的名字 `n` 根本不參與比較**。所以 `∀ (A : Prop), A → A` 與 `∀ (B : Prop), B → B` 只比較定義域（`Prop` vs `Prop` ✓）與函數體（`Π('_', V(0), V(0))` vs `Π('_', V(0), V(0))` ✓）。兩者的 de Bruijn 索引完全一致，於是 α 等價自動成立。

所以這個 `eval` 裡藏著一句驚人的話：**`id` 被用在了「所有命題的函數型別」這個型別上**——也就是說，`id` 的多型參數被實例化成了一個**量化變數本身**。型別變數 $A$ 被代成了 $\forall (B : \mathit{Prop}).\, B \to B$ ，一個 Π 型別。

這件事在 λ→ 裡連想都不能想，因為 $\forall (B : \mathit{Prop}).\, B \to B$ 在 λ→ 裡**沒有型別**（它需要 `Type>Prop`）。而在 λ2 裡它有型別 $\mathit{Prop}$ ，所以它可以拿來實例化 $A$ 。

這個性質在文獻裡叫 **impredicativity**（非預言性 / 自我套用）： $\Pi$ 型別的定義域可以是一個 $\Pi$ 型別自身。Girard 的 System F（1985）正是靠這個性質獲得了驚人的表達力——而 Girard 的理論後來被 Coq、Agda、Lean 這些實際系統採用，作為依賴型別理論的基礎。

`eval` 印出來的 `fun (A : Prop) => fun (x : A) => x : ∀ (B : Prop), B → B` 就是這個過程的證據：左邊是被 `nf` 正規化後的值（`id` 的定義展開成它的 λ 抽象），右邊是它的型別（那個 $\forall (B : \mathit{Prop}).\, B \to B$ ）。

## 讀懂 λ→ 的錯誤示範

cube.js:247 是整個 lambda-cube 裡唯一一個**故意失敗**的內建範例：

```js
{ name: 'λ→ 不允許多型(錯誤示範)', src: 'system λ→\ndef id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x' },
```

輸出：

```
✘ def
    目前的系統不允許這個 Π 型別:定義域屬於 Type,值域屬於 Prop(缺少規則 Type>Prop):∀ (A : Prop), A → A
```

這句錯誤訊息值得逐字拆開，因為它是整個 λ-cube 的設計哲學最直白的一次表白：

- **「定義域屬於 Type」**——這是 `sort(ctx, t.ty)` 的結果。`t.ty` 是 `Prop`，而 `Prop : Type`（cube.js:97），所以定義域的 sort 是 $\mathit{Type}$ 。
- **「值域屬於 Prop」**——這是 `sort([...ctx, {n,ty}], t.b)` 的結果。函數體 `A → A` 的型別是 $\mathit{Prop}$ ，所以值域的 sort 是 $\mathit{Prop}$ 。
- **「缺少規則 Type>Prop」**——`rules` 集合裡沒有這個組合。`rules = new Set(['Prop>Prop'])`，就這麼簡單。
- **「∀ (A : Prop), A → A」**——`show(t, names(ctx))` 把出錯的那個 Π 印出來。

要注意這個錯誤**不是**「宣告的型別與內容不符」，那個檢查在 cube.js:212，是另一回事。這個錯誤發生在**更早**：在 `def` 的宣告階段（cube.js:209-213）就已經失敗了，因為 `K.sort([], pis)` 對 `pis = Π('A', Prop, Π('_', V(0), V(0)))` 呼叫 `infer`，直接撞上 Π 分支的形成規則檢查。

**所以同一行文字，在 λ2 裡是合法的多型恆等函數，在 λ→ 裡是核心親手拒絕的非法型別。** 兩者之間的距離，就是 `rules` 集合裡的一個字串。

## 多型與 Skolem 化：兩種處理量詞的哲學

第 4.3 節講過歸結法裡的 Skolem 化：把 $\forall x\, \varphi(x)$ 換成 $\varphi(f(\ldots))$ ，其中 $f$ 是一個新鲜的 Skolem 函數。理由是 Herbrand 定理——一階邏輯的證明存在性可以完全用項來表述，所以機器可以把存在量詞「消掉」，變成對項的搜尋。

λ2 對同一個 $\forall$ 做了**完全相反**的事：它保留量詞，並且把它變成一個**可以套用到任何命題上的函數**。

| | 歸結法（第 4 章） | λ2（本章） |
|---|---|---|
| 對 $\forall x.\varphi(x)$ 的處理 | **消掉**它：Skolem 化，換成項 | **保留**它：變成 Π 型別 |
| 量詞的地位 | 是公式裡的記號，證明過程中會被消去 | 是型別的一部分，恆久地留在型別裡 |
| 「到處使用」的量化變數 | Skolem 函數 $f$ 的引數 | 抽象出來的綁定變數 $A$ |
| 證明策略 | 機器自己找（統一、剪枝） | 人給線索（`intro` / `apply`） |
| 失敗模式 | 爆炸（Skolem 化破壞健全性） | 爆炸（quantifier explosion） |

兩邊都在處理同一個難題：**量詞讓「證明」不再是項的封閉運算。** Skolem 化的答案是把它變成一個封閉的項空間（然後承受爆炸的代價）；λ2 的答案是把它變成一個**高階函數**，讓量化變數成為可以傳來傳去的對象（然後承受 Type 沒有型別、沒有宇宙階層的代價——5.5 節會看到）。

順帶一提，第 5 章出現的「一次量化、到處使用」（polymorphism 是 let-polymorphism 之外的一種量化）與 Skolem 化之間還有一層對應關係：Skolem 函數 $f$ 扮演的角色，正像一個類型變數的「恆定實例」；而在 λ2 裡 `def id` 是一個**全體的**多型定義，可以用在任何命題上。

## 一個容易誤讀的細節：`id` 不能直接當命題用

前面的 `eval` 範例裡有一個容易被讀過去的細節：

```
eval id (forall (B : Prop), B -> B) id
```

第二個引數為什麼要把 `∀ (B : Prop), B → B` 整個寫出來，而不是寫 `id`？因為在 lambda-cube 裡，**一個命題是一個型別為 `Prop` 的項**，而 `id` 的型別不是 `Prop`。

`infer()` 對常數節點回傳**它被宣告的型別**（cube.js:98），對 Π 型別節點回傳的卻是**它的 sort**（cube.js:104）。同一個命題，兩種寫法，兩種回報：

```
system λ2
def id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x
check id
check forall (A : Prop), A -> A
```

```
✔ check id : ∀ (A : Prop), A → A
✔ check ∀ (A : Prop), A → A : Prop
```

差別有實際後果：

```
check id id
```

```
✘ check
    型別不吻合:id 的型別是 ∀ (A : Prop), A → A,但這裡需要 Prop
```

`id` 不能直接套在「所有命題的函數型別」上，因為那個位置要的是一個**命題**，而 `id` 是**型別為命題的項**。Curry–Howard 之下這兩件事差了一層：前者是證明，後者是被證明的命題。而 impredicativity 說的是「可以把命題當參數傳給多型函數」，所以那個參數必須是一個命題。

這其實是核心設計的直接後果。`infer()` 的常數分支（cube.js:98）只回傳 `G[t.n].ty`，完全不碰 `val`；值的展開只發生在 `whnf()` 裡——常數的值在那裡被換成它宣告的 λ 抽象（cube.js:79），β-歸約則發生在應用的函式位置（cube.js:78）。於是「一個常數的值」與「一個常數的型別」在型別推導裡徹底分家：前者要靠 `eval` 才看得到，後者永遠是宣告時的樣子。

於是內建範例才寫成 `eval id (forall (B : Prop), B -> B) id`：第二個引數是**寫出來的命題**，第三個引數 `id` 則因為 `conv` 只比對結構與索引（5.7 節），剛好和那個命題對得上。

## 多型的射程：λ2 還差什麼

λ2 的多型是「把命題當參數」，僅此而已。它有兩件事做不到。

**第一，不能對宇宙量化。** `Type` 在這個實作裡沒有型別（cube.js:97）：

```
system λ2
check forall (A : Type), A
```

```
✘ check
    Type 沒有型別(λ-cube 的最頂層)
```

多型只能量化 `Prop` 裡的元素，也就是命題；連「命題的空間」本身都沒有被型別化。第 8.1 節會處理這件事。

這兩件事合起來說明一件事：λ2 是 System F 的**最小可用片段**，不是 System F 本身。Girard 的 System F 裡，`Type` 是一個可以量化、可以排序的 universe；lambda-cube 把 universe 壓扁成 `Prop` 與 `Type` 兩個 sort，於是換來一個好得多的錯誤訊息——讀者只會看到「定義域屬於 X,值域屬於 Y」這種可以照著修的描述——也換來一個說不出口的代價：kinds 那一整層消失了。

**第二，不足以定義 Church 編碼的 `∧`。**

```
system λ2
def And (A B : Prop) : Prop := forall (C : Prop), (A -> B -> C) -> C
```

```
✘ def
    目前的系統不允許這個 Π 型別:定義域屬於 Type,值域屬於 Type(缺少規則 Type>Type):Prop → Prop
```

被擋下來的是**宣告的型別**：內層 Π `∀ (B : Prop), Prop` 的定義域 sort 是 `Type`、值域 sort 也是 `Type`，需要 `Type>Type`。錯誤訊息裡的 `Prop → Prop` 是 `show()` 把「函數體沒用到綁定變數」的 Π 顯示成箭頭的結果（cube.js:28，見 5.4 節）。

所以 cube.js:243 那個 Church 編碼 `∧` 的範例用的系統是 `λω` 而不是 `λ2`。**λ2 的多型只把命題變成參數；要把「命題的空間」也變成可排序的東西，還需要另一條規則 `Type>Type`。**

這個「把命題當參數」的安排還帶來一個具體後果：**多型變數無法被省略。** `id` 必須寫成 `id P`、`id Q`，不能像 Lean 或 Coq 那樣靠隱含參數讓 `id` 自己推斷命題。cube.js:145 的 `apply` 策略甚至會主動擋下來，訊息是「apply 遇到依賴型參數(∀),請把參數寫進去,例如 apply h C」。所以 lambda-cube 的多型是**顯式**的：每一次實例化都得寫出來，這也是為什麼本章的範例要動手把 `∀ (B : Prop), B → B` 整個打出來。

最後是 impredicativity 的歷史包袱。Girard 在 1985 年證明 System F 的表達力，同時也證明了它的代價：**若 Π 型別的定義域可以是自己，而 `Type` 又有自己的型別，Girard 悖論成立**，整個理論變成不可判定的。真實系統的解法是把 `Type` 切成宇宙階層（`Type 0 : Type 1 : Type 2 : ...`），impredicativity 只在每個宇宙內部成立。lambda-cube 走的是更粗的路：cube.js:97 讓 `Type` 乾脆沒有型別，悖論連敘述的對象都沒有；代價是 kinds 完全缺席，5.5 節會看到 `Type>Type` 這條規則在這個實作裡只能拿 `Prop` 去用。

## 小結與交棒

λ2 的收穫是：一條規則 `Type>Prop`，讓「∀ 命題」成為一個合法型別，因而讓多型成為可能。多型的本質是：**把一個命題當成參數傳給函數**。Curry–Howard 語言裡就是「把一個證明當成參數傳給函數」——型別與項的界線，在多型出現的那一刻開始變得有意義。

但 λ2 還不夠。它的多型只能量化**命題**（因為定義域只能是 `Prop`），而且它的多型是「一次量化、到處使用」的一種簡化版本：全域常數 `G['id']` 一旦宣告，就是一個可以在任何地方以任何命題實例化的多型常數。

下一節我們走另一條軸：讓**型別可以依賴於項**。這需要另一條規則 `Prop>Type`，它的效果比 `Type>Prop` 更大——它會讓 `Vec zero` 與 `Vec (succ zero)` 成為兩個**不同的型別**，從而讓「長度」這類資訊進入型別。
