# 5.4 λP：依值型別與 Π 型別

上一節沿著「型的型別」這條軸往上爬了一格，得到多型。這節換一條軸：**型別可以依賴於項**。這是 λ-cube 三個維度裡最靠近邏輯學的一個，也是三個維度中唯一直接對應到一階邏輯量詞的。

## `Prop>Type`：當型別可以依賴於項

`λP` 在 `CUBE` 表裡的定義是 cube.js:5 的一個元素：

```js
'λP': ['Prop>Type'],
```

配合 cube.js:170 的基底規則，λP 的規則集合是 `{Prop>Prop, Prop>Type}`。讀法回到 5.3 節建立的框架：**規則 `s1 > s2` 表示「一個定義域 sort 為 $s_1$ 、值域 sort 為 $s_2$ 的 Π 型別是合法的，而且它的型別是 $s_2$ 」。**

`Prop>Type` 因此讀作：「**定義域是命題（sort $\mathit{Prop}$ ）、值域是型別（sort $\mathit{Type}$ ）的 Π 型別是合法的，而且它本身就是一個型別。**」

這一句的後果是：出現了一種**型別層的函數**——它的輸入是一個「住在命題裡的項」，輸出是一個「型別」。最典型的例子就是本節的主題：

```
Vec : Nat → Prop
```

`Nat` 的 sort 是 $\mathit{Prop}$ （因為 `axiom Nat : Prop`），而 `Prop` 這個常數的 sort 是 $\mathit{Type}$ （cube.js:97）。所以 `Nat → Prop` 這個 Π 的 $s_1 = \mathit{Prop}$ 、 $s_2 = \mathit{Type}$ ，需要 `Prop>Type`。有了它，這個 Π 的型別是 $\mathit{Type}$ ——**`Vec` 是一個型別，它把自然數送到型別。**

`Vec` 這樣的東西，在邏輯學裡叫**型別形式（type former）**或**一元謂詞的構造子**。它把「長度是 $n$ 的向量」這個命題，作為「 $n$ 的函數」來對待。

## `Vec` 範例

cube.js:245 的內建範例：

```js
{ name: '依值型別 Vec(λP)', src: 'system λP\naxiom Nat : Prop\naxiom zero : Nat\naxiom succ : Nat -> Nat\naxiom Vec : Nat -> Prop\naxiom nil : Vec zero\naxiom cons : forall (n : Nat), Vec n -> Vec (succ n)\ncheck cons zero nil\ncheck cons (succ zero) (cons zero nil)' },
```

跑出來：

```
✔ axiom Nat : Prop
✔ axiom zero : Nat
✔ axiom succ : Nat → Nat
✔ axiom Vec : Nat → Prop
✔ axiom nil : Vec zero
✔ axiom cons : ∀ (n : Nat), Vec n → Vec (succ n)
✔ check cons zero nil : Vec (succ zero)
✔ check cons (succ zero) (cons zero nil) : Vec (succ (succ zero))
```

請注意 `Vec : Nat → Prop` 與 `cons : ∀ (n : Nat), Vec n → Vec (succ n)` 這兩行的**形狀完全不同**，而這個差別不是風格問題，是邏輯問題。

`Vec` 的定義域是 `Nat`，值域是 `Prop`，兩者都不依賴綁定變數——`Nat → Prop` 是一個**非依賴**的箭頭，它只是把一個自然數映到一個型別。

`cons` 的定義域是 `Nat`，值域是 `Vec n → Vec (succ n)`。**值域提到了綁定變數 `n`**——這是一個**依賴**的 Π 型別。它的意思不是「對每個 $n$ ，有一個從 `Vec n` 到 `Vec (succ n)` 的函數」這麼鬆散的一句，而是字面意義上：**這個函數的型別本身隨著 $n$ 改變**。給它 $n = 0$ ，它的型別是 `Vec zero → Vec (succ zero)`；給它 $n = 1$ ，型別是 `Vec (succ zero) → Vec (succ (succ zero))`。**同一個 `cons`，在不同參數下是不同的型別。**

## 判別力：`Vec zero` ≠ `Vec (succ zero)`

依值型別的價值，在於它讓一些東西「不一樣」。我們用核心親手拒絕一個錯誤來證明：

```
system λP
axiom Nat : Prop
axiom zero : Nat
axiom succ : Nat -> Nat
axiom Vec : Nat -> Prop
axiom nil : Vec zero
axiom cons : forall (n : Nat), Vec n -> Vec (succ n)
✘ check
    型別不吻合:nil 的型別是 Vec zero,但這裡需要 Vec (succ zero)
```

錯誤訊息來自 cube.js:111。核心在推導 `cons (succ zero) nil` 時做了三件事：推 `cons` 的型別得到 `∀ (n : Nat), Vec n → Vec (succ n)`；`whnf` 之後確認它是 Π；然後把參數 `succ zero` 代進函數體，得到結果型別 `Vec (succ zero) → Vec (succ (succ zero))`——注意 `inst`（cube.js:112 的 `inst(tf.b, t.a)`）把 `n` 真的代成了 `succ zero`。於是下一個參數 `nil` 必須有型別 `Vec (succ zero)`，但它的型別是 `Vec zero`，`conv` 判定失敗。

**這正是「依值」的判別力。** 在簡單型別裡，`Vec` 只能是 `Vec : Nat → Type`（一個固定的型別，所有向量同型），或者 `Vec` 根本不存在；有了依值型別之後，**長度資訊進入了型別**。空向量 `nil` 與非空向量 `cons zero nil` 有了不同的型別，於是「`nil` 不能是 `cons` 的參數」這件事被機器自動擋下來，不需要任何額外的註記。

順帶一提，`check Vec zero` 與 `check Vec (succ zero)` 的輸出**都是** `: Prop`：

```
✔ check Vec zero : Prop
✔ check Vec (succ zero) : Prop
```

兩者的型別相同，但**它們是兩個不同的型別**。這是「型別的型別」與「型別本身」的分別：`Vec zero` 與 `Vec (succ zero)` 都是 $\mathit{Prop}$ 的元素，但 $\mathit{Prop}$ 這個集合裡的兩個元素彼此不同，而且核心能分辨它們——`conv` 逐個比較應用的函式與引數，`Ap(Cn('Vec'), Cn('zero'))` 與 `Ap(Cn('Vec'), Ap(Cn('succ'), Cn('zero')))` 顯然不同。

## 依值型別與一階邏輯的量詞

為什麼說 λP 對應的是**一階**邏輯的量詞？

在第 5.1 節的對應表裡， $\forall x.\, P(x)$ 對應到 $\Pi (x : A).\, B(x)$ 。這個對應有兩個層次：

- **型別層面的多型**（λ2 那一維）：量化變數 $x$ 的**型別**也可以被量化，於是出現 $\Pi (X : \mathit{Type}).\, B$ 。這是二階的。
- **項層面的依值**（λP 那一維）：量化變數 $x$ 是一個**項**，而被量化的命題 $P(x)$ 可以**隨著 $x$ 改變**。

λP 保留的是後者。它的 Π 型別 `forall (n : Nat), Vec n` 裡，被量化的是 `Nat` 的**元素**（項），而右邊的 `Vec n` 依賴於這個元素。這正是 $\forall n.\, \mathrm{Vec}(n)$ 這條一階公式的型別論翻譯。

這也是為什麼 λP **不能**量化命題自己。λP 的規則集合是 `{Prop>Prop, Prop>Type}`，沒有 `Type>Prop`，所以 `forall (A : Prop), A -> A` 會被拒絕：

```
✘ def
    目前的系統不允許這個 Π 型別:定義域屬於 Type,值域屬於 Prop(缺少規則 Type>Prop):∀ (A : Prop), A → A
```

`test/test.js` 的第 5 行就是守著這件事：

```js
ok(!t('system λP\ndef id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x').ok, 'λP 沒有多型,拒絕 ∀(A:Prop)');
```

**多型（量化型別）與依值（量化項）是兩條獨立的軸。** 這個正交性正是 λ-cube 得以有八個頂點的結構性原因：每一條軸可以獨立打開或關閉。

## Π 型別的兩種退化：箭頭與 `forall`

`show` 函式（cube.js:19-32）裡有一個關鍵的分支，cube.js:28：

```js
if (t.k === 'p' && !uses(t.b)) return par(show(t.ty, ns, 2) + ' → ' + show(t.b, [...ns, '_'], 1), q > 1);
```

這是說：**一個 Π 型別，如果它的函數體完全沒用到它自己綁定的那個變數，就顯示成箭頭 `ty → b`；否則顯示成 `forall (n : ty), b`。**

判斷「有沒有用到」的工具是 `uses`（cube.js:15）：

```js
const uses = (t, j = 0) => t.k === 'v' ? t.i === j : t.k === 'a' ? uses(t.f, j) || uses(t.a, j) : bind(t) ? uses(t.ty, j) || uses(t.b, j + 1) : false;
```

`uses(t, j)` 的意思是：**在目前這個層級上，索引為 $j$ 的綁定變數有沒有在 `t` 裡出現。** 三個分支各說一件事：

- `v`：這就是那個變數本身，比對索引即可。
- `a`：應用的兩邊都查。
- `bind`（`l` 或 `p`）：**型別部分 `ty` 在同一層**（索引 $j$ 沒變），**函數體 `b` 深了一層**（索引變成 $j+1$ ）。

呼叫 `uses(t.b)` 時用的是預設值 $j = 0$ 。在 `t.b` 裡，索引 0 正是 `t` 自己的那個綁定變數。所以 `uses(t.b)` 精確地回答：「這個 Π 的綁定變數，有沒有出現在它的函數體裡？」

回頭看 `Vec` 與 `cons` 的顯示結果：

- `Vec : Nat → Prop`：`Pi('_', Nat, Prop)`，綁定名是 `_`，函數體 `Prop` 裡沒有任何變數，`uses` 回傳 `false`，所以顯示為箭頭。**這個 Π 與它的綁定變數無關，所以它其實就是一個普通的函數型別**，只不過定義域與值域剛好是 sort 不同。
- `cons : ∀ (n : Nat), Vec n → Vec (succ n)`：外層 Π 的函數體是 `Vec n → Vec (succ n)`。`uses` 遞迴進去時，對內層 Π 會檢查 `uses(ty, 0)` 與 `uses(b, 1)`；內層的 `ty` 是 `Vec n`，其中 `n` 的索引正是 0，於是回傳 `true`。所以外層顯示為 `forall`。而**內層**的 Π（`Vec n → Vec (succ n)`）自己的綁定名是 `_`，函數體 `Vec (succ n)` 裡的 `n` 索引是 1 而非 0，所以 `uses` 回傳 `false`，內層顯示為箭頭。

結果就是那個看起來混合的樣子：`∀ (n : Nat), Vec n → Vec (succ n)`。**外層是依賴的（`forall`），內層是非依賴的（`→`）。** 這不是顯示上的偷懶，而是把「哪一段量化是依賴的」講清楚了。

## 兩種退化的邏輯意義

為什麼要區分「依賴」與「非依賴」？因為它們的**邏輯內容不同**。

非依賴的 `A → B`，其中 $B$ 不提到 $A$ ，它就是最普通的蘊含：從 $A$ 得到 $B$ 。它的判別力是零——不管 $A$ 是什麼， $B$ 都一樣。

依賴的 `forall (x : A), B(x)`，它的內容是「對 $A$ 的**每一個**元素 $x$ ，都有 $B(x)$ 」。 $B$ 隨 $x$ 變，所以這句話比單純的蘊含更有資訊量：`Vec n → Vec (succ n)` 對每個 $n$ 說不同的話。

用第 3 章的自然演繹語言來對照，這個差別正好像 $\forall$ 引入與 $\to$ 引入的差別：lean.js:99 的 `allI` 把 $x$ 換成一個新的名字然後證明 $\varphi(x)$ ，lean.js:95 的 `impI` 把前提放進上下文。前者的公式**在一般化之後會改變形狀**（ $\varphi(x)$ 依賴 $x$ ），後者不會。

而在 λ-cube 裡，這個差別不是靠語法標記出來的，是靠 `uses` **算出來的**。使用者寫 `forall (n : Nat), Vec n → Vec (succ n)` 或寫 `Nat → Prop`，核心不關心你怎麼寫，它只問一件事：**綁定變數有沒有被用到？** 這是 5.7 節要回頭細看的 `de Bruijn` 索引的好處之一——索引讓「用沒用到」變成一個可計算的問題。

## 與第 3 章的量詞對照

lean.js 的 `allI` / `allE` 做的正是 Π 型別的抽象與應用：

- `allI`（lean.js:99）：`return { t: 'all', v: p.v, f: C(p.p) };`——把 $x$ 抽象成一個新變數，得到一條公式。它附帶一個**副作用條件**：`if (ctx.some(([, f]) => fv(f).has(p.v))) bad(...)`，也就是被一般化的變數不能出現在任何假設裡。這是因為在自然演繹裡 $\forall$ 引入是一條需要「 $\varphi$ 不含 $x$ 以外的自由變數」的規則。
- `allE`（lean.js:100）：`return sub(a.f, a.v, p.t);`——把 $\forall$ 裡的變數用一個項取代。

對應到 cube.js：

| 自然演繹 | λ-cube | 說明 |
|---|---|---|
| `allI` | `Pi` 節點 + `Lm` 抽象 | `p` 分支（cube.js:101）檢查 Π 的形成規則；`l` 分支（cube.js:106）把綁定加進上下文 |
| `allE` | `Ap` 節點 + `inst` | `a` 分支（cube.js:107-112）推參數型別、比對定義域、`inst(tf.b, t.a)` 得到代入後的結果型別 |
| `sub` 的避免捕獲（lean.js:65-76） | `shift` / `subst`（cube.js:10-13） | 見 5.7 節 |

差別在**副作用條件的有無**。`allI` 需要「變數新鮮」是因為它處理的是**公式**：公式裡的變數名有全域意義。而在 λ-cube 裡，綁定變數由 `de Bruijn` 索引表示，沒有名字，就沒有捕獲的問題，所以不需要新鮮性檢查——**依賴關係不是靠命名約定的，而是靠索引結構直接表達的。** 這是 λ-cube 相對 lean.js 的一個實質優勢，也是第 7 章要量化比較的重點之一。

## 小結與交棒

λP 打開的是第三條軸。三條軸現在的樣子：

| 軸 | 規則 | λ-cube 裡的樣子 |
|---|---|---|
| 項依賴於項 | （λ 演算本身） | `Lm` / `Ap` |
| 型別依賴於型別 | `Type>Prop`（λ2） | `forall (A : Prop), A → A` |
| 型別依賴於項 | `Prop>Type`（λP） | `Vec : Nat → Prop`、`cons : ∀ (n : Nat), Vec n → Vec (succ n)` |

把第二條與第三條一起打開，就是 λC——Calculus of Constructions——下一節的主題。而在進入 λC 之前，我們需要先把「連接詞去哪了」補上：5.1 節說過核心裡沒有 $\wedge$ 、 $\lor$ 、 $\exists$ 、 $\bot$ ，5.6 節會給出它們的 Church 編碼，那是整個 λ-cube 裡「命題即型別」最徹底的一面。
