# 6.5 一階量詞：∀-消去、∃-消去與新鮮變數

前四節的命題都還在命題邏輯裡。本節加入第一階量詞，而量詞立刻讓三個系統拉開**最大**的距離——比否定、比等式都拉得更遠。原因不難理解：**量詞是綁定機制，而三個系統的綁定機制完全不同。**

- ITP 的 $\forall$ 與 $\exists$ 是 AST 裡的兩個節點（`all` 與 `ex`），消去它們靠**分支**與**新鮮變數**。
- λ-Cube 的 $\forall$ 是 **Π 型別**（內建、免費、單一）； $\exists$ 沒有內建，必須用 Church 編碼自己定義，而那個定義會把系統推到更高的頂點。
- ATP 的量詞在子句化時被 **Skolem 化**： $\forall$ 變成自由變數， $\exists$ 變成 Skolem 函數或常量。量詞在證明過程中**完全不再出現**。

本節用三個定理當量尺：蘇格拉底三段論（只有 $\forall$ ）、 $\forall$ 對 $\wedge$ 的分配（ $\forall$ 與 $\wedge$ 交錯）、以及 $\exists$ 與 $\forall$ 的對偶（兩種量詞同時出現）。

## 6.5.1 ITP：三個定理，三種機制

### 只有 $\forall$ ：一行結束

`lean-prover/src/lean.js:237`：

```js
  { name: '蘇格拉底三段論', src: 'theorem socrates (h : forall x. Man(x) -> Mortal(x)) (m : Man(socrates)) : Mortal(socrates) := by\n  exact h socrates m' },
```

輸出：

```
theorem socrates : Mortal(socrates)
  exact h socrates m
      沒有目標了
✔ 證明完成,核心檢查通過
```

**一行。** 這是本專案裡最短的證明，也是最值得逐字拆開的。原因在 `app()`（`lean.js:112-128`）：它把 `h socrates m` 從左到右讀過去，每讀到一個 token 就問「上下文裡有沒有叫這個名字的假設？」

| 讀到 | 上下文裡有同名假設？ | 判定 | 當前型別 |
|---|---|---|---|
| `h` | 有 | `hyp h` | $\forall x . Man(x) \to Mortal(x)$ |
| `socrates` | **沒有** | 當成**項**，做 $\forall$ 消去 | $Man(socrates) \to Mortal(socrates)$ |
| `m` | 有 | 做 $\to$ 消去 | $Mortal(socrates)$ |

關鍵在第二列：**`socrates` 不是假設，所以它被當成一個項送進 $\forall$ 裡。** 核心的 $\forall$ 消去規則（`lean.js:100`）只做一件事：

```js
    case 'allE': { const a = need(C(p.p), 'all', '∀ 消去'); return sub(a.f, a.v, p.t); }
```

也就是把綁定變數 $x$ 換成項 `socrates` ，其餘不動。整個機制沒有分支、沒有上下文變動，只是**一次帶捕捉安全的代換**。

這個設計有個陰暗面：名字空間是共享的。如果使用者的上下文裡剛好有一個叫 `socrates` 的假設，那麼 `socrates` 就會被當成假設，整個證明會以一種非常難懂的方式失敗。**量詞消去的正確性，取決於一個樸素的命名慣例。**

### $\forall$ 與 $\wedge$ 交錯：十行

`lean-prover/src/lean.js:238`：

```js
  { name: '∀ 對 ∧ 分配', src: 'theorem all_and : (forall x. P(x) & Q(x)) -> (forall x. P(x)) & (forall x. Q(x)) := by\n  intro h\n  constructor\n  intro y\n  have hy := h y\n  cases hy with a b\n  exact a\n  intro z\n  have hz := h z\n  cases hz with a b\n  exact b' },
```

關鍵片段是 `intro y` 之後的快照：

```
  intro y
      y : 項
      h : ∀ x, P(x) ∧ Q(x)
      ⊢ P(y)
```

**`y : 項` 這一行為什麼會出現？** 因為 `intro` 對 $\forall$ 目標做的是「把綁定變數 $x$ 改名成 `y` ，並把主體 $P(x)$ 換成 $P(y)$ 」。一旦離開量詞， $x$ 就變成一個自由的項變數，而它必須是**全新的**——否則會和公式裡其他的 $x$ 撞名。`fresh()` 就是這道防線（`lean.js:137`）：

```js
  const fresh = x => { if (fv(f).has(x) || ctx.some(([, h]) => fv(h).has(x))) throw new Error(`變數名 ${x} 已被使用,請換一個名稱`); }
```

真正負責把關的是**核心**（`lean.js:99`）：

```js
    case 'allI': { if (ctx.some(([, f]) => fv(f).has(p.v))) bad(`變數 ${p.v} 出現在假設中,不能一般化`); return { t: 'all', v: p.v, f: C(p.p) }; }
```

注意這條規則檢查的**不是**「變數名有沒有被用過」，而是「**這個變數是否出現在任何假設裡**」。這是 $\forall$ 引入的正確性條件：若 $x$ 在假設 $h$ 中自由出現，那麼由 $h$ 推導出的 $\forall x . B(x)$ 就不合法（那會是從一個只對某個 $x$ 成立的假設推出對所有 $x$ 成立）。策略層的 `fresh()` 與核心的 `allI` 檢查是**同一件事的兩層**——策略層給友善的訊息，核心給權威的判定。

### $\exists$ 與 $\forall$ 同時出現：分支

`lean-prover/src/lean.js:239`：

```js
  { name: '∃ 與 ∀ 的對偶', src: 'theorem ex_not_all : (exists x. P(x)) -> ~(forall x. ~P(x)) := by\n  intro h\n  intro hn\n  cases h with x hx\n  exact hn x hx' },
```

輸出（節錄）：

```
theorem ex_not_all : (∃ x, P(x)) → ¬(∀ x, ¬P(x))
  intro h
      h : ∃ x, P(x)
      ⊢ ¬(∀ x, ¬P(x))
  intro hn
      h : ∃ x, P(x)
      hn : ∀ x, ¬P(x)
      ⊢ False
  cases h with x hx
      x : 項
      h : ∃ x, P(x)
      hn : ∀ x, ¬P(x)
      hx : P(x)
      ⊢ False
  exact hn x hx
      沒有目標了
✔ 證明完成,核心檢查通過
```

`cases h with x hx` 是**第三種** `cases` 分支（`lean.js:162`）： $h : \exists x . P(x)$ 是存在命題，消去它會產生**一個**新目標，上下文多出見證 `hx : P(x)` 與一個**項變數** `x` （注意 `x : 項` 那一行——它不是假設，所以 `exact hn x hx` 裡的 `x` 會被當成項去做 $\forall$ 消去）。

核心對這個分支的規則是 `exE`（`lean.js:102-106`）：

```js
    case 'exE': {
      const e = need(C(p.p), 'ex', '∃ 消去'), r = C(p.q, [...ctx, [p.h, sub(e.f, e.v, { v: p.x })]]);
      if (fv(r).has(p.x) || fv(e).has(p.x) || ctx.some(([, f]) => fv(f).has(p.x))) bad(`變數 ${p.x} 不夠新`);
      return r;
    }
```

`exE` 做三件事：把 $\exists x . A(x)$ 的主體換成 $A(\text{新變數})$ 放進上下文；檢查**新變數的新鮮性**——它不能出現在分支的結論裡、不能出在被消去的公式裡、也不能出在任何假設裡；然後回傳分支結論。

**這個新鮮性檢查是量詞消去正確性的全部。** 若見證變數 $x$ 可以自由出現在假設中，那麼 $\exists$ 消去就會漏掉一個前提（你可以在分支裡用到只有某個 $x$ 才有的資訊）。核心用三個 `fv()` 檢查把這個洞堵死。

值得留意的是：**`exE` 不產生兩個分支**。 $\wedge$ 消去是「攤平」（一個目標）， $\vee$ 消去是「分岔」（兩個目標）， $\exists$ 消去是「**替換**」（一個目標，但見證是新的）。三種消去對應三種不同的邏輯行為，而它們在策略層共用同一個關鍵字 `cases`。

### 另一頭： $\exists$ 的引入

消去之外還有引入，而它的機制正好相反——**給出見證，而不是抽掉見證**。核心的 `exI`（`lean.js:101`）是：

```js
    case 'exI': return eq(C(p.p), sub(p.f, p.v, p.t)) ? { t: 'ex', v: p.v, f: p.f } : bad('∃ 引入的見證不吻合');
```

策略層的對應指令是 `exists`（`lean.js:155`）：

```js
    case 'exists': { is('ex'); const q = P(arg), t = q.term(); if (!q.done()) throw q.err('語法錯誤:多餘的符號'); const n = ng(ctx, sub(f.f, f.v, t)); return solve({ r: 'exI', t, p: M(n), v: f.v, f: f.f }, [n]); }
```

它把見證項 `t` 代進主體 $P(x)$ 得到新目標 $P(t)$ ，證明它之後核心再檢查一次「這個證明的型別是否恰好是 $P(t)$ 」。實際例子：

```
theorem ex_intro : P(socrates) -> (exists x. P(x)) := by
  intro hp
  exists socrates
  exact hp
```

輸出：

```
theorem ex_intro : P(socrates) → (∃ x, P(x))
  intro hp
      hp : P(socrates)
      ⊢ ∃ x, P(x)
  exists socrates
      hp : P(socrates)
      ⊢ P(socrates)
  exact hp
      沒有目標了
✔ 證明完成,核心檢查通過
```

**`exists socrates` 這一步同時做了兩件事**：把目標 $\exists x . P(x)$ 換成 $P(socrates)$ ，並把證明項片段記成 `exI`（帶著見證 `socrates` 與綁定變數 `x`）。核心的 `exI` 最後會檢查 `eq(C(p.p), sub(p.f, p.v, p.t))`——**證明的命題必須剛好等於把見證代回去的結果**，多一分少一分都不行。這個嚴格性是必要的：否則 `exI` 就會變成「從任何命題推出 $\exists x . P(x)$ 」的後門。

## 6.5.2 λ-Cube：∀ 免費，∃ 要爬上 λC

λ-Cube 的情況最有趣，因為**它的一半是免費的**。

$\forall$ 在 λ-Cube 裡就是 Π 型別：`forall (x : A), B` 是內建語法，不需要任何 `def` 。上一節的蘇格拉底三段論因此只是把 ITP 的版本翻譯過來：

```
system λP
axiom Nat : Prop
axiom Man : Nat -> Prop
axiom Mortal : Nat -> Prop
axiom socrates : Nat
axiom man_socrates : Man socrates
axiom all_mortal : forall (x : Nat), Man x -> Mortal x
theorem socrates_thm : Mortal socrates := by
  exact (all_mortal socrates man_socrates)
```

輸出：

```
✔ axiom all_mortal : ∀ (x : Nat), Man x → Mortal x
✔ theorem socrates_thm : Mortal socrates
    exact (all_mortal socrates man_socrates)
        沒有目標了
```

**「 $\forall$ 消去」在這裡就是一次 β 歸約**——`all_mortal socrates` 把 Π 型別的參數代進去。核心的 `infer()`（`cube.js:108-113`）在遇到應用節點時做 `inst(tf.b, t.a)`，那正是 β 歸約：

```js
      case 'a': {
        const tf = whnf(infer(ctx, t.f)), ns = names(ctx);
        if (tf.k !== 'p') throw E(`${show(t.f, ns)} 不是函數,它的型別是 ${show(tf, ns)}`);
        const ta = infer(ctx, t.a);
        if (!conv(ta, tf.ty)) throw E(`型別不吻合:${show(t.a, ns)} 的型別是 ${show(ta, ns)},但這裡需要 ${show(tf.ty, ns)}`);
        return inst(tf.b, t.a);
      }
```

**這裡沒有新鮮性檢查，因為根本不需要**： $\forall$ 引入在 Π 型別裡是**綁定**（de Bruijn 索引），不存在「變數名撞名」的問題。第 3.5 節與第 5.7 節談過的 de Bruijn 索引，在量詞這裡第一次顯出它的實際價值：**它把新鮮性從一個需要檢查的條件變成一個不可能發生的情況。**

但 $\exists$ 就沒有這份Lucky。λ-Cube 沒有 $\exists$ 的內建表示，要自己用 Church 編碼定義（`lambda-cube/src/cube.js:246`）：

```js
  { name: '存在量詞(λC)', src: 'system λC\ndef Ex (A : Prop) (P : A -> Prop) : Prop := forall (C : Prop), (forall (x : A), P x -> C) -> C\ntheorem ex_intro (A : Prop) (P : A -> Prop) (a : A) (h : P a) : Ex A P := by\n  intro C f\n  apply f a\n  assumption' },
```

輸出：

```
✔ def Ex : ∀ (A : Prop), (A → Prop) → Prop
✔ theorem ex_intro : ∀ (A : Prop), ∀ (P : A → Prop), ∀ (a : A), P a → Ex A P
    intro C f
        A : Prop
        P : A → Prop
        a : A
        h : P a
        C : Prop
        f : ∀ (x : A), P x → C
        ⊢ C
    apply f a
        A : Prop
        P : A → Prop
        a : A
        h : P a
        C : Prop
        f : ∀ (x : A), P x → C
        ⊢ P a
    assumption
        沒有目標了
```

**請注意這個定義的三個代價：**

1. **`Ex` 的第二個參數是一個「型別層的函數」`P : A → Prop`**。這不是一般的 Church 編碼（那只需要 `A`、`B` 兩個命題參數），而是需要一個**依值於元素的命題族**。所以 `Ex` 的型別是 $\forall (A : Prop)$ ， $(A \to Prop) \to Prop$ 。
2. **因此這個 `def` 需要 `Prop > Type` 這條規則**——也就是說，**要定義 $\exists$ ，系統必須至少爬到 $\lambda P$ （依值型別）**。我們在第 6.3 節看過，在 $\lambda \to$ 裡連 `Nat -> Prop` 都寫不出來：

```
✘ axiom
    目前的系統不允許這個 Π 型別:定義域屬於 Prop,值域屬於 Type(缺少規則 Prop>Type):Nat → Prop
```

   這就是「∀ 有內建、∃ 沒有」的真正代價：** $\forall$ 在 $\lambda \to$ 裡免費， $\exists$ 要在 $\lambda P$ 裡才付得起。**
3. **證明變長了。** `ex_intro` 要 4 條指令、2 條定義，比 ITP 的 `exI` 節點（`lean.js:101`，一個 `eq()` 比較就完事）麻煩得多。為什麼？因為 Church 編碼的 $\exists$ 沒有一個「建構子」——`exI` 那種「給出見證就完事」的行為，在 Church 編碼裡要寫成一整段延續（continuation）的操作。

## 6.5.3 ATP：量詞消失了

ATP 對量詞的處理是三者中最激進的：**它把量詞從子句集裡徹底抹掉。**

Skolem 化的程式碼是這樣的（`theorem-prover/src/prover.js:60-67`）：

```js
function skolem(f, env, us) {
  switch (f.t) {
    case 'all': { const v = fresh(); return skolem(f.f, { ...env, [f.v]: { v } }, [...us, { v }]); }
    case 'ex': return skolem(f.f, { ...env, [f.v]: { f: 'sk' + (++skn), a: us } }, us);
    case 'and': case 'or': return { t: f.t, l: skolem(f.l, env, us), r: skolem(f.r, env, us) };
    default: { const a = f.t === 'not' ? f.f : f; return { t: 'lit', s: f.t !== 'not', n: a.n, a: a.a.map(x => sub(x, env)) }; }
  }
}
```

兩行做完了所有的事：

- **`case 'all'`： $\forall$ 變成一個自由變數。** 綁定被解開，變數名由 `fresh()` 產生（`_2` 、 `_4` ……），輸出時被 `pv()` 改寫成 `X2` 、 `X4` 。
- **`case 'ex'`： $\exists$ 變成一個 Skolem 函數或常量。** 函數名是 `sk1` 、 `sk2` ……，**它的參數是當時所有的全稱變數**（`us`）。

第二點是 Skolem 化的精髓：**如果 $\exists$ 變數依賴於某個 $\forall$ 變數，Skolem 函數就把它當作參數。** 來看真實輸出：

```bash
node -e "
const P = require('./src/prover.js');
console.log(P.format(P.prove(['forall x. exists y. (Loves(x,y))'], 'exists y. Loves(a,y)')));
"
```

```
✔ 證明成功(產生 3 個子句,0 ms)
  1. Loves(X5,sk1(X5))    [前提]
  2. ~Loves(a,X7)    [否定結論]
  3. ⊥    [歸結 1, 2]
```

第 1 條子句就是 Skolem 化的全部痕跡：原本的 $\forall x . \exists y . Loves(x,y)$ 變成了 `Loves(X5,sk1(X5))`。** $\forall$ 變成自由變數 `X5`； $\exists$ 變成以 `X5` 為參數的 Skolem 函數 `sk1`。** 第 2 條是否定結論 $\neg\exists y . Loves(a,y)$ ，它被 NNF 化時 $\exists$ 變成了對偶的 $\forall$ ，所以 Skolem 化給的是一個**自由變數** `X7` 而不是 Skolem 函數。第 3 條的歸結把 `X5` 合一到 `a` ，於是 `sk1(a)` 與 `X7` 對上，矛盾。

再看一次否定結論帶 $\exists$ 的例子：

```
✔ 證明成功(產生 9 個子句,0 ms)
  1. ~P(X11) | Q(X11)    [前提]
  2. ~Q(X13) | R(X13)    [前提]
  3. P(sk2)    [否定結論]
  4. ~R(sk2)    [否定結論]
  5. Q(sk2)    [歸結 1, 3]
  8. R(sk2)    [歸結 2, 5]
  9. ⊥    [歸結 8, 4]
```

**`sk2` 是個常量**（不是函數），因為它來自否定結論 $\neg\forall x . (P(x) \to R(x))$ —— $\forall$ 在 NNF 裡變成 $\exists$ ，而這個 $\exists$ 不依賴任何全稱變數，於是 Skolem 化給它一個**常量**。整個「對所有 $x$ 」的語意被壓縮成「有一個特定的 $x$ 叫 `sk2` 」。

**這就是 ATP 的量詞哲學： $\forall$ 是自由變數， $\exists$ 是 Skolem 符號，量詞本身在證明過程中不存在。** 它換來的是可搜尋的子句空間，付出的代價有兩項：

1. **不可反推。** 從子句集裡你讀不出「這裡原本有個 $\forall$ 」，只能靠 Skolem 函數的參數個數去猜。
2. **語意假設。** Skolem 化在**古典邏輯**裡是可靠的，但在直觀主義邏輯裡不是——因為 $\exists x . P(x) \to P(c)$ 在直觀主義裡不成立。所以第 6.3 節說的「ATP 天生古典」，在 Skolem 化這裡又得到一次印證：**這是同一個隱藏假設的第二個現場。**

## 6.5.4 對照小結

| | ITP | λ-Cube | ATP |
|---|---|---|---|
| $\forall$ 的表示 | AST 的 `all` 節點 | **Π 型別**（內建） | **自由變數** |
| $\exists$ 的表示 | AST 的 `ex` 節點 | 自己 `def Ex`（需 $\lambda P$ 以上） | **Skolem 函數／常量** |
| $\forall$ 消去的動作 | `allE`：一次帶捕捉安全的代換 | β 歸約 | 不存在（量詞已消失） |
| $\exists$ 消去的動作 | `exE`：**分支 + 新鮮性檢查** | Church 編碼的延續操作 | 不存在（量詞已消失） |
| 「變數新鮮」由誰保證 | **核心檢查**（`lean.js:99`、`:104`） | **不可能發生**（de Bruijn 綁定） | 不需要 |
| 量詞語意的損失 | 無（AST 保留量詞結構） | 無（Π 保留綁定結構） | **有**： $\forall$ 變自由變數、 $\exists$ 變 Skolem 符號 |
| 失敗時的訊息 | `變數名 x 已被使用,請換一個名稱`（策略層）／`核心檢查失敗:變數 x 不夠新`（核心） | `目前的系統不允許這個 Π 型別:缺少規則 Prop>Type` | `✘ 無法證明:子句集已飽和,結論不是前提的邏輯後果` |

三種處理可以排成一句話：

> ** $\forall$ 在 λ-Cube 是「型別」，在 ATP 是「變數」，在 ITP 是「公式裡的一個節點」； $\exists$ 在 λ-Cube 是「自己定義的高階運算」，在 ATP 是「被消掉的符號」，在 ITP 是「需要分支與新鮮性檢查的消去」。**

三個系統對量詞的處理，恰好對應它們的整體哲學：

- λ-Cube 把 $\forall$ 變成**型別**——因為在 Curry–Howard 對應下， $\forall$ 就是 Π，量詞與型別量詞是同一件事。
- ITP 把量詞留在**公式裡**——因為它要保留命題的可讀性與可分解性，使用者必須看得見「這裡有個 $\forall$ 」。
- ATP 把量詞**消掉**——因為它要的是一個可以搜尋的扁平空間，而量詞是那個空間裡最不友好的部分。

下一節處理「否定 + 量詞」的組合，也就是德摩根律。屆時我們會看到三個系統處理「否定」的三種截然不同的方式：ITP 在解析期把它**展開**成 $A \to \bot$ ，ATP 在子句化時把它**對偶化**，λ-Cube 則要自己**編碼**它。
