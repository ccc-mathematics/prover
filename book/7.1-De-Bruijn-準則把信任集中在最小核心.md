# 7.1 De Bruijn 準則：把信任集中在最小核心

第 6 章把同一批數學餵給三個系統，看它們各自怎麼說話。那一章的結論是語言學的：三個系統描述「放棄」的方式不一樣，但它們有一個共同的做法——**都不把「這個命題被證明了」這件事的最終決定權交給整個程式**。本章要處理的就是這個共同做法的工程意義：我們叫它 **de Bruijn 準則**。

準則的內容一句話就能講完：**一個證明輔助系統的可信部分，必須小到可以被一個完整的人獨立審查；而所有可能出錯的部分，都必須被隔離在這個可信部分之外。** 前半句是 de Bruijn 在 1960 年代末設計 Automath 時留下的洞見——Automath 是計算機上第一個證明檢查器（van Benthem Jutting 用它把 Landau 的《分析基礎》整本翻譯並檢查了一遍，這是史上第一本被完整機器檢查的數學書）。後半句則是 2005 年 Henk Barendregt 與 Freek Wiedijk 替這條洞見取的名字：Barendregt 與 Wiedijk 在〈The Challenge of Computer Mathematics〉一文裡把它表述為「de Bruijn 準則」，並引述 de Bruijn 自己的說法——驗證程式只需要看見「在待驗證的那份證明中，少數那幾條邏輯規則是否始終被遵守」；儘管一份證明可以有好幾兆位元，**驗證程式卻可以很短**，短到數學家或邏輯學家可以用平常的方式把它看完。

## 7.1.1 準則的真正內容：不是「小」，是「可獨立重做」

這條準則最容易被誤解成一句程式設計的口號：「核心越小越好」。但如果只這樣理解，它會立刻被兩個反例推翻。第一，真實的 Lean 核心有好幾萬行；把它壓到三十行，並不比把一個玩具壓到三十行更有意義。第二，也是更重要的：**小本身不保證可信**——三十行裡如果藏著一個錯誤的 α 等價判定，同樣會讓錯誤的證明通過。

所以準則真正要求的是三件事，缺一不可：

1. **邊界明確**：可信部分與不可信部分之間有一條可以被指認出來的線。在本專案裡，那條線就是 `src/*.js` 檔案內部的段落邊界：`check()` 是一個函式，策略層是另一組函式，兩者之間沒有任何共享狀態。
2. **可被獨立重做**：一個有耐心的人可以在不讀其他部分的情況下，把這段程式重新寫一遍，並確認兩者行為一致。這要求核心**不依賴**不可信部分的任何資料結構。
3. **可被外部檢查**：核心產生的結果必須是**資料**（證明項、型別），而不是「我覺得對」。資料可以被第三方的檢查器重新驗證。

第三點是本專案三個系統都做到了的地方：`lean-prover` 的核心最後產出的是一棵證明項樹（`sx(pf)`，`lean.js:211`），`lambda-cube` 的核心產出的是一個項與它的型別，`theorem-prover` 的核心產出的是一串子句與推導鏈（`format(r)`，`prover.js:208`）。這些東西都與「誰產生它」無關。換句話說，**三個系統的輸出都是可攜帶的物件，而不是程序內部的狀態**。

## 7.1.2 逐個量化：三個核心各有多大

現在把準則拿來量本專案的三個核心。為了讓數字有意義，先說明「核心」在這裡指的是什麼：**它是唯一有權回答「這個命題被證明了」的程式片段**。

### `lean-prover` 的 `check()`：30 行

```js

  const C = (q, c = ctx) => check(q, c, fl);
  const bad = m => { throw new Error('核心檢查失敗:' + m); };
  const need = (f, t, m) => f.t === t ? f : bad(m + ' 的對象形狀不對');
```

（`lean-prover/src/lean.js:80-83`）

整個函式從 `:80` 到 `:109`，去掉開頭的簽章與結尾的大括號，**28 行有效程式碼**。這 28 行裡有 18 條規則的分支，每條分支平均不到兩行。

### `lambda-cube` 的 `infer()`：22 行

```js

      case 'v': { const e = ctx[ctx.length - 1 - t.i]; if (!e) throw E('自由變數'); return shift(e.ty, t.i + 1); }
```

（`lambda-cube/src/cube.js:94-96`）

`infer()` 從 `:94` 到 `:115`，**22 行**。但嚴格來說，λ-Cube 的可信邊界比這 22 行稍寬一點：`infer()` 依賴同一個 `kernel()` 函式裡的 `conv()`（`:82-90`）、`whnf()`（`:77-81`）、`nf()`（`:91`）與 `sort()`（`:93`）。把整個 `kernel()` 算進去是 `:75-117`，**43 行**。這仍然是很小的數字，但它比 `check()` 多出一層：**λ-Cube 的核心需要自己「跑」一點東西**（做 β 歸約與 δ 展開），而 ITP 的核心只做形狀比對。這是兩個系統在表達力上的直接後果，第 7.2 節會回來細說。

### 為什麼 ATP 的核心反而比較難做小

把三個數字並排放在一起，會看到一個值得停下來的反差：驗證一個**已經寫好的**證明項，只需要 22 到 30 行；自己**產生**一個證明並判斷它對不對，卻要 56 行，而且**這 56 行還不能隨便再壓**。

原因在第 2.4 節講過。ATP 的「核心檢查」實際上不是檢查，而是**執行**。`prove()` 內部的迴圈（`:160-186`）在做四件事：因子化、等式歸結、等式替換、二元歸結。這四件事每一件都必須是**可靠的**，而且它們的可靠性不是「定義上顯然」，而是**靠外部的元定理支撐**的：

- 二元歸結規則是可靠的，因為 Herbrand 定理保證「若公式集不可滿足，則存在一個有限的 Herbrand 展開子集不可滿足」（2.4.1 節）；
- Skolem 化是「等價的」，因為它把存在量詞換成新符號，這個替換保住了可滿足性（4.3 節）；
- 飽和意味著「不滿足」，這個斷言需要 Robinson 的反駁完备性定理（2.4 節的 Robinson 1965）。

**這就是 ATP 核心「小而可信」最難的地方**：它的每一行不只需要對自己的輸入正確，还需要整套元理論成立才能對使用者宣稱「這個命題在邏輯上是後果」。ITP 的核心沒有這個負擔——`check()` 做的事是「這個證明項套用每一條規則都合法」，而「合法」的定義就是規則本身，沒有外部定理。

換句話說：**ITP 的核心小，是因為它只驗證「形式上的正確」；ATP 的核心大，是因為它必須同時保證「語意上的正確」。** 前者是自證的，後者需要哲學。

這一點還有個實際後果：**ATP 的核心無法被獨立重做並取得同樣的信任**。你可以重寫 `check()` 然後確認它對同一批證明項給出同樣的答案；但你重寫 `prove()` 之後，要確認新舊一致，你得重新跑那套 Herbrand／Skolem 的論證——而那正是整個第 2 章、第 4 章的內容。這不是實作上的懶惰，是**信任結構上的差別**。

## 7.1.3 「策略不可信」的實際意義

準則的後半句——「所有可能出錯的部分都必須被隔離」——在本專案裡有非常具體的意義：**策略層寫錯了，只會讓證明失敗，不會讓錯誤的證明通過。**

這不是一句話，是可以示範的。我們手動構造一個假的證明項，直接餵給核心：

```js
try { L.check({ r: 'andE1', p: { r: 'hyp', n: 'h' } }, [['h', { t: 'atom', n: 'P', a: [] }]]); }
catch (e) { console.log(e.message); }
```

輸出是：

```
核心檢查失敗:∧ 消去 的對象形狀不對
```

這正是 `lean-prover/test/test.js:7-8` 的那兩行。這個證明項在結構上是荒謬的：它宣稱用「∧ 消去」規則從一個原子命題 `P` 得到結論，但 `andE1` 要求對象必須是合取式。核心在 `need(C(p.p), 'and', '∧ 消去')` 那一行（`lean.js:90`）擋下它。

再看幾個手寫的偽造證明項會被擋在哪裡：

| 偽造手法 | 核心在哪裡擋下 | 訊息 |
|---|---|---|
| 對原子命題用 `andE1` | `lean.js:90` 的 `need` | 核心檢查失敗:∧ 消去 的對象形狀不對 |
| 用前提為 $Q$ 的 `h2` 去餵 $P$ | `lean.js:96` 的 `eq(i.l, C(p.a))` | 核心檢查失敗:→ 消去的前提不吻合 |
| 引用不存在的假設 | `lean.js:85` 的 `look(ctx, p.n) \|\| bad(...)` | 核心檢查失敗:找不到假設 zz |
| 留下一個沒填的洞 | `lean.js:87` 的 `case 'meta'` | 核心檢查失敗:仍有未解決的目標 |
| 使用不存在的規則名 | `lean.js:108` 的 `return bad('未知的規則 ' + p.r)` | 核心檢查失敗:未知的規則 fraud |

五個嘗試，五個不同的攔截點。這就是「核心有權說不」的具體含義：**不是核心比較聰明，而是核心的每一條分支都被設計成對形狀不對的輸入有反應**。

反過來，還有一類偽造是核心**擋不下**的，值得明說：**一個完全合法、但結論不是宣告命題的證明項**。例如上面那個 `impE` 例子裡，把 `h1` 餵 `hp` 會得到命題 $Q$ ；這是一個完全合法的證明項，核心會快樂地回傳 $Q$ ：

```js
L.check({ r: 'impE', f: { r: 'hyp', n: 'h1' }, a: { r: 'hyp', n: 'hp' } }, ctx);
// => { t: 'atom', n: 'Q', a: [] }
```

這時**是宣告比對擋下它的**，不是核心：

```js
    const pf = inst(S.assign[g0.id], S.assign), fl = {};
    if (!eq(check(pf, ctx, fl), F)) throw new Error('核心推出的命題與宣告不符');
```
（`lean-prover/src/lean.js:209-210`）

這個分工值得停下來想清楚：**核心不知道 theorem 宣告的存在**。它只回答「這個證明項證明了什麼」，然後由外面的執行器拿答案去跟宣告比對。這就是 7.2 節要細談的設計選擇，但它在此處已經顯出價值——因為它意味著核心的職責被壓到了最小。

## 7.1.4 什麼不該放進核心

知道什麼該放進核心之後，反過來問「什麼不該放」更有用。本專案在架構上排除了四類東西，每一類都有具體的理由。

**第一，DSL。** 一個友善的指令語言——像 `cases h with hp hq` 裡的 `with` 子句——是讓人少打字的東西，屬於「寫起來舒服」的範疇，不屬於「判斷對錯」的範疇。`cases` 的核心部分是 `lean.js:158-164`，那裡只處理形狀；「`with` 後面接兩個名字」這個語法糖被消化在 `ws.filter(x => x !== 'with')` 裡，位置在策略層。

**第二，錯誤訊息的美化。** 這是本專案最乾淨的一次分層。核心的錯誤訊息一律是機械的：

```js
  const bad = m => { throw new Error('核心檢查失敗:' + m); };
```
（`lean-prover/src/lean.js:82`）

而策略層的錯誤訊息是給人看的：

```js
  const is = (t, m) => { if (f.t !== t) throw new Error(`${name} 不適用:目標是 ${fm(f)}${m || ''}`); };
```
（`lean-prover/src/lean.js:136`）

注意兩者的差異不只是措辭：**策略層的訊息裡有 `fm(f)`，也就是把命題重新印成人看得懂的樣子**；核心完全不做這件事。核心的訊息只描述「形狀不符」這個事實，不描述「你本來想做什麼」。這是刻意的：核心一旦開始嘗猜使用者的意圖，它就開始需要上下文，而上下文正是它不該依賴的東西。

**第三，效能優化。** `conv()` 用的是全結構比較（`cube.js:82-90`），`whnf()` 是個可能無限迴圈的迴圈（`cube.js:77-81`），`nf()` 是遞迴正規化（`cube.js:91`）——這些都不是最佳化演算法。`lambda-cube/README.md` 的「限制」段落直說：「化簡用『定義等價』而非最佳化,大型項會很慢。」這是核心設計的**已知代價**，不是缺陷：因為核心一旦開始追求速度，就會開始引入快取、共享狀態、暫存表——而那些東西全都難以審查。第 7.2 節會把這筆帳算清楚。

**第四，自動搜尋。** ITP 的核心不做搜尋（證明項是使用者透過策略給的），λ-Cube 的核心也不做搜尋。ATP 的核心**必須**做搜尋——這正是它 56 行的原因，也是 7.1.2 節討論過的取捨。

## 7.1.5 一個常見的誤解：核心小不代表核心不用長大

最後要澄清一件事，因為它會在下兩節不斷出現。

常有人看到本專案的核心只有二三十行，就以為「可信核心就該這麼小」。這是錯的。第 8.1 節要盤點的三個缺口——等號、歸納型別、宇宙階層——每一個都必須動核心：加等號要加 `eqI` / `eqE` / `eqRefl` 三條規則；加歸納型別要加 recursor 的型別推導；加宇宙階層要改 `sort()` 與 `case 's'`。真實的 Lean 核心有幾萬行。

**核心小的真正意思不是「核心永遠停在三十行」，而是「核心裡的每一行都對應一條被明確命名過的推理規則」。** 本專案的核心之所以小，不是因為它省略了什麼，而是因為它**把規則的數目壓到了極致**：ITP 的核心只認六種命題形狀、18 條規則，λ-Cube 的核心只認五種項節點、七個分支。

這也是 de Bruijn 準則在實作層面的真正要求：核心不需要小，但核心必須**可被逐行對照到一個明確的規則清單**。讀者讀 `check()` 的 `switch` 時，應該能逐個 `case` 說出「這是自然演繹的哪一條規則」；讀 `infer()` 的 `switch` 時，應該能逐個 `case` 說出「這是型別論的哪一條形成規則」。做不到這件事的核心，再小也不符合準則。

## 小結與交棒

de Bruijn 準則要求：**可信部分小到可被完整審查，所有可能出錯的部分被隔離在外**。本專案的三個核心是 30 行、22 行（連同輔助共 43 行）、56 行；前兩個小，因為它們只驗證「形式上的正確」，第三個大，因為它必須同時保證「語意上的正確」，而後者需要 Herbrand 與 Skolem 的元定理撐腰。

準則的後半句在本專案裡有一個可以親手示範的版本：**策略層寫錯了，只會讓證明失敗，不會讓錯誤的證明通過**。我們手寫了五種偽造證明項，五個都被核心擋下，而且擋下的位置各不相同。

下一節要問的是一個更細的問題：既然核心小到可以逐行唸出來，那**它應該長什麼形狀**？具體來說，`check()` 回傳「證明項所證明的命題」，`infer()` 回傳「項的型別」——這兩個東西看起來是不同的工作，但背後其實是同一件事的兩種視角。

下一節：**核心的形狀：`check()` 與 `infer()` 的對稱。**
