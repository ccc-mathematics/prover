# 7.2 核心的形狀：`check()` 與 `infer()` 的對稱

第 7.1 節把「核心必須小」這件事量化了：30 行、22 行、56 行。但大小只是外部的量度，真正決定一個核心好不好審查的，是它的**內部形狀**。這一節要處理的核心問題是：`lean-prover` 的核心回傳「證明項所證明的命題」，`lambda-cube` 的核心回傳「項的型別」，這兩件事看起來是兩份不同的工作——為什麼它們其實是同一件事？

## 7.2.1 同一件事的兩種視角

先看兩個函式的簽章：

```js
function check(p, ctx, fl = {}) {
```
（`lean-prover/src/lean.js:80`）

```js
  function infer(ctx, t) {
```
（`lambda-cube/src/cube.js:94`）

`check` 收的是**證明項** `p`，`infer` 收的是**項** `t`。兩者的上下文都是一個陣列（`ctx`）。但回傳值是關鍵：

- `check(p, ctx)` 回傳的是 `$p$ 所證明的命題`——也就是說，**輸入是證明，輸出是命題**；
- `infer(ctx, t)` 回傳的是 `t` 的型別——也就是說，**輸入是項，輸出是型別**。

在 Curry–Howard 對應之下，這兩句話是同一句話。「證明項證明了命題」讀成「證明項有型別 $\mathrm{Prop}$ 」；「項有型別」讀成「項是一個證明，而它的型別是被證明的命題」。第 5 章花了一整章建立這個對應，第 3.3 節則指出 `check()` 的設計是「**檢查與推導是同一個動作**」。這裡可以把那句話說得更狠：**`check()` 與 `infer()` 是同一個演算法在兩種邏輯裡的實作**。

差異只在**等價判定的標準**：

| | ITP（`check()`） | λ-Cube（`infer()`） |
|---|---|---|
| 兩個項什麼時候算同一個？ | α 等價 | βδ 定義等價（`conv()`） |
| 判定函式 | `eq()` = `key(a) === key(b)`（`lean.js:57`） | `conv()`（`cube.js:82-90`） |
| 名字 | 綁定名稱不同也算同一個 | 綁定名稱不同也算同一個（de Bruijn 索引） |

ITP 之所以只需要 α 等價，是因為它的證明項是**語法樹**：每個節點帶著自己的規則名，而規則的形式由核心的 `switch` 決定。λ-Cube 需要 βδ 等價，是因為它的項帶著**計算內容**：一個 `Ap` 節點套用在 λ 抽象上，會化簡成別的東西。

換句話說：**λ-Cube 的核心必須會算，ITP 的核心不必**。這是兩者形狀分歧的第一個原因，也是它們大小不同（22 行對 30 行，但 λ-Cube 還得外加 `conv` / `whnf` / `nf` / `sort` 四個輔助，共 43 行）的直接後果。

## 7.2.2 對照表：簽章、回傳值、失敗方式、遞迴結構、輔助函式

把兩個核心並排攤開，會看到一個幾乎逐格對應的結構。

| 面向 | `check()`（lean.js:80-109） | `infer()`（cube.js:94-115） |
|---|---|---|
| 簽章 | `check(p, ctx, fl = {})` | `infer(ctx, t)` |
| 第一個參數 | 證明項 `p`（`{ r: 'impE', ... }`） | 項 `t`（`{ k: 'a', ... }`） |
| 上下文 | `ctx`：`[名稱, 公式]` 的陣列 | `ctx`：`{ n, ty }` 的陣列 |
| 第三參數 | `fl`：副作用旗標物件 | 無（旗標閉包捕捉） |
| 回傳值 | 命題樹 | 型別樹 |
| 失敗方式 | `throw new Error('核心檢查失敗:' + m)` | `throw new Error(m)`（`E` 輔助，`cube.js:76`） |
| 分派機制 | `switch (p.r)`（規則名） | `switch (t.k)`（節點形狀） |
| 遞迴方式 | 局部輔助 `C(q, c = ctx)` 帶著 ctx 遞迴 | 直接呼叫 `infer(ctx', t')` |
| 輔助「形狀檢查」 | `need(f, t, m)` | `sort(ctx, T)` / `whnf(t)` |
| 輔助「相等判定」 | `eq(a, b)` | `conv(a, b)` |
| 「洞」的處理 | `case 'meta'` → 拒絕（`lean.js:87`） | `case 'm'` → 拒絕（`cube.js:100`） |
| 「作弊」的處理 | `case 'sorry'` → 設旗標（`lean.js:86`） | `case 'z'` → 設旗標（`cube.js:99`） |

值得逐格說明三個地方。

**第一，失敗方式幾乎一樣，但訊息前綴不同。** ITP 的核心錯誤一律帶「核心檢查失敗:」前綴（`lean.js:82`），λ-Cube 的核心錯誤則是裸訊息（`cube.js:76` 的 `const E = m => new Error(m);`）。這個差異不是美學問題，而是**架構差異的後果**：ITP 的策略層錯誤與核心錯誤是兩種錯誤，必須能被使用者分辨（1.3 節的「五種狀態」表格裡，`error` 與 `kernel` 是分開的兩格），所以核心錯誤需要一個專屬前綴；λ-Cube 沒有獨立的 `kernel` 狀態（它的核心例外在 `runScript` 的 `try` 裡被接住，記成 `error`），訊息裡靠「核心」二字辨認（`cube.js:204` 的「核心推出的型別與宣告不符」）。

**第二，遞迴方式的差異反映兩種資料結構的差異。** ITP 的 `check` 用了一個局部箭頭函式：

```js
  const C = (q, c = ctx) => check(q, c, fl);
```
（`lean-prover/src/lean.js:81`）

這個 `C` 的存在理由是**旗標物件的傳遞**：`fl` 必須一路跟著遞迴走，`sorry` 節點才能在深處被標記上。這是 `check()` 唯一「多餘」的參數——若拿掉 `fl`，`check` 的簽章就會跟 `infer` 一模一樣。λ-Cube 的旗標 `fl` 則是在 `kernel()` 的閉包裡被捕捉的（`cube.js:75` 的 `function kernel(G, rules, fl)`），所以 `infer` 本身只需要兩個參數。**這就是兩個核心簽章差一點點的全部原因**，而且那個差異完全由「副作用旗標住在哪裡」決定。

**第三，輔助函式的分工是同一套模式。** `need(f, t, m)` 檢查「這個東西的形狀對不對」，不對就丟出帶說明的錯誤；`sort(ctx, T)` 做同樣的事，只不過它多一步 `whnf`（因為型別可能是個還沒展開的 `def`）。`eq(a, b)` 問「這兩個公式是不是同一個命題」；`conv(a, b)` 問「這兩個項是不是同一個東西」。

**兩個輔助的哲學差異值得停一下。** `eq` 是 `key(a) === key(b)`——把命題正規化成一個字串再比。這是一個**終止的、沒有副作用的**判定。`conv` 卻是：

```js
  const conv = (a, b) => {
    a = whnf(a); b = whnf(b); if (a.k !== b.k) return false;
```
（`lambda-cube/src/cube.js:82-83`）

`whnf` 是一個 `for (;;)` 的無限迴圈（`cube.js:77-81`）。**在語意上，`conv` 是一個可能不終止的程式。** 因為 `whnf` 會無條件展開 `def` 的值（`cube.js:79`），而 `def` 不能遞迴這件事不是核心檢查的，而是靠使用者的自律。`lambda-cube/README.md` 的「限制」段落列了這一條：「`def` 不能遞迴」。

這是本章第一個真正的**核心形狀差異**：ITP 的核心是「總會終止的」——它的每一條分支都是有限的形狀比對，遞迴深度等於證明項的高度。λ-Cube 的核心是「可能不終止的」——它的判定需要跑歸約，而歸約的長度取決於使用者寫了什麼。

**這一條差異有實際後果**：一個 ITP 核心的審查者，只要確認了 `switch` 的每個分支，就**同時**確認了它的終止性。一個 λ-Cube 核心的審查者，還必須額外確認展開過程會停下來。這在第 8.1 節會回來——`def` 不能遞迴這條限制，正是核心裡缺了一個「守衛」的後果。

## 7.2.3 「回傳命題再與宣告比對」這個設計的價值

現在可以解釋 7.1.3 節留下來的問題：為什麼 `check()` 不直接接受一個宣告，而是回傳命題再讓外面比對？

答案是因為**這樣核心就不需要知道 theorem 宣告的存在**。看三個地方的對照：

**ITP 的比對在核心之外：**

```js
    const pf = inst(S.assign[g0.id], S.assign), fl = {};
    if (!eq(check(pf, ctx, fl), F)) throw new Error('核心推出的命題與宣告不符');
    r.status = fl.sorry ? 'sorry' : 'done'; r.term = sx(pf);
```
（`lean-prover/src/lean.js:209-211`）

**λ-Cube 的比對也在核心之外：**

```js
            fl.sorry = false; const full = wrap(Lm, bs, fill(S.assign[g0.id], S.assign));
            if (!K.conv(K.infer([], full), decl)) throw new Error('核心推出的型別與宣告不符');
```
（`lambda-cube/src/cube.js:203-204`）

注意 `K.infer([], full)` 的第二個引數是**空上下文**——宣告的綁定變數都已經被 `wrap(Lm, bs, ...)` 包成 λ 抽象了，所以推導時不需要上下文。核心只看見「一個項，推導出它的型別」。

這個設計帶來四個好處。

**第一，核心可以被獨立測試。** 這是最實際的一個好處，而且已經被用上了：`lean-prover/test/test.js:7-8` 直接呼叫 `L.check(偽造證明項, 假設清單)`，完全沒有 theorem 宣告、沒有策略層、沒有 `runThm`。如果 `check()` 的簽章是 `check(p, ctx, decl)`，那個測試就得先構造一個宣告，而偽造證明項的測試會變得囉嗦。

**第二，核心的輸入輸出都是純資料。** `check(p, ctx)` 的輸入是一個 JSON 化得掉的樹與一個陣列，輸出是一個 JSON 化得掉的樹。這意味著**第三方可以獨立實作一個檢查器**，餵同一批證明項進去，看答案是否一致——這正是 de Bruijn 準則的第三條要求（「可被外部檢查」）在實作層面的樣子。

**第三，比對的失敗與核心的失敗可以分開診斷。** 7.1.3 節那個例子已經展示過：一個合法的證明項推導出 $Q$ ，而宣告是 $P \to R$ ，於是錯誤發生在 `lean.js:210` 的比對處，訊息是「核心推出的命題與宣告不符」。使用者一看就知道：**證明項本身沒問題，是它證明的東西跟我要的不一樣**。這跟「核心檢查失敗」是完全不同的兩件事。

**第四，核心不必處理宣告的形式多樣性。** ITP 的宣告可以是 `theorem 名稱 (h1 : P) (h2 : Q) : R := by`，任何形式；λ-Cube 的宣告可以是 `theorem name (A : Prop) (x : A) : B := by`，任何形式。核心都不 care——它只看見「一個證明項」與「一組假設」。

## 7.2.4 效能與大小的取捨：核心設計的已知代價

現在來算那筆帳。三個核心的設計都為了「可審查」付出了具體的代價，而且這些代價都被記錄在本專案的 README 裡。

**第一項：`conv()` 的全結構比較。**

```js
      case 'a': return conv(a.f, b.f) && conv(a.a, b.a);
      case 'l': case 'p': return conv(a.ty, b.ty) && conv(a.b, b.b);
```
（`lambda-cube/src/cube.js:86-87`）

`conv` 沒有任何快取，沒有 hashconsing，沒有「先比大小再比內容」這種啟發式。它就是老老實實地走兩棵樹。**同一個型別被比對兩次，就重算兩次。** 這在教學用的規模下完全沒問題，但在一個有上萬個定理的環境裡，這個核心會是瓶頸。

**第二項：`whnf()` 的迴圈。**

```js
  const whnf = t => { for (;;) {
    if (t.k === 'a') { const f = whnf(t.f); if (f.k === 'l') { t = inst(f.b, t.a); continue; } return Ap(f, t.a); }
    if (t.k === 'c' && G[t.n] && G[t.n].val) { t = G[t.n].val; continue; }
    return t;
  } };
```
（`lambda-cube/src/cube.js:77-81`）

`whnf` 只做頭部展開，但它**沒有任何「展開過幾次」的計數，也沒有大小遞減的檢查**。所以一個自我指涉的 `def` 會讓它無限轉下去。這是第 7.2.2 節提過的「可能不終止」的具體來源。

**第三項：`nf()` 的遞迴正規化。**

```js
  const nf = t => { t = whnf(t); return t.k === 'a' ? Ap(nf(t.f), nf(t.a)) : bind(t) ? { k: t.k, n: t.n, ty: nf(t.ty), b: nf(t.b) } : t; };
```
（`lambda-cube/src/cube.js:91`）

`nf` 把**整棵子樹**正規化。對一個深度 $n$ 的項，呼叫 `nf` 的複雜度是 $O(n)$ 乘上每個節點的展開成本——而展開成本又取決於 `def` 的大小。一個巢狀三層的 `def` 展開後，項的大小可能是原始的數十倍。

**第四項：ITP 這邊的對應代價。** ITP 的核心不需要化簡，所以沒有這些負擔；但它換來了另一個代價：**證明項必須自足**。每一個 `impI` 節點都自帶它的前提公式（`lean.js:95` 的 `case 'impI': return { t: 'imp', l: p.f, r: ... }`），所以證明項比「只記規則名」的最小表示大。這個代價很小，卻是必須付的——3.3 節已經說過：如果 $A$ 只能從上下文推導，核心就要嘛信任它、要嘛重新推導它。

這三項加起來，就是 `lambda-cube/README.md` 那句話的全部內容：

> 化簡用「定義等價」而非最佳化,大型項會很慢。

**這筆帳是值得的**，理由有三個。

第一，**核心的正確性是可優先的**。一個被最佳化過的核心裡，會出現快取失效、指標共享、隱式狀態——每一個都是審查者必須額外推理的東西。「慢」只是體驗問題；「可能悄悄算錯」是信任問題。de Bruijn 準則的權衡是明確的：**寧可慢，不要不可查。**

第二，**慢的部分是可以往上搬的**。如果 `conv` 真的太慢，可以在外面加一層**快取**——但那層快取必須放在核心之外，因為一旦放進去，核心就不再是核心了。這個選項的存在，正是「核心小」這個架構決定的。

第三，**代價是可以被記錄的**。README 的「限制」段落把「大型項會很慢」寫下來，等於向使用者宣告：這個核心的設計選擇有已知後果，且後果已知。8.1 節講 η 規則時，會回到 `conv` 的 `l` 分支，說明加 η 規則要動核心、並且需要先補一個「項的自由變數計算器」——那正是把「慢」這個問題推到底會遇到的牆。

## 7.2.5 那麼，ATP 的核心為什麼長得完全不一樣

把前兩節的方法套到 ATP 上，會立刻得到矛盾：`prove()` 不回傳命題，也不回傳型別。它回傳的是一個**狀態物件**。

```js
    return { status, steps, generated, ms, hasGoal: !!goal };
```
（`theorem-prover/src/prover.js:196`）

這個差別不是隨意的，而是 7.1.2 節講過的那件事的必然結果。讓我們把邏輯攤開：

- ITP 與 λ-Cube 的核心是**檢查器**。它假設證明項已經存在（ITP）或項已經存在（λ-Cube），只驗證它們合不合法。
- ATP 的核心是**搜尋器**。它自己產生子句，所以它沒有「給定一個東西來檢查」這種介面可言。

因此 ATP 的核心有幾個 ITP 沒有的特徵：

**它需要回報「我放棄了」。** ITP 的核心永遠不會「放棄」——給它一個證明項，它要嘛通過、要嘛丟例外。ATP 的核心有三種結局（`prover.js:196` 加上 `:161`、`:162`）：`proved`（找到空子句）、`saturated`（子句空間用完）、`timeout`（資源用完）。後兩種是**資訊量不對稱的**：`proved` 是确定的，`saturated` 是可信但需保留的，`timeout` 是空洞的（1.1 節講過）。

**它的輸出是「一串子句」而不是「一棵樹」。** `steps` 陣列裡每一項是一個子句加上它的規則名與來源（`prover.js:194`）。這是因為歸結的推理鏈是**線性的**（每一條新子句由兩個舊子句推出），不像證明項那樣是一棵可以獨立檢查的樹。

**它的核心內含剪枝。** `accept()` 裡的包含檢查與 `prune()`（`prover.js:146-154`）是**語意**上的判斷（「這個子句被那個更強的子句包含了嗎」），不是形狀上的判斷。這個判斷一旦出錯，錯誤的子句會被丟掉，而真正的矛盾可能正好在那個被丟掉的子句裡——**後果是漏掉一個真命題，而不是接受一個假命題**。方向是安全的，但「安全」不等於「可靠」：剪枝的正確性需要子句包含關係的健全性（第 4.6 節的主題）。

**所以 ATP 核心的「回傳值再與宣告比對」這一招用不上。** ITP 可以說「核心推出什麼命題，跟宣告比一比」，因為核心的輸出是一個可以跟宣告比較的**物件**。ATP 的輸出是一個**程序**，一個程序沒辦法跟一個宣告比較。

## 小結與交棒

兩個核心看起來不同，實際上在做同一件事：**給定一個樹狀證據，遞迴地推導出它的型別**。`check()` 推導出的是命題，`infer()` 推導出的是型別，在 Curry–Howard 之下這是同一個詞。

它們的形狀差異只有三個來源：**等價判定的標準**（α 等價對 βδ 等價）、**是否需要計算**（不需要對需要，因而 λ-Cube 多出 `conv` / `whnf` / `nf` / `sort` 四個輔助，也因而多了一個「可能不終止」的風險）、**以及副作用旗標住在哪裡**（`fl` 參數對閉包捕捉）。

而「回傳命題再與宣告比對」這個設計，是整個架構裡最被低估的一個決定：它讓核心不需要知道 theorem 宣告的存在，讓核心可以被獨立測試（`test/test.js:7-8` 就在這樣做），讓核心的錯誤與比對的錯誤可以分開診斷，也讓核心的輸入輸出都是可攜帶的純資料。

同時，這一節也把三個核心的代價算清楚了：`conv()` 的全結構比較、`whnf()` 的無限迴圈、`nf()` 的遞迴正規化，全部是為了「可審查」而付出的。**核心慢不要緊，核心不可查才要緊。**
