# 7.3 策略層的設計：目標棧與洞的填補

第 7.2 節結束在核心的邊界上。核心的輸入是一個**已經完成的證明項**，但使用者寫的從來不是證明項——他們寫的是一行行指令。所以中間必須有一層，把「指令」變成「證明項」。這就是策略層。

本專案的兩個 ITP——`lean-prover` 與 `lambda-cube`——策略層的結構幾乎一模一樣。本節要做的，是把這個「幾乎一模一樣」攤開，然後解釋為什麼它值得被設計成這個樣子，以及它跟真實系統的差距在哪裡。

## 7.3.1 兩個策略層的骨架

先看兩個 `tactic()` 函式的開頭。這裡有六行值得逐字比對：

**ITP：**

```js
function tactic(S, name, arg) {
  const g = S.goals[0]; if (!g) throw new Error('已經沒有目標了');
  const { ctx, f } = g, M = x => ({ r: 'meta', id: x.id });
  const solve = (pf, gs = []) => { S.assign[g.id] = pf; S.goals = [...gs, ...S.goals.slice(1)]; };
```
（`lean-prover/src/lean.js:129-132`）

**λ-Cube：**

```js
function tactic(K, G, S, name, arg) {
  const g = S.goals[0]; if (!g) throw new Error('已經沒有目標了');
  const ctx = g.ctx, ns = ctx.map(e => e.n), d = ctx.length;
  const solve = (pf, gs = []) => { S.assign[g.id] = pf; S.goals = [...gs, ...S.goals.slice(1)]; };
```
（`lambda-cube/src/cube.js:120-123`）

除了 λ-Cube 多兩行（算 `ns` 與 `d`，供 `assumption` 與顯示用），**`solve` 那行是逐字相同的**：

```js
const solve = (pf, gs = []) => { S.assign[g.id] = pf; S.goals = [...gs, ...S.goals.slice(1)]; };
```

這一行裡有三個動作，每一個都對應一個設計決定：

**動作一：`S.assign[g.id] = pf`。** 把「這個目標的證明片段」記到一張以目標編號為索引的表裡。這張表就是**洞的填補表**。

**動作二：`S.goals = [...gs, ...S.goals.slice(1)]`。** 把棧頂的目標換成 `gs` 這組新目標，剩下的目標原封不動地往後挪。

**動作三：`S.goals.slice(1)` 這個 `1`。** 它表示「只取棧頂那一個」，而 `gs` 插在**前面**。所以新產生的目標**優先於**原本排队的目標被處理。

這三個動作合起來，就是「目標導向程式設計」在證明上的應用：一個目標棧（`S.goals`）、一個洞的填補表（`S.assign`）、以及一個同時更新兩者的函式（`solve`）。

## 7.3.2 目標棧：一個受限但好用的模型

`S.goals` 是一個陣列，元素是「目標」物件。兩個專案的目標結構不同，但概念相同：

**ITP 的目標**（`lean.js:194`）：

```js
  const S = { goals: [], assign: {}, sorry: false, mk: (c, v, f) => ({ id: ++n, ctx: c, vars: v, f }) };
```

**λ-Cube 的目標**（`cube.js:191`）：

```js
        const S = { goals: [], assign: {}, n: 0 }, g0 = { id: ++S.n, ctx: bs, ty }; S.goals = [g0];
```

兩個目標都有**編號**（`id`）、**上下文**（`ctx`）、**要證的東西**（ITP 的 `f` 是命題，λ-Cube 的 `ty` 是型別）。ITP 的目標還多一個 `vars`（記錄這個目標裡用過哪些變數名，供 `intro` 檢查名字衝突用）。

棧的行為由 `solve` 完全決定。讓我們用它跑一遍 `lean-prover/examples/syllogism.lean` 的策略序列，看棧的變化：

| 指令 | 棧頂目標 | 執行後的棧 |
|---|---|---|
| （初始） | `⊢ P → R` | `[P → R]` |
| `intro hp` | `⊢ P → R` | `[P, R]` |
| `apply h2` | `⊢ P` | `[Q, R]` |
| `apply h1` | `⊢ Q` | `[P, R]` |
| `exact hp` | `⊢ P` | `[]` |

注意 `apply h2` 那一步：`h2` 的型別是 $Q \to R$ ，目標是 $R$ ，所以 `apply` 開出一個新目標 $Q$ 。棧變成 `[Q, R]`——新目標在前面。

再注意 `exact hp` 那一步：`hp` 的型別是 $P$ ，目標是 $P$ ，`exact` 不開新目標，直接把棧頂消掉。

**棧這個模型的三個好處：**

**第一，它把「進度」變成一個可以印出來的東西。** `showGoals` 就是印這個棧：

```js
const showGoals = gs => gs.length ? (gs.length > 1 ? gs.length + ' 個目標\n\n' : '') + gs.map(showGoal).join('\n\n') : '沒有目標了';
```
（`lean-prover/src/lean.js:218`；`lambda-cube/src/cube.js:226` 逐字相同）

兩個系統的 `showGoals` 一字不差，因為「目標棧」這個概念本身是一樣的。這是 7.2 節說過的「同一個骨架的三次實作」在報告層的投影。

**第二，它讓「證明尚未完成」變成一個自然的狀態。** 棧不空就是還沒證完。`runThm` 裡的這行：

```js
  if (S.goals.length) { r.status = 'open'; return r; }
```
（`lean-prover/src/lean.js:207`）

**第三，它讓錯誤的定位變得容易。** 因為棧是有序的，`--trace` 印出的每一個快照就是「第 $i$ 條指令之後的棧」，可以逐條對照讀者腦中的推理。

**棧這個模型的限制也同樣清楚，而且正是下一節要處理的：棧頂限制。**

## 7.3.3 洞（meta）：策略產生的是「含洞的片段」

現在說到本節最關鍵的機制：**洞**。

一條策略不會直接產生完整的證明項。它產生的是一個**含洞的片段**——洞就是「這個位置還沒證明，但等一下會有東西填進來」。

**ITP 的洞**是一個規則節點：

```js
  const { ctx, f } = g, M = x => ({ r: 'meta', id: x.id });
```
（`lean-prover/src/lean.js:131`）

**λ-Cube 的洞**是一個項節點：

```js
const V = i => ({ k: 'v', i }), Sx = s => ({ k: 's', s }), Ap = (f, a) => ({ k: 'a', f, a }), Cn = n => ({ k: 'c', n }), Mv = id => ({ k: 'm', id });
```
（`lambda-cube/src/cube.js:7`）

注意 `M` 與 `Mv` 都是**建立洞的函式**。策略在需要一個「未來會被證明的東西」的位置，就放一個洞進去，並且**記下它的編號**（`x.id` 是目標的編號）。

洞怎麼被填？兩個專案各有一個函式負責，位置幾乎一樣：

**ITP 的 `inst()`：**

```js
const inst = (p, A) => Array.isArray(p) ? p.map(x => inst(x, A)) : p && typeof p === 'object'
  ? (p.r === 'meta' ? inst(A[p.id], A) : Object.fromEntries(Object.entries(p).map(([k, v]) => [k, inst(v, A)]))) : p;
```
（`lean-prover/src/lean.js:177-178`）

**λ-Cube 的 `fill()`：**

```js
const fill = (t, A) => t.k === 'm' ? fill(A[t.id], A) : t.k === 'a' ? Ap(fill(t.f, A), fill(t.a, A)) : bind(t) ? { k: t.k, n: t.n, ty: t.ty, b: fill(t.b, A) } : t;
```
（`lambda-cube/src/cube.js:165`）

兩個函式的邏輯完全一樣：**遍歷整棵樹，遇到洞節點就拿 `A[洞的編號]` 換掉它，然後繼續往下填。** `A` 就是那張填補表 `S.assign`。

填補的時機在證明結束之後：

**ITP（`lean.js:209`）：** `const pf = inst(S.assign[g0.id], S.assign), fl = {};`

**λ-Cube（`cube.js:203`）：** `const full = wrap(Lm, bs, fill(S.assign[g0.id], S.assign));`

注意 ITP 是 `inst(S.assign[g0.id], S.assign)`——**先取棧頂（也就是最後剩下的那個目標）的片段作為根，再用整張表去填**。λ-Cube 多一步 `wrap(Lm, bs, ...)`，因為它的宣告有綁定變數，要把 `bs` 包成 λ 抽象。

**這個機制的漂亮之處在於：填洞的順序完全不影響結果。** 這是「洞」相對於「巢狀結構」的關鍵優點。舉個例子：`apply` 產生多個前提目標時，證明項是巢狀的：

```js
    case 'apply': {
      const [pf, F] = app(arg, ctx), prem = []; let c = F;
      while (!eq(c, f)) { if (c.t !== 'imp') throw new Error(`apply 失敗:${fm(F)} 的結論無法吻合目標 ${fm(f)}`); prem.push(c.l); c = c.r; }
      const gs = prem.map(a => ng(ctx, a));
      return solve(gs.reduce((p, x) => ({ r: 'impE', f: p, a: M(x) }), pf), gs);
    }
```
（`lean-prover/src/lean.js:147-152`）

這裡 `gs.reduce` 產生的是巢狀的 `impE` 鏈：`impE(pf, 洞1)` 套在 `impE(洞1, 洞2)` 外面之類的結構。如果用「巢狀填空」而不是「洞」，你就得規定「先填最內部的洞」——而在巢狀很深時這很容易搞錯。用洞就不用管：所有的洞都在同一張表裡，遍歷時順便填，順序無關。

**這也是核心為什麼要拒絕洞的原因。** 洞是策略層的中間產物，核心不應該見到它：

**ITP：**
```js
    case 'meta': return bad('仍有未解決的目標');
```
（`lean-prover/src/lean.js:87`）

**λ-Cube：**
```js
      case 'm': throw E('仍有未解決的目標');
```
（`lambda-cube/src/cube.js:100`）

如果 `inst()` / `fill()` 有任何遺漏（洞沒填滿、填補表少一項），核心就會在這裡拒絕。這是第 7.1 節說的「核心不假設任何關於策略層的東西」的最後一道保險：**策略層就算整個壞掉，核心也不會因此接受一個壞證明。**

## 7.3.4 策略清單：兩邊都有什麼，兩邊差在哪

現在可以回答本節開頭的問題了：為什麼 `lean-prover` 有 13 條策略而 `lambda-cube` 只有 6 條？

先列清單：

| 策略 | ITP（`lean.js`） | λ-Cube（`cube.js`） | 說明 |
|---|---|---|---|
| `intro` | `:139` | `:128` | 引入假設／綁定 |
| `exact` | `:145` | `:134` | 用現成的東西完成目標 |
| `assumption` | `:146` | `:139` | 用上下文裡的某個假設 |
| `apply` | `:147` | `:140` | 為前提開新目標 |
| `have` | `:165` | `:151` | 加入新假設 |
| `sorry` | `:171` | `:161` | 標記為未真正證明 |
| `constructor` | `:153` | — | 目標是 $A \wedge B$ 時拆成兩個 |
| `left` / `right` | `:154` | — | 目標是 $A \vee B$ 時選一邊 |
| `exists` | `:155` | — | 目標是 $\exists x . P(x)$ 時給見證 |
| `exfalso` | `:156` | — | 目標改成 $\bot$ |
| `by_contra` | `:157` | — | 古典反證 |
| `cases` | `:158` | — | 拆開 $\wedge$ / $\vee$ / $\exists$ 假設 |
| `show` | `:170` | — | 檢查目標是不是某個式子 |

**兩邊都有的六條**：`intro`、`exact`、`assumption`、`apply`、`have`、`sorry`。這六條構成的是「**核心支援的通用骨架**」——它們在兩個系統裡做的事本質相同。

**只有 ITP 有的七條**，全都是**邏輯連接詞的專用策略**：`constructor`、`left` / `right`、`exists`、`exfalso`、`by_contra`、`cases`、`show`。

這個分布不是偶然的，它有非常清楚的成因：**λ-Cube 沒有邏輯連接詞**。

第 5.6 節講過： $\wedge$ 、 $\vee$ 、 $\exists$ 、 $\bot$ 在 λ-Cube 裡全是用 Π 型別定義出來的（Church 編碼）。既然它們不是核心認得的東西，策略層就不需要「拆開它們」的專用策略——**通用策略就夠了**。

我們可以拿 `cases` 跟 `intro` 對照著看：

**ITP 的 `cases`（`lean.js:158-164`）** 有一大段 `if (A.t === 'and') ... if (A.t === 'or') ... if (A.t === 'ex') ...`，因為它必須判斷被拆的假設是什麼形狀，然後產生對應的證明項（`andE1` / `orE` / `exE`）。

**λ-Cube 沒有 `cases`**，因為它沒有東西可拆。Church 編碼的 $\wedge$ 是一個 Π 型別，`intro` 就能拆開它——這正是 `lambda-cube/examples` 裡 Church 編碼範例的寫法：

```
theorem and_swap (A B : Prop) (h : And A B) : And B A := by
  intro C f
  apply h C
  intro a b
  apply f
  assumption
  assumption
```

`intro C f` 把 `And A B` 展開成 $\forall C . (A \to B \to C) \to C$ 的兩個 Π，一次解決。**ITP 需要 `cases` 加上 `constructor` 加上 `left` / `right` 加起來才做得到的事，λ-Cube 用 `intro` 一條就做完了**——代價是使用者要自己把 Church 編碼的結構寫出來。

同樣的對照也解釋了 `exfalso` 與 `by_contra` 為什麼是 ITP 專有：它們是**古典邏輯**的操作。λ-Cube 的核心是直觀主義的（`intro` 對應 Π 抽象，沒有雙重否定消去），所以策略層根本沒有「反證」這回事可用。第 8.2 節會回頭細講這件事。

反過來，**λ-Cube 有一個 ITP 沒有的能力**：`intro` 可以一次處理多個名字。

```js
    case 'intro': {
      if (ws.length > 1) return ws.forEach(w => tactic(K, G, S, 'intro', w));
```
（`lambda-cube/src/cube.js:129`）

這是因為 λ-Cube 的宣告可以有任意多個綁定（`theorem name (A : Prop) (B : Prop) (x : A) : B := by`），而 ITP 的 `intro` 一次只引入一個。這個差異是語言的：ITP 的命題裡蘊含是巢狀的，λ-Cube 的 Π 也是巢狀的，但 λ-Cube 的宣告是**多變數的綁定列表**，一次拆開比較自然。

## 7.3.5 「只作用於棧頂」這個限制

回到 `tactic()` 的第一行：

```js
  const g = S.goals[0]; if (!g) throw new Error('已經沒有目標了');
```
（`lean-prover/src/lean.js:130`；`lambda-cube/src/cube.js:121` 逐字相同）

策略**只作用於棧頂**。這是一個硬性的限制，也是一個值得深究的設計。

**好處是：狀態簡單到不需要思考。** 一條策略永遠只需要處理「當前的目標」，不需要知道「我現在在整個證明的哪裡」。這讓策略可以獨立撰寫、獨立測試。ITP 的 13 條策略裡，每一條都可以用「給定一個目標 `g` 與一個參數，算出新的棧與新的填補表」這個signature來描述。

**好處二：錯誤訊息可以對準當前目標。** `is()` 這個輔助：

```js
  const is = (t, m) => { if (f.t !== t) throw new Error(`${name} 不適用:目標是 ${fm(f)}${m || ''}`); };
```
（`lean-prover/src/lean.js:136`）

它只提到**棧頂目標**的樣子。使用者看到「constructor 不適用:目標是 $P \to Q$ 」時，立刻知道問題出在哪裡，不需要在一堆目標裡猜。

**代價是：不能對非棧頂的目標操作。** 而這在實務上很常需要。

最典型的情境是 `cases` 產生兩個分支：

```js
      if (A.t === 'or') { const n1 = ng([...ctx, [a, A.l]], f), n2 = ng([...ctx, [b, A.r]], f); return solve({ r: 'orE', p: H, x: a, a: M(n1), y: b, b: M(n2) }, [n1, n2]); }
```
（`lean-prover/src/lean.js:161`）

`orE` 產生兩個新目標 `[n1, n2]`，棧頂是 `n1`。使用者照著直覺會想「我想先處理 `n2`」——但沒有辦法。因為 `tactic()` 永遠操作 `S.goals[0]`，而 `n2` 在 `n1` 的下面。

要處理 `n2`，唯一的辦法是**先把 `n1` 解掉**。這在很多情況下沒問題（分支通常是獨立的，先做哪個都行），但有時候分支 $n_1$ 需要的資訊要等分支 $n_2$ 才有——那使用者就卡住了。

**第二個代價：`apply` 一次只能開一串前提目標。** 這是設計上必然的：`apply` 只能看棧頂目標的型別，只能為棧頂目標開新目標。它不能同時為兩個不同的目標各開一串。

**第三個代價：`have` 的兩種形式受限。**

```js
      const F = parseF(m[3]), n1 = ng(ctx, F), n2 = ng([...ctx, [m[1], F]], f); return solve({ r: 'let', n: m[1], p: M(n1), q: M(n2) }, [n1, n2]);
```
（`lean-prover/src/lean.js:168`）

`have 名稱 : 命題` 產生兩個目標：`[n1, n2]`，其中 `n1` 是「先證明這個命題」，`n2` 是「用它完成原目標」。使用者必須先證 `n1`，才能用 `n2`。如果這兩個目標之間有循環依賴（要證 $A$ 才能證 $B$ ，要證 $B$ 才能證 $A$ ），就死鎖了。

## 7.3.6 跟真實系統的差距：`all_goals` 與 `focus`

真實的證明助手怎麼解決這些限制？

**Lean 的 `all_goals`**：把一條策略（或一段 tactic mode）套用到**棧上的每一個目標**，而不是只有棧頂。它的實作方式是把每個目標各自跑一遍策略。

**Coq 的 `focus`**：把棧頂的 $n$ 個目標合成一個「焦點」，讓後續指令只在這 $n$ 個目標裡跑，跑完之後焦點自動解開。這正好對應「我要同時處理 `cases` 產生的兩個分支」這個需求。

這兩者都是在本專案的模型上加了一層，而那一層是**策略層的**，不是核心的。核心完全不受影響——這正是 de Bruijn 準則帶來的好處：**功能可以往上長，信任邊界不必動。**

回到本專案：**這是最先該加的功能。** 具體來說，`lean-prover` 加上 `all_goals` 或 `focus` 的改動很小：

- `all_goals` 的版本：把 `tactic()` 從「操作 `S.goals[0]`」改成「對 `S.goals` 的每個元素各操作一次」，然後把結果合併。因為 `solve` 已經把「新目標」與「填補片段」分開記錄（`S.assign[g.id]`），合併兩個目標的結果在資料結構上是直接的。
- `focus` 的版本：需要一個「焦點區間」的概念，`solve` 在焦點內時要更新焦點而不是整個棧。

兩個改動都在 `tactic()` 與 `solve()` 這幾行裡，**核心一行都不用動**。這就是 7.1 節講的架構紅利。

## 7.3.7 ATP 沒有這一層

最後要說明一件在本書前六章裡一直隱約可見、但從未正面講過的事：**`theorem-prover` 沒有策略層。**

第 1.2 節已經指出這件事：「ATP 沒有策略層。`prover.js` 的 `prove()` 是一個自帶搜尋策略的引擎——挑選子句、歸結、因子化、等式替換全都寫在 `while (!empty)` 那個迴圈裡。」第 4.5 節把那個迴圈整個拆開講過了。

現在可以從本章的角度說清楚這意味著什麼。

**架構上的差異**：ATP 是「沒有策略」的全自動系統。使用者給的是一個待證命題，系統自己找矛盾。它沒有目標棧（`prover.js` 裡沒有 `S.goals` 這種結構），沒有洞（沒有 `meta` 節點），沒有 `solve` 這種「同時更新棧與填補表」的函式。

**進度的單位不同**：ATP 的進度單位是「已產生的子句數」（`gen`）與「推理鏈的長度」（`steps`），不是「還剩幾個目標」。這也是 `showGoals` 在 ATP 缺席的原因（1.2 節講過）。

**失敗的語義不同**：ATP 不會「停在半路」——它要嘛找到矛盾（`proved`），要嘛把子句空間用完（`saturated`），要嘛撞到上限（`timeout`）。沒有「還有目標沒解完」這種狀態，因為「還有目標」這個概念在 ATP 裡不存在。

**取捨是清楚的**：

| | ITP（有策略層） | ATP（無策略層） |
|---|---|---|
| 使用者參與 | 必須給思路 | 不需要 |
| 核心大小 | 小（30 行 / 43 行） | 大（56 行） |
| 核心的可靠性來源 | 規則本身 | Herbrand、Skolem 等元定理 |
| 失敗的類型 | `error` / `open` / `kernel` | `saturated` / `timeout` |
| 適用範圍 | 一階邏輯 + 直觀／古典命題邏輯 | 一階邏輯（可含等式） |

**兩者不是替代關係，而是分工**：第 6.7 節講群論與等式時，這個分工已經具體出現過——ATP 在等式理論上遠遠更強（它是自動的，會窮舉等式替換的可能性），而 ITP 在那裡幾乎無能為力（`lean-prover` 的核心連等號都不認得，`lean.js:7` 的詞彙層沒有 `=`）。反過來，ATP 在需要人類洞察的命題上會卡在 `saturated`，而 ITP 可以靠使用者的一個 `by_contra` 解決。

**本章要說的是：這種分工之所以可能，正是因為核心被隔開了。** ATP 把搜尋放進核心（因為它無法迴避），所以它的核心必須大、必須被元理論撐腰；ITP 把搜尋放在策略層（因為它可以放），所以它的核心可以小到三十行。**同一個問題——「誰來找證明」——的答案，直接決定了核心的大小。**

## 小結與交棒

兩個 ITP 的策略層幾乎同構：一個目標棧 `S.goals`、一個洞的填補表 `S.assign`、一個同時更新兩者的 `solve()`。策略產生的是**含洞的證明項片段**，洞由 `inst()` / `fill()` 在最後一次填滿，遍歷順序無關——這是「洞」相對於「巢狀填空」的關鍵優點。

策略清單的差異有清楚的成因：**兩邊都有的六條是通用骨架，只有 ITP 有的七條全是邏輯連接詞的專用策略**，而 λ-Cube 之所以不需要它們，是因為它把 $\wedge$ 、 $\vee$ 、 $\exists$ 全都用 Π 型別編碼掉了（5.6 節）。同理，`exfalso` 與 `by_contra` 是 ITP 專有，因為 λ-Cube 的核心是直觀主義的。

棧頂限制是這個模型最明顯的取捨：它讓狀態簡單、錯誤訊息精準，代價是不能對非棧頂目標操作。真實系統用 `all_goals` 與 `focus` 補上這個缺口，而**補的是策略層，核心一行都不用動**——這是本章最值得記住的一點。

而 ATP 沒有這一層，是同一個問題的相反答案：把搜尋放進核心，核心就必須大到 56 行，並且必須靠 Herbrand 與 Skolem 的元理論撐腰。
