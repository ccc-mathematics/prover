# 7.5 測試策略：核心必須拒絕偽造證明

前三節建立了架構：核心小、策略層隔離、介面零相依。但架構本身不能證明架構是對的——那要靠測試。

而這裡有一個特別的點：**可信核心的測試跟一般軟體的測試方向是相反的。** 一般軟體的測試問「對的輸入會產生對的輸出嗎」；核心的測試還必須問「**壞的輸入會被拒絕嗎**」。一個從來沒有被餵過壞資料的核心，等於沒有被檢驗過。

## 7.5.1 三個測試檔案的實際內容

三個測試檔案都很短，讓我們逐行讀。

### `lean-prover/test/test.js`：9 行，12 個斷言

```js
const L = require('../src/lean.js'); let fail = 0;
const ok = (c, m) => { console.log((c ? 'PASS  ' : 'FAIL  ') + m); if (!c) fail++; };
for (const e of L.examples) ok(L.runThm(e.src).status === 'done', e.name);
ok(L.runThm('theorem t : P -> Q := by\n  intro h\n  exact h').status === 'error', '錯誤的策略會被拒絕');
ok(L.runThm('theorem t : P -> P := by\n  intro h').status === 'open', '未完成的證明回報 open');
ok(L.runThm('theorem t : P := by\n  sorry').status === 'sorry', 'sorry 會被標記');
try { L.check({ r: 'andE1', p: { r: 'hyp', n: 'h' } }, [['h', { t: 'atom', n: 'P', a: [] }]]); ok(false, '核心應拒絕偽造的證明項'); }
catch (e) { ok(true, '核心拒絕偽造的證明項'); }
process.exit(fail ? 1 : 0);
```
（`lean-prover/test/test.js:1-9`）

這 9 行裡有 **12 個斷言**：8 個內建範例（`:3`）加 4 個專門的斷言（`:4`–`:7-8`）。跑起來會印出 12 行 `PASS`，最後一行是 `PASS  核心拒絕偽造的證明項`。

注意最後一行。**那兩行（`:7-8`）是整個專案最重要的一個斷言**——第 1.2 節說它「直接把手伸進核心，餵給它一個手寫的、結構上不成立的證明項，要求核心丟出例外」。

### `lambda-cube/test/test.js`：12 行，14 個斷言

```js
const C = require('../src/cube.js'); let fail = 0;
const ok = (c, m) => { console.log((c ? 'PASS  ' : 'FAIL  ') + m); if (!c) fail++; };
for (const e of C.examples) ok(C.runScript(e.src).ok === !e.name.includes('錯誤'), e.name);
const t = s => C.runScript(s);
ok(!t('system λP\ndef id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x').ok, 'λP 沒有多型,拒絕 ∀(A:Prop)');
ok(!t('system λ2\ndef And (A B : Prop) : Prop := forall (C : Prop), (A -> B -> C) -> C').ok, 'λ2 沒有型別運算子,拒絕 Prop→Prop→Prop');
ok(!t('system λ2\ndef id : forall (A : Prop), A -> A := fun (A : Prop) (x : A) => x\ncheck id id').ok, '型別不吻合的應用被拒絕');
ok(!t('axiom P : Prop\ntheorem t : P := by\n  intro h').ok, '目標不是 Π 時 intro 失敗');
ok(t('axiom P : Prop\ntheorem t : P := by\n  sorry').cmds[1].status === 'sorry', 'sorry 會被標記');
ok(t('axiom P : Prop\ntheorem t : P -> P := by\n  intro h').cmds[1].status === 'open', '未完成的證明回報 open');
ok(!t('check Type').ok, 'Type 沒有型別');
process.exit(fail ? 1 : 0);
```
（`lambda-cube/test/test.js:1-12`）

λ-Cube 的測試多了一層：**它測的是「系統頂點選對沒有」**。看 `:5` 那條：`system λP` 然後定義一個多型的 `id`，期望被拒絕——因為 λP 的規則集只有 `{'Prop>Prop', 'Prop>Type'}`，而 `forall (A : Prop), ...` 需要 `Type>Prop`。**這條測試實際上在測核心的 `case 'p'` 分支**（`cube.js:101-105`）。`:6` 那條測的是另一個方向，但它被什麼理由擋下的，測試訊息沒有說清楚——這個含糊之處，正好是本節下一段的教材。

**這裡需要停一下，因為這一條測試的訊息與它實際測到的東西之間有落差，而這個落差本身就是教材。**

測試訊息寫的是「λ2 沒有型別運算子,拒絕 Prop→Prop→Prop」。但實際執行後得到的錯誤訊息是：

```
目前的系統不允許這個 Π 型別:定義域屬於 Type,值域屬於 Type(缺少規則 Type>Type):Prop → Prop
```

讓我們把這個落差追到底，因為它比表面看起來更有意思。

### 追查：被拒絕的其實是「宣告型別」，不是「值」

`def` 的處理順序在 `cube.js:212`：

```js
          K.sort([], pis); if (!K.conv(K.infer([], val), pis)) throw new Error('定義的內容與宣告的型別不吻合');
```
（`lambda-cube/src/cube.js:212`）

**第一個動作是 `K.sort([], pis)`**——先檢查宣告型別 `pis` 本身合不合法。而 `pis` 是用 `wrap(Pi, bs, ty)` 組出來的（`cube.js:209`），`bs` 就是宣告的綁定清單。所以 `def And (A B : Prop) : Prop` 的宣告型別是 $\Pi (A : \mathit{Prop}) . \Pi (B : \mathit{Prop}) . \mathit{Prop}$ ——`A` 與 `B` **綁定在 `Prop` 這個 sort 上**。而 `Prop` 的 sort 是 `Type`（`cube.js:97`），所以這個 Π 型別的定義域與值域的 sort **都是 `Type`**，`case 'p'` 的規則檢查（`cube.js:103`）因此要求規則 `Type>Type`——**而 λ2 沒有這一條**（`cube.js:6`）。**所以被拒絕的不是那個值，而是 `def` 的宣告型別本身。**

我用幾個對照組確認了這件事：

| 指令 | 系統 | 結果 | 原因 |
|---|---|---|---|
| `def And (A B : Prop) : Prop := ...` | λ2 | 拒絕 | 宣告型別 `Prop→Prop→Prop` 需 `Type>Type` |
| `def id : forall (A : Prop), A -> A := ...` | λ2 | **通過** | `A` 綁定在命題上，內層 Π 只需 `Prop>Prop` |
| `def And (A B : Prop) : Prop := ...` | λω | **通過** | λω 有 `Type>Type` |

**這張表揭露了兩件事。** 第一，**測試訊息的措辭不準確，但測試的行為是對的**——它確實擋下了一個在 λ2 裡不該被接受的定義，只是被擋下的對象是**宣告型別**而不是訊息裡寫的那個值。

第二，**這是本章論點的極好實例**。這條負向測試寫的時候，作者（也就是我）**只知道它擋下了某個東西，不知道它擋下的是什麼**。**這就是負向測試的兩面**：它保證了「壞的東西被擋下」，但不保證「以正確的理由被擋下」。要後者，就得把斷言寫得更精確：

```js
const r = C.runScript('system λ2\ndef And (A B : Prop) : Prop := forall (C : Prop), (A -> B -> C) -> C');
ok(r.cmds[1].msg.includes('缺少規則 Type>Type'), 'λ2 缺 Type>Type,應擋下綁定在 Prop 上的宣告');
```

**這個斷言比原來的強**：它不只說「被擋了」，還說「以正確的理由被擋」。若有人改了 `case 'p'` 的規則檢查順序，它會失敗。

## 7.5.2 負向測試：核心測試的核心

回到本節的主題。前面提過 `lean-prover/test/test.js:7-8` 那兩行，讓我們拆開看它測的是什麼。

```js
try { L.check({ r: 'andE1', p: { r: 'hyp', n: 'h' } }, [['h', { t: 'atom', n: 'P', a: [] }]]); ok(false, '核心應拒絕偽造的證明項'); }
catch (e) { ok(true, '核心拒絕偽造的證明項'); }
```

**這個證明項是手寫的。** 它繞過了整個策略層，直接構造一棵形狀不對的樹：`{ r: 'andE1', ... }` 宣稱用「∧ 消去」規則，`p: { r: 'hyp', n: 'h' }` 說明它的前提是引用假設 `h`，上下文則說明 `h` 的型別是原子命題 $P$ 。

**這棵樹不可能由策略層產生**：策略層的 `andE1` 只會出現在 `cases` 處理合取式假設的時候（`lean.js:160`），那時候被消去的東西一定是一個 `and`。所以這是一個「理論上不可能出現」的證明項——而這正是負向測試的關鍵：**它測的不是「策略能不能產生正確的證明項」，而是「核心能不能拒絕不正確的證明項」**。

`:6` 那條也值得看：`sorry` 的核心處理是 `case 'sorry': fl.sorry = true; return p.f;`（`lean.js:86`）。**`sorry` 通過了核心的檢查**——核心不拒絕它，但設了 `fl.sorry` 旗標，`runThm` 再把它翻譯成 `sorry` 狀態（`lean.js:211`）。所以 `:6` 測的是「**作弊通道是有名有姓的**」：它不能假裝成成功，但也不能假裝成失敗。

λ-Cube 的對應測試在 `:9`，而它的核心處理是 `case 'z': fl.sorry = true; return t.ty;`（`cube.js:99`）。**結構完全一樣。** 這說明第 7.2 節的結論在這裡又得到一次確認：兩個 ITP 的核心是同一個設計的兩次實作。

### ATP 的負向測試

ATP 的測試檔案（`theorem-prover/test/test.js`，9 行）用的是**完全不同的策略**：

```js
const P = require('../src/prover.js');
let fail = 0;
for (const e of P.examples) {
  const want = e.name.includes('非定理') ? 'saturated' : 'proved';
  const got = P.prove(e.premises, e.goal || null).status;
  console.log(`${got === want ? 'PASS' : 'FAIL'}  ${e.name}  (${got})`);
  if (got !== want) fail++;
}
process.exit(fail ? 1 : 0);
```
（`theorem-prover/test/test.js:1-9`）

它**沒有手寫偽造的證明項**——因為 ATP 沒有「給定一個證明項讓我檢查」這個介面（7.2.5 節講過）。它的負向測試是**語意上的**：第九個內建範例是「非定理(應回報失敗)」（`prover.js:220`），期望狀態是 `saturated` 而不是 `proved`。

這是三個測試檔案裡**唯一一個測試失敗案例**的測試。它的價值在於：**它測的是「系統不會亂講」**——ATP 最大的風險不是證不出來，而是**亂講**，把一個不成立的命題說成成立的。

**這三種負向測試剛好對應三種架構**：

| 架構 | 負向測試的形式 | 測的是 |
|---|---|---|
| ITP | 手寫偽造證明項餵給 `check()` | 核心的形狀檢查 |
| ITP | 錯誤的策略 / `sorry` / 未完成 | 策略層的行為與旗標 |
| ATP | 一個不是定理的命題 | 語意上的誠實 |

## 7.5.3 「測核心」與「測策略」的不同

這是本節要明確區分的一件事，它決定了測試該怎麼寫。

**測核心**：給核心一個輸入，檢查它回傳的答案，測的是**核心的判斷是否正確**；它應該是**獨立的**——不經過策略層、不經過 `runThm`。

**測策略**：給策略層一個指令序列，檢查它產生的目標棧與證明項，測的是**策略的行為是否符合預期**；它通常**不直接檢查證明項**——證明項的正確性已經由核心負責了。

分工可以從 `lean-prover/test/test.js` 的結構看出來：前 8 個斷言（`:3`）測的是**端到端**——策略跑完 → 核心檢查 → 狀態是 `done`，這是「整合測試」；後 4 個則針對特定層：`:4`、`:5` 測策略層，`:6` 測核心的旗標機制，`:7-8` **只測核心**。

**為什麼負向測試必須直接打核心，不能只靠整合測試？** 因為整合測試有一個盲區：**策略層不會產生形狀不對的證明項**。如果策略層是對的，整合測試永遠不會遇到核心需要拒絕的輸入，核心的拒絕邏輯（`need()`、`eq()`、三個側條件）會**完全沒有被執行過**。

這是本章最重要的論點：**如果一個可信核心從來沒有被餵過壞資料，它就還沒有被檢驗過。** 那些「核心檢查失敗」的分支會是死碼碼——它們看起來有防護，但從未被執行，因此可能從未被驗證。換句話說：**正向測試只能證明「該通的地方通了」，負向測試才能證明「不該通的地方擋住了」**。

## 7.5.4 建議的測試金字塔

基於以上觀察，一個更完整的測試策略應該有四層。這個金字塔本專案**還沒有實作**（除了最底層），但它是 8.5 節的練習素材。

| 層 | 目標 | 現況 |
|---|---|---|
| **核心規則逐條測試** | 每條核心規則都有一個「合法實例」與一個「非法實例」，理想上 36 個 | 只有 `andE1` 有負向案例 |
| **解析／顯示往返測試** | `parse` → `fm`（或 `show`）→ `parse` 回到等價的東西 | 缺 |
| **範例整合測試** | 一組涵蓋各種規則組合的完整證明 | 有，但缺「負向的整合案例」 |
| **跨系統一致性測試** | 三個系統對同一個命題給出**相容的結論** | 缺 |

**第一層**最重要，因為核心規則正是最容易寫錯而最不容易被正面案例發現的地方：

```js
// 合法：impE 對上正確的前提
ok(checkImpE({ f: { r: 'hyp', n: 'h1' }, a: { r: 'hyp', n: 'hp' } }) === Q, 'impE 合法');
// 非法：impE 對上錯誤的前提
ok(throws(() => checkImpE({ f: { r: 'hyp', n: 'h2' }, a: { r: 'hyp', n: 'hp' } })), 'impE 前提不吻合被擋下');
```

**第二層**測的是**前後端的接縫**，不是核心。它能抓到「解析器跟顯示器不一致」的 bug——例如 `fm` 把 $\neg A$ 印成 $A \to \bot$ ，但解析器不認得 `False` 這個寫法。

**第三層**就是現在 `test/test.js` 的主要內容（`:3` 的八個內建範例），涵蓋了 $\wedge$ 交換、假言三段論、 $\vee$ 交換、雙重否定消去、Peirce、一階量詞實例化、 $\forall$ 對 $\wedge$ 分配、 $\exists$ 與 $\forall$ 的對偶。它的缺口是「負向的整合案例」——像 ATP 那個「非定理(應回報失敗)」一樣的案例。

**第四層**是本專案獨有的可能性——三個系統都存在，用的是同一套語法。可以檢查：**都該證明的都證明了**、**都該拒絕的都拒絕了**（一個明顯不是定理的命題，ATP 會說 `saturated`，ITP 會說 `open` 或 `error`）、**術語一致**。它是第 6 章那個「三系統交會」的工程化版本。

## 7.5.5 誠實地指出目前的不足

如果這一章要對讀者有用，它必須說清楚現在的測試**不夠**在哪裡。

### 不足一：沒有模糊測試（fuzzing）

三個專案的解析器都是手寫的遞迴下降解析器（`lean.js:10-36`、`cube.js:37-72`、`prover.js:7-42`），而遞迴下降解析器是模糊測試最有效的目標之一——隨機產生字串餵進去，確認「要嘛成功、要嘛丟出帶上下文的錯誤訊息」。

但現在的狀況是：**解析器只被少數幾個手寫的輸入測過**。一個缺右括號的輸入、一個用了保留字的輸入、一個 Unicode 全形符號的輸入——都沒有被覆蓋。

### 不足二：沒有對 `lex()` 跳脫處理的回歸測試

這是最具體的一個缺口，而且第 3.2 節已經把它記錄下來了。

`lean-prover/src/lean.js:7` 的 `lex()` 有兩段跳脫處理：

```js
const lex = s => s.replace(/[∀∃¬∧∨→↔⊥]/g, c => GREEK[c]).replace(/\/\\/g, '&').replace(/\\\//g, '|').match(/<->|->|[A-Za-z_][\w']*|\S/g) || [];
```

（`lean-prover/src/lean.js:7`）

第 3.2 節把這兩條規則記成了一個「已知 bug」。**它的行為描述大致正確，但成因寫錯了，而成因正是最容易寫錯的部分**：第一條規則的樣式 `/\/\\/g` 匹配的是**斜線後面接反斜線**這兩字元的序列，不是「一個反斜線」；而替換字串裡的 `&` 在 JavaScript 裡**不是**特殊字元（只有 `$&` 才是），所以那條規則確實在做替換、不是空操作。兩個常見的誤讀會導致完全相反的結論。

實測這份檔案裡真實的 `lex()`（用 `eval` 從原始碼字串直接組出函式，不做任何轉錄）：

| 輸入 | 記號串 | 結果 |
|---|---|---|
| `P & Q` | `["P","&","Q"]` | 正常 |
| `A /\ B` | `["A","&","B"]` | 被解讀成 `A ∧ B` |
| `A \/ B` | `["A","|","B"]` | 正常 |
| `P \& Q` | `["P","\\","&","Q"]` | 解析失敗（錯誤訊息是「語法錯誤:多餘的符號(附近:P \)」） |

前兩列的跳脫寫法其實是刻意設計的（Mathematica 風格的 `/\` 與 `\/`），但它們**從未寫進 README**，所以使用者誤打 `/\` 時，公式會被安靜地解讀成合取——**一個會安靜改寫公式的輸入管道，比一個會報錯的管道危險得多**：後者會擋住使用者，前者會讓一個意思不同的命題悄悄進入證明。第四列才是真正的缺陷：`\&` 根本不是受支援的寫法，卻留下一個孤零零的反斜線記號，錯誤訊息也完全指不到真正的原因。

**這個行為至今沒有被修，也沒有被任何測試釘住。** 正因為它無害（跳脫寫法只是個備用輸入管道），它就更容易永遠留著：**沒有測試失敗，就沒有人會去修它；沒有回歸測試，也沒有人會發現連「它是怎麼壞的」都可能被記錯**。

而這正是本章的原則的最好例子：**一個 bug 沒有被測試釘住，就等於沒有被記錄。** 一條回歸測試只要兩行：

```js
// 已知行為:lex 的跳脫處理把 "\/" 讀成 "|",但 "\&" 不被支援,產生 4 個記號(正常應為 3)。見 book/03.2 節。
// 若此斷言失敗,代表 lex 被修正(或進一步損壞)——兩者都需要更新 03.2 節的記錄。
ok(lex('P \\& Q').length === 4, 'lex 的跳脫記號處理有已知行為,記錄在 03.2 節');
```

把行為釘在測試裡有兩個好處：**它警告未來的人不要隨手「修正」這個行為**（修正會讓這條測試失敗，迫使修正者更新文件），以及**它讓文件的記錄變成可執行的**。而第二個好處特別重要：一條只斷言「壞掉了」的測試，仍不能保證壞掉的原因被記對了。真正有價值的回歸測試要斷言**具體的行為**——例如「`\/` 產生 3 個記號」、「`\&` 產生 4 個記號而不是 3 個」、「`/\` 被讀成 `&`」——這樣任何對成因的誤解都會在測試裡露出來。

### 不足三：核心規則的負向覆蓋率偏低

18 條規則裡只有 `andE1` 有負向測試，這意味著**核心裡 17 條規則的拒絕路徑從未被執行過**。

特別值得擔心的是那三個側條件——它們是核心裡最容易寫錯、而且錯了不會被正面案例發現的規則：`orE` 的兩分支結論必須相同（`lean.js:94` 的 `eq(a, b) ? a : bad(...)`）、`allI` 的變數不得出現在假設中（`lean.js:99`）、`exE` 的見證變數必須新鮮（`lean.js:104`）。這三條如果寫錯了（例如把 `eq(a, b)` 寫成 `eq(a.l, b.l)`），**所有正面測試都會通過**——只有「故意違反側條件」的負向案例才抓得到。

### 不足四：ATP 缺少「核心層級」的負向測試

ATP 沒有 ITP 那種「餵偽造證明項」的測試，因為它沒有那個介面。但這不代表它不需要——ATP 的核心有幾個可以測的東西，目前都沒測：**`unify()` 的 occurs check**（`prover.js:81`）——`X = f(X)` 應該失敗，這個邏輯錯誤會造成無限展開；**剪枝的健全性**（`prover.js:146-154`）——被剪掉的子句不該是證明鏈上的必要環節；**`norm()` 的恆真子句偵測**（`prover.js:114-120`）——`P ∨ ¬P` 應該被丟掉。

### 不足五：沒有效能的迴歸測試

`lambda-cube` 的 README 說「大型項會很慢」，但沒有任何測試標記這個行為。如果未來有人改動 `conv()` 使得大型項變得更慢，沒有東西會發現。一個「這個項的推導應該在 N 毫秒內完成」的斷言，就足以防止最惡劣的退化。

### 不足六：ATP 的退出碼不一致（回扣 7.4.1 節）

這是工程層面的不足，但兩者相關：**因為 ATP 的 CLI 永遠回傳 0，`npm test` 之外沒有任何自動化工具能判斷 ATP 的測試是否通過**——在 CI 裡，ATP 的測試失敗不會讓建置失敗。（補充：ATP 的 `test/test.js` **有** `process.exit(fail ? 1 : 0)`（`:9`），所以 `npm test` 本身是對的。問題出在 CLI 那條路徑上。）

## 7.5.6 本節的建議清單

綜合以上，如果要為本專案補上測試，我會照這個順序做：

1. **先補 `lex()` 的回歸測試**（兩行），把 3.2 節記錄的行為釘住。
2. **再補三個側條件的負向案例**（`orE`、`allI`、`exE` 各一個）——這是核心裡最容易出錯而最不容易被發現的部分。
3. **然後補 ATP 的 `unify()` occurs check 案例**——ATP 核心裡唯一一個「寫錯會導致非終止」的規則。
4. **再考慮模糊測試**——從 `lex()` 開始（所有輸入的入口），產生隨機字串餵進 `parseF`，確認不會 hang。
5. **最後做跨系統一致性測試**——把第 6 章的人工比較變成自動斷言。

前三項都是「小而關鍵」的：每一項都只需要幾行，卻各自封住一個真實的漏洞。第 4、5 項則是規模較大的工程。

## 小結與交棒

可信核心的測試與一般軟體的測試**方向相反**。除了「對的輸入產生對的輸出」之外，還必須問「壞的輸入會被拒絕嗎」——否則核心裡那些「核心檢查失敗」的分支就是從未被執行過的死碼碼。

本專案在這方面做了一件很對的事：`lean-prover/test/test.js:7-8` 直接把手伸進核心，餵一個**策略層不可能產生的**偽造證明項，要求核心丟出例外。λ-Cube 走的是另一條路：測「系統頂點選對沒有」。ATP 走的是第三條路：測「一個明顯不是定理的命題，系統不會亂講」。三種負向測試剛好對應三種架構。

本章也誠實地列出了六個不足：沒有模糊測試、**沒有對 `lex()` 跳脫處理的回歸測試**、核心規則的負向覆蓋率偏低（18 條規則只有 1 條有負向案例）、ATP 缺少核心層級的負向測試、沒有效能迴歸測試、ATP 的退出碼不一致。其中「`lex()` 沒有回歸測試」最值得記住，它同時展示了本章論點的兩面。

**第一面：一個 bug 沒有被測試釘住，就等於沒有被記錄。** 3.2 節用人工記下了那個跳脫記號的缺陷，而只要兩行程式碼，那個記錄就會變成可執行的，並阻止任何人「順手修掉」它。

**第二面：人工的記錄本身也會出錯。** 前面把 `lex()` 的跳脫處理追到底之後，發現 3.2 節記的**行為大致正確，但對成因的描述不準確**：它把第一條規則的樣式讀成「一個反斜線」、又把替換字串裡的 `&` 當成特殊字元，兩處都會導向錯誤的結論。這個落差不是誰不仔細，而是**只有真的去跑、去讀位元，才會浮現**。一份寫在文件裡的「已知問題」，可靠性永遠低於一條會失敗的斷言。

本章是第 7 章的最後一節。我們從 de Bruijn 準則開始，談了核心的形狀、策略層的結構、介面的打包，最後談到怎麼證明這套架構真的有效。下一章是第 8 章「局限與延伸：從三個玩具走向真實的證明器」——那裡會把這三個玩具缺的東西攤開來：歸納型別、宇宙階層、η 規則、古典邏輯的完整代價、自動化、SMT，每一項都會標出「最小改動要動到哪裡」。

值得注意的是，第 8.1 節已經回扣過本章的核心命題：**核心小，不代表核心不用長大**。本專案的核心之所以是三十行，是因為它把規則的數目壓到了極致，而不是因為它省略了什麼。真實的證明器會長大——但它長大的方式是**每一行都對應一條被明確命名過的規則**。
