# 8.1 缺了什麼：歸納型別、宇宙階層與 η 規則

第 7 章把三個玩具的**工程骨架**攤開了：可信核心要小、策略層要厚、介面要零依賴。但工程骨架回答的是「怎麼把它做對」，不是「它能做多少事」。三個系統在本書寫到這裡為止所展示的能力，全部落在「一階命題邏輯的少量定理」這個範圍內；它們離「證明群論、證明排序演算法的正確性、證明一個定理產生器的健全性」還有好幾個數量級的距離。

本章要做的事情是**精確地列出這些距離**，而且每列一條都要在原始碼裡找到證據。本節先處理三個系統中「表達力」層面的缺口：歸納型別、宇宙階層、η 規則。這三樣東西有共同的性格——它們都不是「多幾條推理規則」那麼簡單的事，而各自需要一整套機制：**歸納型別需要一個正性檢查與一個 recursor 產生器；宇宙階層需要一個 sort 檢查器；η 規則需要一個定義等價的正規化程序**。把它們拆開來看，才知道「從玩具到真實」要補的不是零件，而是三台機器。

## 8.1.1 一張缺口總表

先把三個系統的缺口攤成表格，作為本節的骨架。左欄是系統，中欄是缺什麼，右欄是「在原始碼裡的證據」。

| 系統 | 缺口 | 原始碼證據 |
|---|---|---|
| `lean-prover` | 沒有等號 | 詞法規則不含 `=`（`lean.js:7`），`a = b` 直接解析失敗 |
| | 沒有歸納 | 命題形狀只有 `imp / and / or / all / ex / bot / atom`（`lean.js:84-107`） |
| | 沒有型別 | 核心檢查的是「證明項的命題」，命題本身沒有型別 |
| | 沒有自動化 | 策略必須逐條手寫（`lean.js:138-172`） |
| `lambda-cube` | 沒有歸納型別 | `Nat` 只能 `axiom`（`cube.js:245` 的範例） |
| | 沒有宇宙階層 | `Type 沒有型別(λ-cube 的最頂層)`（`cube.js:97`） |
| | 沒有 η 規則 | `conv` 只做結構相等（`cube.js:82-90`） |
| | 沒有隱含參數 | `apply` 遇到依賴參數主動擋下（`cube.js:145`） |
| | `def` 不能遞迴 | `G[name]` 在解析完主體之後才寫入（`cube.js:213`） |
| | `theorem` 不透明 | 定理與公理同形，沒有 `val`（`cube.js:190`） |
| `theorem-prover` | 等式沒有項排序 | 替換方向兩個都試（`prover.js:131`） |
| | 等式沒有化簡 | 產生新子句後只做去重與恆真剔除（`prover.js:114-120`） |
| | 等式用完即丟 | 參數替換把等式從結果子句中刪除（`prover.js:136`） |
| | 資源上限 | 10 秒 / 20000 子句（`prover.js:144`） |

這張表的價值在於**右欄全部是可點名的行號**。本節接下來要做的，是把每一列從「限制描述」升級成「因果解釋」：為什麼這個系統會缺這個東西，缺了之後具體會發生什麼事，以及加回去的最小改動是什麼。

## 8.1.2 lean-prover：核心只認七種命題形狀

`lean-prover` 的核心規則表在 `lean.js:84-107`，整張表可以用一句話概括：**每個 `case` 都把一個證明項的型別算出來**。而能被算出型別的命題，必須是解析器認得的形狀。解析器在 `lean.js:21-34` 的 `un()` 裡一共生產七種命題節點：

- `atom`：像 `P(x)` 的原子命題，其中 `x` 是**項**（`lean.js:16` 的 `term()` 只會把 `f(a, b)` 組裝成 `{f, a}`）；
- `imp`：蘊含（`~A` 被展開成 `A → ⊥`，見 `lean.js:23`）；
- `and`、`or`：合取與析取；
- `all`、`ex`：量詞；
- `bot`：`False`。

這份清單裡沒有等式。所以「`lean-prover` 沒有等號」不是一句籠統的批評，而是一個可以實測的事實：

```
$ node -e "require('./src/lean.js').parseF('a = b')"
語法錯誤:多餘的符號(附近:a =)
```

`=` 連詞法層都沒進去（`lean.js:7` 的正規表示式只認 `<->`、`->`、識別字與單一字元），所以 `a = b` 裡的 `=` 被切成一個獨立 token，`parseF` 隨即因為「多餘的符號」而失敗。這帶來三個連鎖的後果：

1. **沒有 Leibniz 定律**。第 4.7 節說過，沒有等式就沒有可替換性，整個代數推理就無法表達。第 6.7 節的群論命題 `inv(e) = e`，在 `lean-prover` 裡連**命題**都寫不出來。
2. **沒有自由定理的來源**。像「任何函數 $f$ 都滿足 $f \circ g = g \circ f$ 對某個 $g$ 成立」這類結論，若用等式表達就只是套用 Leibniz 定律；用 `atom` 表達就只能靠 `apply` 一層層套。
3. **歸納原理寫不出來**。歸納原理的本質是「對所有 $n$ 成立」，而它的自然寫法是對一個函式做等式比較。沒有等式，連「 $f$ 與 $g$ 對所有輸入都相等」都無法陳述。

第二個缺口是**歸納**。`lean-prover` 的核心裡沒有任何一條規則能把「對 $0$ 成立」與「若對 $n$ 成立則對 $\mathrm{succ}\ n$ 成立」組成「對所有自然數成立」。這個缺口不像等號那樣可以靠加一個 AST 節點補上——它需要一個**把資料型別當成一等公民**的機制。

第三個缺口是**型別**。這裡要說清楚，因為容易誤讀：`lean-prover` 裡「命題」是它的型別語言，但**命題本身沒有型別**。`check()` 迴傳的是一個命題節點，不是「某個型別的項」；`P` 與 `Q` 在核心眼裡只是兩個形狀不同的樹。這意味著核心**無法回答「這條命題是定理還是公理」**——它只回答「這棵證明項的形狀對不對」。要把命題當成一類有結構的對象來推理（例如「證明所有命題的析取」），核心需要的是一個更高層的型別系統。

第四個缺口是**自動化**。`lean.js:138-172` 的策略表裡每一條策略都要求使用者給出「哪一個假設、哪一個方向、哪一個建構子」。真實的 Lean 證明裡這類樣板佔了大半，8.3 節會專門處理。

## 8.1.3 lambda-cube：頂點之上還缺四樣

5.5 節結尾已經列過 λC 的七條缺口，這裡把其中最要命的四條拿來做因果分析。

**歸納型別**。5.4 節的 `Nat` 是這樣來的：

```
axiom Nat : Prop
axiom zero : Nat
axiom succ : Nat -> Nat
```

（`cube.js:245` 的內建範例就是這三行。）它是一個**假設**，不是一個定義。這意味著我們可以寫 `Nat`、可以寫 `zero` 與 `succ`，但**寫不出歸納原理**。歸納原理的形式是：

$$
\frac{P(0) \qquad \forall n . \left(P(n) \to P(\mathrm{succ}\ n)\right)}{\forall n . P(n)}
$$

在 `lean-prover` 裡這條規則沒有對應的核心 case，所以 `intro` / `apply` / `exact` 無論怎麼組合都湊不出來；在 `lambda-cube` 裡更徹底，連 `P(n) \to P(\mathrm{succ}\ n)` 這種「把 $P$ 套在項上」的說法都沒有可用的表示（`lambda-cube` 的命題就是型別，套用要用 `Ap` 節點與 `conv` 判定）。

**宇宙階層**。`cube.js:97` 這一行是全書最短、也最意味深長的錯誤訊息：

```js
      case 's': if (t.s === 'Prop') return Sx('Type'); throw E('Type 沒有型別(λ-cube 的最頂層)');
```

`Prop` 有型別（`Type`），`Type` 沒有型別。這是一個**刻意的閉包**：λ-cube 的頂點是「把三條軸打開」，而不是「把宇宙也打開」。5.5 節已經指出它的後果——`λω_` 與 `λω` 的招牌規則 `Type>Type` 在這個實作裡只能拿 `Prop` 去用，不能拿 `Type` 去用，真正的 kinds（ $\mathit{Type} : \mathit{Type}$ ）缺席。

**η 規則**。`conv` 的實作在 `cube.js:82-90`：

```js
  const conv = (a, b) => {
    a = whnf(a); b = whnf(b); if (a.k !== b.k) return false;
    switch (a.k) {
      case 'v': return a.i === b.i; case 's': return a.s === b.s; case 'c': return a.n === b.n;
      case 'a': return conv(a.f, b.f) && conv(a.a, b.a);
      case 'l': case 'p': return conv(a.ty, b.ty) && conv(a.b, b.b);
    }
    return false;
  };
```

它是**結構相等**加上 `whnf` 做的 β/δ 展開（`cube.js:77-81`）。η 規則說的是 `fun x => f x` 與 `f` 應該判定為等價（在 $x$ 不出現於 $f$ 的自由變數中時）；這條規則在 `conv` 裡完全不存在。5.5 節說得很謹慎：目前這個缺口「還看不見」，因為 `conv` 的五個呼叫點（`cube.js:111`、`136`、`139`、`204`、`212`）**全部作用於型別**，沒有一個作用於項。本節要補上的一句話是：**這個缺口不是不存在，而是延遲爆發**。

它會在什麼時候爆發？兩種情形。第一種是把等式做成一個可以 `exact` 的命題（把 $\equiv$ 做成 `Prop` 裡的關係），那麼 `refl` 的檢查就會落到**項**的等價判定上，而 `conv` 立刻不夠用。第二種是加入依賴型別的「definitional unfolding」：`def f := fun x => g x` 之後，`f` 與 `fun x => g x` 必須互相轉換，否則依值型別的推導會產生大量假的「型別不吻合」。

**隱含參數**。`cube.js:145` 這一行是 λ-cube 與真實系統差距的縮影：

```js
          if (uses(cur.b)) throw new Error('apply 遇到依賴型參數(∀),請把參數寫進去,例如 apply h C');
```

使用者必須把隱含參數手寫出來，否則 `apply` 直接失敗。真實的 Lean 靠 unification 推斷隱含參數（elaborator 的工作），Coq 靠 unification 與 universe 推斷。

## 8.1.4 theorem-prover：等式的三個缺失

`theorem-prover` 的等式推理是三個系統中**最完整**的：它有 `para`（參數替換，`prover.js:128-140`）與 `eqres`（等式歸結，`prover.js:171-175`）兩條規則，能把第 6.7 節的群論命題在 207 毫秒內用 1537 個子句證完。

但第 4.7 節末尾已經點出三個缺失，這裡把它們的**機制**講清楚，因為它們正是 8.4 節的 SMT 與 8.5 節第三個練習的靶心。

**沒有項排序**。`prover.js:131` 這一行同時嘗試兩個方向：

```js
    for (const [l, r] of [[e.a[0], e.a[1]], [e.a[1], e.a[0]]]) {
```

等式是對稱的，所以兩個方向都合法；但**現代 ATP 不會兩個方向都試**——它給所有項一個全序（Knuth–Bendix 順序之類），只允許從大到小替換。這保證每一次替換都是「簡化」而不是「膨脹」，推理因此可以在有限時間內收斂。兩個方向都試的直接代價，第 4.7 節已經指出：`e` 與 `mul(inv(a),a)` 可以互相替換，於是產生了大量等價的變體——群論範例的第 7 步與第 1274 步其實是同一個想法的兩面。

**沒有化簡**。新子句產生後，`prover.js:114-120` 的 `norm()` 只做三件事：去重複文字、剔除恆真子句（`t = t`）、變數改名。**它不做代數化簡**。所以 `mul(mul(inv(X1856),e),X1856)` 這種明顯可以化簡的項會一直留在子句集裡，被反覆拿來配對。

**等式用完即丟**。`prover.js:136` 組出結果子句時，把被用掉的等式從 `A` 裡濾掉了：

```js
        out.push([[...A.filter(x => x !== e), ...B.map(x => x === L ? L2 : x)].map(x => applyL(x, s)), 'para', [ida, idb]]);
```

這讓推論**可靠性不受影響**（前提仍蘊含結論），但**完備性打折**：等式從此離開子句集，不能再被拿來做別的替換。現代 ATP 用「超對稱」（superposition）取代這條規則，等式既被保留又被簡化。

**資源上限**。`prover.js:144`：

```js
  const maxMs = opts.maxMs || 10000, maxN = opts.maxClauses || 20000, t0 = Date.now();
```

十秒與兩萬個子句。這不是隨便挑的數字，而是「在 JavaScript 單執行緒、每次代換都做完整展開的條件下，先保證能回應」的字面反應。真正的 ATP 的上限通常以「小時 / 幾百萬子句」計。

## 8.1.5 為什麼歸納型別是必需品

前面列了四個缺口，但只有一個是「數學的必需品」，其他三個都是「工程上的必需品」。**歸納型別屬於前者**：沒有它，你連一個像樣的自然數定理都寫不出來。

原因有三層。

第一層是**定義**。Peano 在 1889 年給自然數的定義是： $0$ 是一個自然數；每個自然數 $n$ 有一個後繼 $\mathrm{succ}\ n$ ；除 $0$ 之外每個自然數都是某個自然數的後繼。這三句合起來描述的是一個**由構造子生成的最小集合**。Coq 的 `Inductive nat := O | S nat.` 做的事情就是把這三句翻譯成機器可檢查的形式。

第二層是**消去**。有了 `Nat` 這個型別與它的兩個構造子，我們還需要一條規則說「對 $n$ 的每個案例做歸納」。在 Coq 裡這條規則不是手寫的，而是 `Inductive` 指令**自動產生**的 `nat_rect`：

```
nat_rect : ∀ (P : nat → Prop), P O → (∀ n, P n → P (S n)) → ∀ n, P n
```

注意它的形狀：把「要證明什麼」抽象成一個**假設的命題** $P$ （這就是 motive），把「 $P(0)$ 與歸納步驟」變成前提，把「 $\forall n . P(n)$ 」變成結論。`Inductive` 指令實際上產生了四樣東西：

1. 一個新的 Π 型別 `nat : Type`；
2. 一組建構子 `O` 與 `S`，帶有它們的型別；
3. 一個 recursor（`nat_rect`）以及它對應的證明規則；
4. 一個**消去限制**：recursor 的 motive $P$ 可以消去到 `Prop`，但消去到 `Type` 需要額外條件（大消去）。

第三層是**嚴格正性**。為什麼 Coq 不允許你寫

```
Inductive Bad := mk : ((Bad → nat) → nat) → Bad.
```

因為這會導致矛盾。直覺是：`Bad` 若能被「接受一個把 `Bad` 變成 nat 的函式」的函式構造出來，那麼 `Bad` 就同時是「最小的非空集合」與「能構造出矛盾」的東西。Coq 的檢查規則是：型別參數只允許出現在**嚴格正**的位置（`nat` 裡不允許、`(Bad → nat) → nat` 裡 `Bad` 出現在箭頭的**左邊**，所以不允許）。這條檢查叫 **strict positivity**，它是歸納型別正確性的技術保證。

現在來回答一個關鍵問題：**為什麼 `lambda-cube` 加不了歸納型別？** 因為上面第 3 點的 recursor 需要 `nat_rect` 的型別裡，motive 的 sort 要比 `nat` 所在的宇宙**高一階**：

```
nat_rect : ∀ (P : nat → Type_0), ... → ∀ n : nat, P n
```

`P : nat → Type_0` 這個 Π 型別本身住在 `Type_1`。所以要寫下 `nat_rect` 的型別，系統必須有 `Type_0` 與 `Type_1` 兩個宇宙——**宇宙階層不是歸納型別的配件，而是它的前提條件**。這就是 Girard's paradox 的教訓在工程上的回響，下一小節會說清楚。

## 8.1.6 宇宙階層與 Girard 悖論

先把邏輯講完。假設類型系統裡有 $\mathit{Type} : \mathit{Type}$ ，也就是「型別的型別就是型別」。Girard 在 1970 年證明：這樣的系統**不一致**。理由的骨架是：

1. 由於 $\Lambda x . x\ x$ 這種自我套用的型別存在；
2. 由於 $\mathit{Type} : \mathit{Type}$ ，可以構造一個把「型別」本身送進「型別」的項；
3. 把它與自我套用結合，就得到一個循環的等式，產生矛盾。

形式化的細節不必在此重複，但**結論必須記住**：單一宇宙（ $\mathit{Type} : \mathit{Type}$ ）是不安全的；安全的做法是**階層**： $\mathit{Prop} : \mathit{Type}_0 : \mathit{Type}_1 : \mathit{Type}_2 : \dots$ ，而且每一層的 Π 型別只能住進**下一層**。這是 Martin-Löf 的直觀主義型別論與 Coq/Lean 都採用的設計。

現在回頭看 `cube.js:97`：

```js
      case 's': if (t.s === 'Prop') return Sx('Type'); throw E('Type 沒有型別(λ-cube 的最頂層)');
```

這行的背後設計是：**λ-cube 的 `Type` 是一個「沒有型別的最高 sort」**，它扮演的是 $\mathit{Type}_0$ 與 $\mathit{Type}_1$ 的合流位置——既是「命題的 sort」，又是「型別的 sort」，但**自己不再往上**。這麼做的直接好處是：Girard 悖論的原料（ $\mathit{Type} : \mathit{Type}$ ）在系統裡**不可表達**，所以不需要正性檢查之外的任何額外防護；`Type>Type` 這條規則（`cube.js:103`）只作用在「 $\mathit{Type}$ 是 $\mathit{Type}$ 的定義域」這種 Π 型別上，作用不到「 $\mathit{Type}$ 自己有型別」這件事上。

代價則是 5.5 節說的那樣：kinds 缺席，`Type>Type` 這條規則名不副實。

**最小改動**是把單一 `Type` 拆成一個宇宙族：把 sort 節點 `Sx(s)` 改成 `Sx('Type' + n)`，讓 `Prop` 的型別是 `Type_0`、`Type_0` 的型別是 `Type_1`，並且在 `cube.js:103` 的形成規則檢查裡要求「值域的宇宙編號嚴格大於定義域的宇宙編號」。這一步做完之後，`λω_` 的 `Type>Type` 才真的是「型別運算子」的規則，`nat_rect` 才有地方住。

## 8.1.7 η 規則與「項的定義等價」

η 規則有兩條：

$$
\frac{x \notin FV(t)}{\Gamma \vdash \mathrm{fun}\ x \Rightarrow t[x/x] \equiv t : \Gamma} \qquad \frac{\Gamma \vdash f : A \to B}{\Gamma \vdash \mathrm{fun}\ x \Rightarrow f\ x \equiv f : \Gamma}
$$

第一條是 **η-擴張**：`fun x => t` 與把 $t$ 裡的 $x$ 換回那個綁定變數的 $t$ 等價。第二條是 **η-收縮**：`fun x => f x` 與 `f` 等價。

為什麼需要它？因為 $\beta$ 歸約只處理「應用的函式是 λ 抽象」的情況，它**不會**把 `fun x => f x` 化簡成 `f`。而如果一個系統裡有「項的定義等價」這個概念（例如 `def` 展開、之後又要做 $\beta$ -正規形比較），那麼 `f` 與 `fun x => f x` 會被判為不等價，導致種種反直覺的失敗：

- `def f := fun x => g x` 與 `def f := g` 應該是同一個定義，但 `conv` 說它們不同；
- 依值型別的推導中，`Vec n` 與 `Vec (f x)` 在 `f = fun x => g x` 的情況下應該可互相轉換，但 `conv` 做不到；
- 一旦把 $\equiv$ 做成 `Prop` 裡的命題（8.5 節第一個練習要做的事），`refl` 的檢查就會直接卡在這裡。

**最小改動**是讓 `conv` 的 `l` 分支多走一步：把 `fun x => b` 與 `b'` 比較時，先檢查 $x$ 是否不出現在 $b'$ 的自由變數中，若出現則嘗試把 $b'$ 裡的 $x$ 代回 `b`（注意 $b$ 裡綁定的 $x$ 對應 de Bruijn 索引 `0`，所以要用 `subst(b, 0, V(1))` 這類操作），化簡後再比較。這個改動不超過十行，但它需要 `lambda-cube` 有一個**項的自由變數計算器**——目前 `cube.js` 沒有（`uses` 只判斷「某個索引是否被用到」，`cube.js:15`），所以連第一步都要補。

## 8.1.8 最小改動一覽

把本節的三個缺口轉成可執行的清單：

| 缺口 | 最小改動 | 大約工作量 | 會不會動到核心 |
|---|---|---|---|
| 等號 | 加 `eq` 命題形狀 + `eqI` / `eqE` / `eqRefl` 三條核心規則 + 一個 `subst` 策略 | 約 60 行 | 會（加三個 case） |
| 歸納型別 | 加一個 `ind` 指令，產生 Π 型別、建構子與 recursor；加嚴格正性檢查 | 約 300 行 | 會（加 recursor 的型別推導） |
| 宇宙階層 | sort 變成 `Type_0`、`Type_1`…；形成規則要求編號嚴格遞增 | 約 80 行 | 會（改 `sort` 與 `case 's'`） |
| η 規則 | `conv` 的 `l` 分支加 η-擴張/收縮 | 約 10 行 | 會（改 `conv`） |
| 隱含參數 | 策略層做 unification 推斷 | 約 100 行 | 不會 |
| 項排序（ATP） | 一個項的全序 + 只允許從大到小替換 | 約 120 行 | 會（改 `para`） |

**注意最後一欄**。歸納型別、宇宙階層、η 規則三樣都要動核心，這正好回扣第 7.1 節的 de Bruijn 準則：**核心小，不代表核心不用長大**；核心小的真正意思是「核心裡的每一行都對應一條被明確命名過的推理規則」，而不是「核心永遠停在三十行」。真實的 Lean 核心有幾萬行，但它每一行都對應一條規則或一個定義；本專案的核心三十行，也只是把規則數目壓到了極致而已。

## 8.1.9 小結與交棒

本節盤點了三個系統在表達力上的缺口，並且為每一個缺口找到原始碼裡的證據：

- `lean-prover` 的核心只認七種命題形狀（`lean.js:84-107`），連等號都不在詞法層（`lean.js:7`）；
- `lambda-cube` 缺歸納型別、宇宙階層與 η 規則，分別對應 `cube.js:245`、`cube.js:97`、`cube.js:82-90`；
- `theorem-prover` 的等式缺項排序、化簡與保留，分別對應 `prover.js:131`、`prover.js:114-120`、`prover.js:136`。

三個缺口裡面，**歸納型別與宇宙階層是綁在一起的**（recursor 需要宇宙），**η 規則則是「項的定義等價」的必要前提**。下一節要處理的缺口不在「表達力」這一維度，而在「邏輯強度」：三個系統面對古典邏輯的態度完全不同——`lean-prover` 把它放進核心，`lambda-cube` 把它擋在門外，`theorem-prover` 根本沒意識到這件事。這個差別會直接決定「證明了」這三個字在你的系統裡意味著什麼。
