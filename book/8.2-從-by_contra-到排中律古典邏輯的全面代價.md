# 8.2 從 by_contra 到排中律：古典邏輯的全面代價

8.1 節盤點的是「能表達什麼」的缺口。這一節換一個維度：**在同樣的表達力下，「已被證明」這三個字有多重**。三個系統在這一點上的分歧比表達力上的分歧更徹底，而且更不容易察覺——因為古典性不會讓任何一條證明失敗，它只會讓更多的證明成立。

先把結論擺在前面：**三個系統把古典性放在三個完全不同的位置**。`lean-prover` 把它放進**核心的規則表**裡，是一條有名字的規則（`dne`）；`theorem-prover` 把它放進**整個證明方法的語意假設**裡，是 Herbrand 定理的前提；`lambda-cube` 根本不提供它，所以用戶可以自己用 Π 型別把它「加回來」，但那會讓核心失去 Curry–Howard 的保證。本節要把這三種位置各自的代價講清楚。

## 8.2.1 三個系統的邏輯強度定位

**`lean-prover` 是古典的。** 證據有兩處。核心的規則表裡：

```js
    case 'dne': { const f = need(C(p.p), 'imp', '反證'); return f.r.t === 'bot' && f.l.t === 'imp' && f.l.r.t === 'bot' ? f.l.l : bad('反證需要 ¬¬A'); }
```

（`lean-prover/src/lean.js:98`）

以及策略層的 `by_contra`：

```js
    case 'by_contra': { const h = ws[0] || 'h', neg = { t: 'imp', l: f, r: BOT }, n = ng([...ctx, [h, neg]], BOT); return solve({ r: 'dne', p: { r: 'impI', h, f: neg, p: M(n) } }, [n]); }
```

（`lean-prover/src/lean.js:157`）

注意 `by_contra` 做的事情正是標準的自然演繹反證法：把目標 $A$ 的否定 $\neg A$ 當成假設引進來，把目標換成 $\bot$ ，然後用 `dne` 把 $\neg\neg A$ 收成 $A$ 。**核心裡沒有 $\neg\neg$ 這個形狀**——`~A` 在解析階段就展開成 `A → ⊥`（`lean.js:23`），所以 $\neg\neg A$ 的形狀是 `(A → ⊥) → ⊥` ，而 `dne` 正是認這個形狀（`f.l.t === 'imp' && f.l.r.t === 'bot'`）。

**`lambda-cube` 在 `Prop` 裡是直觀的。** 這裡需要一個精確的說明，因為「沒有否定」聽起來像缺陷，但事實上它是這個系統最乾淨的地方。`lambda-cube` 的核心裡沒有 $\neg$ 、 $\wedge$ 、 $\lor$ 、 $\exists$ 、 $\bot$ 任何一個符號（`cube.js:1-2` 的檔頭註解就說明了這點），它們全部是使用者用 Π 型別定義出來的縮寫。而用 Π 型別定義出來的否定只能是**直觀的否定**：

$$
\neg A \;\equiv\; A \to \bot \qquad \text{其中} \qquad \bot \;\equiv\; \forall (X : \mathit{Prop}),\, X \to X
$$

在這個編碼下， $\neg\neg A$ 就是 $(A \to \bot) \to \bot$ ，而 $\neg\neg A \to A$ **不可導**——這正是直觀主義邏輯與古典邏輯的分界線（6.3 節會把這道牆具體展示出來）。λ-cube 的核心裡沒有任何一條規則能推出它，因為核心的每一條規則都有 Curry–Howard 讀法： $\Pi$ 抽象與 $\Pi$ 消去、 $\lambda$ 抽象與 $\beta$ 歸約、sort 檢查。這套規則系統在語意上就是 Heyting 代數。

**`theorem-prover` 是古典的，但古典性不在某一條規則裡。** 它的否定不是物件層的連接詞，而是**元層的一個旗標**。`nnf()` 對否定做的處理是「翻轉極性」：

```js
    case 'not': return nnf(f.f, !pos);
```

（`theorem-prover/src/prover.js:53`）

而極性最終落在每個文字的 `s` 欄位上：

```js
    default: { const a = f.t === 'not' ? f.f : f; return { t: 'lit', s: f.t !== 'not', n: a.n, a: a.a.map(x => sub(x, env)) }; }
```

（`theorem-prover/src/prover.js:65`）

目標的否定則是在載入時直接包一層：

```js
  if (goal) { const g = load(goal, 'negated goal'); items.push({ f: { t: 'not', f: g.f }, rule: g.rule }); }
```

（`theorem-prover/src/prover.js:157`）

這裡值得停下來看清楚，因為它是三個系統裡最容易被忽略的一點：**歸結法之所以「古典」，不是因為它有某一條古典規則，而是因為它整個證明方法建立在古典的一階語意上**。第 2.4 節說過 Herbrand 定理的角色：歸結法在 Herbrand 展開的意義下判定的是**古典一階邏輯**的可證性。否定是「這個公式為假」的意思，而不是「導出矛盾」的意思。所以 `theorem-prover` 裡根本沒有「反證法」這件事——**整個證明都是反證法**：把目標的否定塞進子句集，找矛盾。

順帶說明一個實測結果：`theorem-prover` 的內建範例裡有 Peirce 定律，而它只用了三個子句就證完：

```
== Peirce’s law
✔ 證明成功(產生 3 個子句,0 ms)
  1. P    [否定結論]
  2. ~P    [否定結論]
  3. ⊥    [歸結 2, 1]
```

（`theorem-prover/src/prover.js:214` 的範例，跑 `node bin/cli.js --demo` 得到的輸出）

三個子句，因為 Peirce 定律的否定在 NNF 與 CNF 之後塌成了一個矛盾的子句對。**這裡沒有任何「古典性的痕跡」**——它不是被某條規則標記出來的，它只是整個方法的預設。

## 8.2.2 `dne` 是核心裡唯一的非直觀成分

現在把視角拉回 `lean-prover`。第 3.3 節做過一張表，把核心的每一條規則都對應到自然演繹規則與 Curry–Howard 讀法。那張表裡有**三個「無對應」**：`dne`、`sorry`、`meta`。前兩個是工程性機制（被標記的逃生門與未填的洞），只有 `dne` 是**邏輯性的**。

這一點值得說得更細。核心的規則表裡，其他每一條規則都可以用一句「它把什麼變成什麼」來描述：`impI` 把假設包成 $\Pi$ 型別，`impE` 是 modus ponens，`andI` 組成合取，`allI` 一般化。而 `dne` 的描述只能是：「接受一個形狀為 $\neg\neg A$ 的前提，交出 $A$ 」。**在直觀主義邏輯裡，這條推理是不允許的。**

那為什麼把它放進核心是安全的？因為三個理由要分開講：

1. **它不會造成不一致。** 加上 `dne` 的系統不會推出 $\bot$ 之外的東西——它只是讓更多命題可證。核心仍然是**可靠的**（sound）：核心接受的每一個證明項，在古典語意下都對應一個真的命題。
2. **它是經典邏輯中本來就成立的定理。** $\neg\neg A \to A$ 在古典邏輯裡是定理，不是公理。所以把它放進核心並沒有「偷偷加進一個假設」，只是把「古典語意下成立的事實」提前用了。
3. **它被命名了。** 這是關鍵。3.3 節說過：「古典性不必藏進每一一條規則裡，只要被命名為一條獨立的規則，它就能被辨識、被移除、被討論。」`dne` 是一個 `case`，你可以 grep 它、可以把它移除、可以在文件裡說明它做了什麼。**它沒有被藏起來。**

但第三點也正是問題所在。**一旦它被命名，問題就從「你藏了什麼」變成「你為什麼把它放在這個層級」**。這就是本節要回答的問題。

## 8.2.3 邏輯強度的取捨

把三個系統的邏輯強度排成一列：

| | 直觀部分 | 古典部分 | 古典性放在哪裡 |
|---|---|---|---|
| `lean-prover` | `hyp`…`exE` 共 17 條規則 | `dne` 一條 | **核心**（`lean.js:98`） |
| `lambda-cube` | 全部規則 | 無 | **不存在**（可由使用者自行定義，但核心不保證） |
| `theorem-prover` | 無（整體古典） | 全部 | **證明方法的語意**（Herbrand 定理） |

「更強的邏輯」帶來兩件事，方向相反：

**好處：更多命題可證。** `lean-prover` 的 `dne` 讓 Peirce 定律與雙重否定消去可以被證明，內建範例裡就有這兩條（`lean.js:235-236`）。在 `theorem-prover` 裡，幾乎所有非平凡的古典命題都能被找到。

**代價：「可證」不再等同於「構造性地可證」。** 這是更根本的損失。在直觀主義邏輯裡，「 $\Gamma \vdash A$ 有一個證明」意味著存在一個**資訊量足夠的物件**（證明項）使得 $A$ 為真——具體說，是存在一個函數把 $A$ 的證明資料變成某個可計算的結果。這個對應不是裝飾性的，它正是 Curry–Howard 對應的內容。**一旦加入 `dne`，「證明項」就不再完全對應「程式」了**，因為證明項裡可能出現一個無法執行的節點。

這裡可以引進 **Glivenko 定理**（1929）作為連結。Glivenko 定理說：

$$
\Gamma \vdash_{C} A \quad\Longleftrightarrow\quad \Gamma \vdash_{I} \neg\neg A
$$

意思是：**古典邏輯可證的命題，一定可以用直觀的方式證出它的「雙重否定版本」；反過來，直觀地證出 $\neg\neg A$ ，在古典語意下就是證出了 $A$ **。這條定理告訴我們兩件事：

- 兩套邏輯之間**沒有不可翻譯的落差**。每一個古典證明都有一個直觀的「影子版本」（把每個原子命題 $P$ 換成 $\neg\neg P$ 就是最簡單的翻譯）。
- 但**翻譯會改變證明項的內容**。翻譯後的證明項不是原來那個，它多了一层否定，也就不再是同樣的程式。

所以「我們用了古典邏輯」這句話，精確地說是：「我們允許證明項的形狀比純直觀的情形更寬，因此**可執行的證明**這個概念被稀釋了」。丢的不是命題，是命題與程式之間的對應。

## 8.2.4 排除中律意味著排除一類程式

現在把 Curry–Howard 用到底，看看排除中律在**程式語言**層面到底排除了什麼。

排中律是：

$$
\forall (P : \mathit{Prop}),\, P \lor \neg P
$$

在 Curry–Howard 之下， $P \lor \neg P$ 是一個**和型別**（sum type），而 $\forall P$ 是一個 Π 型別。所以排中律是一個**函式**：

$$
\mathrm{em} : \forall (P : \mathit{Prop}),\, P \oplus (P \to \bot)
$$

它的行為是：**給我一個命題 $P$ ，我告訴你 $P$ 成立還是不成立。** 這是一個「決策器」。

問題立刻來了： $P$ 可以是「這個程式的 while 迴圈會終止嗎」。`em` 是一個把任意命題轉成答案的函式——**它不可能被執行**，因為執行它就等於解決一個未決問題。Brouwer 拒絕排中律（2.3 節開頭那段歷史）不是因為它「不直觀」，而是因為它是一個**不可能存在的程式**。

同樣的邏輯可以用 Peirce 定律再說一次（6.4 節會把它與 `lean-prover` 的實際證明對照）。Peirce 定律

$$
((P \to Q) \to P) \to P
$$

在 Curry–Howard 之下是一個函式：給我一個「能從 $P \to Q$ 推出 $P$ 」的函式，我還給你 $P$ 。直覺上它的實作必須是「拿到 $P \to Q$ 的手續，設法產出 $P$ 」——在直觀世界裡你沒有別的辦法，所以做不到。

**雙重否定消去也一樣**： $\neg\neg P \to P$ 在 Curry–Howard 之下是

$$
\mathrm{dne} : (P \to \bot) \to \bot \to P
$$

注意這個型別的形狀：**它是一個「雙重否定」的接收器**。第一個引數是「給我一個把 $P$ 變成矛盾的函式」，第二個是「給我一個矛盾」，它回傳 $P$ 。這個函式在程式語言裡有名字，而且你可能已經用過：**它就是 `call/cc`**。

具體地說，在 Scheme 裡：

```scheme
(define call/cc
  (lambda (k)
    (call/cc (lambda (k2) (k k2)))))
```

`call/cc` 的型別正是 $(A \to R) \to R$ ——「給我一個 continuations $k$ ，如果我用 $k$ 跳走，整個呼叫就以 $k$ 的引數為回傳值結束」。而 `call/cc` 是從 `dne` 造出來的：給定一個「丟棄 $P$ 」的函式 $f : P \to \bot$ 與一個「捕獲 $f$ 的呼叫」的函式，就能把 $P$ 逼出來。

這裡有一個關鍵的工程事實：**`call/cc` 是可執行的**。它是一個真實語言裡最有用的控制結構之一。所以「古典邏輯排除了一類程式」這句話需要修正：**它排除的不是所有帶古典性的程式，而是「不可執行的」那部分——具體說，是那些要求你對一個不可判定問題給出答案的程式。** `call/cc` 不要求你回答不可判定的問題，它只是改變控制流。

這就是為什麼 Coq 與 Lean 都把古典邏輯放進**函式庫（library）**而不是核心：Lean 的 `Classical.em` 與 `Classical.choice` 是 `Classical` 命名空間裡的公理，使用者必須 `open Classical` 把它引進來；Coq 的 `Classical_Prop.v` 同理。它們在 `Prop` 裡是公理（因此可以 `exact` 進任何命題），但**不能被用來計算**——這正是為什麼 Lean 裡從 `Classical.em` 抽出的資料要用 `noncomputable` 標記。

**「可證」與「可計算」的分界線，就畫在這裡。**

## 8.2.5 這對「從證明器學到程式語言」的影響

現在可以回答本節的總問題：這對「從證明器學到程式語言」有什麼直接影響？

第 1.1 節把全書的中心問題定在「當我們說『一個命題已被證明』時，機器究竟檢查了什麼？」。本節的答案是：**答案取決於你把古典性放在哪一层。**

- 在 `theorem-prover` 裡，答案是「機器找到了一條 Herbrand 意義下的矛盾鏈」。這是一個**語意**答案：沒有「證明項」這回事，只有推理鏈。整個鏈的每一步都是古典的。
- 在 `lambda-cube` 裡，答案是「存在一個項，其推導型別在 $\beta\delta$ 等價下等於宣告型別」。這是一個**構造性**答案：那個項就是證明本身。
- 在 `lean-prover` 裡，答案是「存在一個證明項，其型別等於宣告命題」——**但這個證明項可能含有一個 `dne` 節點**。所以嚴格地說，答案是「存在一個證明項，它除了別的規則之外還允許使用一次被命名為 `dne` 的古典步驟」。

第三個答案既不是純語意的，也不是純構造性的。它是**混合的**，而混合的邊界必須由文件說清楚。3.3 節那句「古典性不必藏進每一條規則裡，只要被命名為一條獨立的規則，它就能被辨識、被移除、被討論」，講的就是這件事：**命名是最低成本的誠實。**

## 8.2.6 實務建議：把古典性隔離出去

如果真的要讓 `lean-prover` 更接近真實的 ITP，最小改動不是「把 `dne` 拿掉」，而是**把它降級**：

1. 把 `case 'dne'`（`lean.js:98`）從核心移到一個**明確標記的公理通道**——類似 `sorry` 但不設 `fl.sorry` 旗標，而是設一個 `fl.classical` 旗標，報告層用它把狀態標成「含古典假設」。
2. 讓 `by_contra`（`lean.js:157`）在使用者沒有明確宣告（例如 `open classical`）時報錯。
3. 在文件與 README 的「限制」段落裡寫明：**核心是可直觀化的；古典性來自一條被命名的規則。**

代價是使用者要多打一行字。收益是：**當有人問「你這個證明是不是構造性的」，答案是一個可以 grep 的字串，而不是一個需要通讀規則表的判斷。**

順帶說明另一個方向：`theorem-prover` 的古典性藏在 Herbrand 語意裡，**無法用同樣的手法隔離**。因為它的「規則」是子句運算，而子句運算本身在古典語意下才正確。要在這裡做誠實，只能在**報告層**做：把 `proved` 與 `saturated` 的措辭寫清楚（這一點 4.7 節末尾已經做了：「結果未知」四個字很重要），並且在文件裡明說「本證明器是古典一階邏輯的決策程序」。

## 8.2.7 小結與交棒

本節的核心結論有三條：

1. **三個系統把古典性放在三個不同的地方**：`lean-prover` 放在核心的一條規則（`lean.js:98`），`theorem-prover` 放在整個方法的古典語意裡，`lambda-cube` 根本不提供。
2. **`dne` 可以安全地放進核心**，因為它是古典邏輯中本來就成立的定理，而且被命名了；放它進去的真正代價不是可靠性，而是「可證」不再等同於「構造性地可證」，Curry–Howard 對應在那個節點上失效。
3. **在程式語言層面，排除中律排除的是「對不可判定問題給出答案的程式」**；而雙重否定消去對應的 `call/cc` 恰恰是可執行的，所以「古典邏輯 = 不可執行的邏輯」是過度簡化。正確的說法是：**古典性擴大了邏輯強度，同時稀釋了「證明 = 程式」的對應**。

Glivenko 定理說明這兩套邏輯之間沒有不可翻譯的落差，所以「要不要古典性」不是對錯問題，而是**要把它放在哪一層、要不要在報告裡說清楚**的問題。

下一節要處理的，是另一個同樣屬於「真實證明器必須回答」的問題：**自動化的第二種可能**。前面的章節裡，三個系統的自動化程度都低得離譜——`lean-prover` 的每一條策略都要人手動指定，而真實的 Lean 證明裡，樣板策略佔了大半。8.3 節會說明：為什麼在這個專案的架構裡加一個 `auto` 是容易的，以及它為什麼仍然是**壞交易**。
