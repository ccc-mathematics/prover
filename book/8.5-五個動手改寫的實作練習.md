# 8.5 五個動手改寫的實作練習

8.4 節結束在一份清單上。理論講完了，剩下的事情是把它們變成程式碼。本節給出五個練習，每一個都建立在前面幾節的論證之上，並且都**可以獨立完成、独立驗收**。

這五個練習不是「回家功課列表」，而是**一條可行的升級路徑**：它們依序從「最容易但最能改變日常體驗」走到「最難但最能改變系統定位」。練習 1 讓 `lean-prover` 能處理等式；練習 2 讓 `lambda-cube` 能處理歸納；練習 3 讓 `theorem-prover` 變快；練習 4 讓 `lean-prover` 少做重複勞動；練習 5 把三個玩具縫合成一個可以互相驗證的系統。

## 8.5.0 五個練習總覽

| # | 目標 | 主要檔案 | 難度 | 預估工時 |
|---|---|---|---|---|
| 1 | 在 `lean-prover` 加入等號 | `lean-prover/src/lean.js` | 中階 | 4–6 小時 |
| 2 | 在 `lambda-cube` 加入歸納型別 | `lambda-cube/src/cube.js` | 高階 | 10–15 小時 |
| 3 | 在 `theorem-prover` 加入項排序與單位傳播 | `theorem-prover/src/prover.js` | 中階 | 4–6 小時 |
| 4 | 加一個 `auto` 策略 | `lean-prover/src/lean.js` | 初階 | 3–5 小時 |
| 5 | 把三個系統做成同一個前端 | 新增 `tools/` 與共用模組 | 中階 | 6–8 小時 |

順序建議：**先做 4，再做 1，再做 3，最後做 2 與 5**。練習 4 最容易；練習 1 與 3 各自把一個玩具推向可用；練習 2 最接近「重做一個真實系統的核心」，最有分量也最容易被放棄。

## 8.5.1 練習一：在 lean-prover 加入等號

**要改哪裡。** 全部在 `lean-prover/src/lean.js`：

| 位置 | 現況 | 要做的事 |
|---|---|---|
| `lean.js:7` | 詞法規則不含 `=` | 加入 `=` 的詞法 |
| `lean.js:16` | `term()` 只組裝函式應用 | 保持不變（等式兩端就是項） |
| `lean.js:21-34` | `un()` 產生七種命題節點 | 新增 `eq` 節點：`{ t: 'eq', l: term, r: term }` |
| `lean.js:42-51` | `fm()` 顯示 | 新增 `eq` 的顯示分支 |
| `lean.js:55-57` | `key()` 與 `eq()` | `key()` 需處理 `eq` 節點（`eq` 兩端要用 `kt()` 正規化） |
| `lean.js:84-107` | 核心規則表 | 新增 `eqI`、`eqE` 兩個 case |
| `lean.js:138-172` | 策略表 | 新增 `subst`、`rewrite` |

**建議做法。** 核心新增兩條規則。

第一條是**等式引入（refl）**。以下是建議的實作草稿（**不是現有原始碼**）：

```js
    case 'eqI': return { t: 'eq', l: p.a, r: p.b };
```

它直接回傳證明項裡記錄的兩端。這與 `impI` 的設計哲學一致（3.3.2 節說過）：**證明項必須自足**，核心不去推導「等式兩端應該長什麼樣」，而是信任證明項攜帶的資訊。為了防止偽造，`eqI` 應當檢查 `p.a` 與 `p.b` 結構相等：

```js
    case 'eqI': return kt_eq(p.a, p.b) ? { t: 'eq', l: p.a, r: p.b } : bad('等式引入的兩端不同');
```

（仍是草稿；`kt_eq` 這個比對函式要新寫，作用是把兩個項正規化後比較，邏輯上與 `key()`（`lean.js:55`）相同。）

**這一行是整個練習裡最重要的一行**：如果沒有它，使用者可以寫 `theorem t : a = b := by eqI` 而核心照單全收——那整個等號機制就是假的。7.5 節講過「核心必須拒絕偽造證明」，這就是那個原則的第一次實戰。

第二條是**等式消去（代入）**：

$$
\frac{\Gamma \vdash a = b \qquad \Gamma \vdash P[a]}{\Gamma \vdash P[b]}
$$

在 `lean-prover` 的 AST 裡， $P$ 是一個**命題**（不是一個帶洞的項），所以最直接的實作是：讓證明項攜帶「被代入的命題」與「代入後的命題」，核心檢查兩者確實相差一次代換。建議的實作草稿（**不是現有原始碼**）：

```js
    case 'eqE': { const e = need(C(p.p), 'eq', '等式消去'); const b2 = C(p.b); return eq(sub(b2, e.l, e.r), p.f) ? b2 : bad('等式消去的結論不吻合'); }
```

注意 `sub()`（`lean.js:66-76`）已經存在，而且已經處理變數捕獲（3.5 節）。**這是重用既有工具的典型例子**：等號機制不需要新的代換引擎。

策略層的 `subst` 就更簡單了：找到 context 裡一條形如 `h : a = b` 的假設，把目標 `f` 裡的 `a` 換成 `b`，然後產生一個 `eqE` 證明項。

**需要新增什麼規則。** 核心兩條（`eqI`、`eqE`），策略兩條（`subst`、`rewrite`）。另外建議把 `~` 與 `!=` 統一處理：`a != b` 展開成 `(a = b) → ⊥` ，與 `~A` 展開成 `A → ⊥` 的做法一致（`lean.js:23`）。

**需要新增什麼測試。** 在 `lean-prover/test/test.js` 加上：

1. **等式三律**（對稱、傳遞、取代）三個 `done` 的例子；
2. **核心拒絕偽造**：手寫一個 `{ r: 'eqI', a: term_a, b: term_b }` 但兩端不同的證明項，斷言 `L.check` 丟出例外。這條測試要照 7.5 節的既有寫法（`lean-prover/test/test.js:7-8` 已經有一個 `andE1` 的偽造案例）；
3. **等式與命題邏輯的互動**：例如從 $P$ 與 $P = Q$ 推出 $Q$ 。

另外新增一個範例檔 `lean-prover/examples/eq.lean`，內容是第 6.7 節群論案例的**簡化版**：只保留左單位律與反元素定義，證明 `inv(e) = e`。**要注意 ITP 證群論會比 ATP 冗長得多**——這正是第 6.7 節要量化的對比。

**驗收標準。**

- `node bin/cli.js --demo` 必須**多印出新範例**（等式三律那一組），且輸出格式與其他範例一致；
- `npm test` 全綠，且測試裡明確包含「核心拒絕偽造的等式證明項」；
- `lean-prover/README.md` 的「限制」段落必須更新（現在寫著「沒有等號、歸納、型別與自動化」，至少要拿掉「等號」）。

## 8.5.2 練習二：在 lambda-cube 加入歸納型別

**要改哪裡。** `lambda-cube/src/cube.js`，牽涉四個地方：

| 位置 | 現況 | 要做的事 |
|---|---|---|
| `cube.js:7-9` | 節點只有五種 | 新增 recursor 應用節點，或以 `def` 的 `val` 承載 |
| `cube.js:75-117` | `kernel()` | `infer()` 與 `whnf()` 要認得歸納型別的建構子與 recursor |
| `cube.js:168-222` | `runScript()` | 新增 `ind` 指令分支 |
| `cube.js:172` | `starts` 的正規表示式 | 加入 `ind` 關鍵字 |

**建議做法。** 指令的語法可以設計成：

```
ind Nat : Type :=
  | zero : Nat
  | succ : Nat -> Nat
```

它必須產生四樣東西：**一個 Π 型別**（`Nat : Type`）、**一組建構子**（`zero : Nat`、`succ : Nat -> Nat`）、**一個 recursor**（`nat_rect`）、以及**一個正性檢查的結果**。

recursor 的型別是整個練習的技術核心。Coq 裡的 `nat_rect` 是：

```
nat_rect : ∀ (P : Nat → Prop), P zero → (∀ n, P n → P (succ n)) → ∀ n, P n
```

現在把這個型別放進 `lambda-cube` 的 sort 系統裡看會發生什麼：

- `P : Nat → Prop` 這個 Π 型別的定義域 sort 是 `Type`、值域 sort 是 `Type`，因此需要 `Type>Type` 規則；
- `∀ n, P n` 的值域 sort 是 `Prop`（因為 `P n : Prop`），定義域 sort 是 `Type`，需要 `Type>Prop`；
- 整個 `nat_rect` 的 sort 因此是 `Type`。

**所以 `nat_rect` 在單一宇宙的 λ-cube 裡是放得下的**——前提是系統有 `Type>Type` 與 `Type>Prop` 兩條規則，也就是 λC 與 λω。**但這正是 8.1.6 節說的宇宙問題的第一個具體案例**：若 `P` 的值域改成 `Type`（大消去，允許 `nat_rect` 用來定義資料型別上的函數），那麼 `P : Nat → Type` 這個 Π 型別本身就住在「比 `Type` 高一階」的地方，而單一宇宙容不下它。

**因此本練習的關鍵設計決定是：先做小消去（motive 限制在 `Nat → Prop`），把大消去當成後續擴充。** 並在文件裡說清楚為什麼——因為「小消去 vs 大消去」正是歸納型別與宇宙階層的交會處。

`Vec` 是第二個目標，也是第二個難關。`Vec : Nat → Type` 需要 `Prop>Type`（λP），而它的建構子 `cons : ∀ (n : Nat), Vec n -> Vec (succ n)` 需要依值型別，也就是 λP 的 Π 消去規則。**所以 `Vec` 只能在 λP 或 λC 下做**，在 λ→ 或 λ2 下會被 `cube.js:103` 的形成規則擋下來——這個錯誤訊息本身就會成為教材。

**需要新增什麼規則。**

1. **核心規則**：`nat_rect` 的消去規則。Coq 的計算規則是 `nat_rect P pz ps zero` 化簡成 `pz`，`nat_rect P pz ps (succ n)` 化簡成 `ps n (nat_rect P pz ps n)`。在 `lambda-cube` 裡，這意味著 `whnf()`（`cube.js:77-81`）要能對 recursor 應用做 case analysis。這需要一個新節點形狀 `{ k: 'r', ... }`，或者把 recursor 的 `val` 寫成一個 Church 編碼風格的 λ 項。
2. **正性檢查**：一個 `ind` 指令的建構子參數裡，型別參數只允許出現在「嚴格正」的位置。最小實作可以先做一個**保守版**：拒絕任何在建構子參數型別裡出現被定義型別名的情況（這比嚴格正性更嚴，會拒絕一些合法的例子，但足以示範機制）。更好的做法是實作正性檢查：沿著型別的結構遞迴，允許 `Nat` 出現在恆等、`Nat → A`（箭頭左邊）、`List Nat`（參數位置）等位置，拒絕 `(Nat → A) → B` 這種。
3. **`def` 的遞迴限制**：`cube.js:213` 讓 `G[name]` 在解析完主體之後才寫入，所以 `def` 不能遞迴。歸納型別**恰好就是遞迴的正確形態**（`succ` 的型別提到 `Nat`，但它的實作是建構子，不是函式本體），所以 `ind` 不需要動 `def` 的這條規則。

**需要新增什麼測試。**

1. `lambda-cube/test/test.js` 新增：對 `Nat` 做歸納的定理證明成功（`runScript(...).ok === true`）；
2. **正性檢查的負例**：`ind Bad : Type := | mk : (Bad -> Nat) -> Bad` 必須被拒絕，而且錯誤訊息要說明是「嚴格正性」違規；
3. **宇宙限制的負例**：在 λ2（沒有 `Prop>Type`）下定義 `Vec` 必須被擋下，並且錯誤訊息要指出缺哪條規則；
4. 新增範例檔 `lambda-cube/examples/nat.lc`。

**驗收標準。**

- `node bin/cli.js --demo` 多印出歸納範例；
- `npm test` 全綠，且測試明確涵蓋「正性檢查拒絕不正型的歸納定義」與「小宇宙下拒絕大消去」；
- `lambda-cube/README.md` 的「限制」段落必須更新（移除「沒有歸納型別」，並補上「只有小消去」這個新的限制說明）。

## 8.5.3 練習三：在 theorem-prover 加入項排序與單位傳播

**要改哪裡。** `theorem-prover/src/prover.js`：

| 位置 | 現況 | 要做的事 |
|---|---|---|
| `prover.js:128-140` | `para()` 兩個方向都試 | 只允許從大到小替換 |
| `prover.js:114-120` | `norm()` 只去重複與剔恆真 | 加入化簡（可選） |
| `prover.js:147-154` | `accept()` | 接受子句時做單位傳播 |
| `prover.js:160-186` | 主迴圈 | 優先處理單位子句 |
| `prover.js:204-207` | `statusText` | `saturated` 的措辭必須修改 |

**建議做法。** 項排序用 **Knuth–Bendix 順序**（KBO）的簡化版：**先比重量（大小），重量相同再比字典序**。重量的定義是 $w(t) = a_0 + \sum_i w(t_i)$ （常數與函數符號各有一個正權重， $a_0$ 取 1 即可），變數的重量最小。

實作上要注意 KBO 的兩個性質：**穩定性**（若 $t$ 是 $s$ 的子項則 $t < s$ ）與**可變元性**（若 $t$ 是 $s$ 的實例則 $t \le s$ ）。第一個性質保證「從大到小替換」不會造成無限膨脹；第二個性質保證替換之後大小關係仍然成立。**這兩點必須寫在測試裡**——`theorem-prover/test/test.js` 可以直接測 `gt()` 的這兩個性質，這是少數「可以直接測的數學性質」。

然後把 `para()` 裡的這兩行：

```js
    for (const [l, r] of [[e.a[0], e.a[1]], [e.a[1], e.a[0]]]) {
```

改成依 `gt()` 結果**只選一個方向**（若 $g(l, r)$ 則只能 $l \to r$ ）。

**這一步有一個必須誠實面對的後果：完备性會下降。** 受限方向的參數替換仍然是**可靠的**（結論仍是前提的邏輯後果），但有些等式推論需要從小到大才做得出來。因此 `saturated` 的意義會改變：它不再代表「結論不是前提的邏輯後果」，而只代表「在**有序子句空間**裡沒有更多推論」。**`statusText`（`prover.js:206`）那句「結論不是前提的邏輯後果」必須改成誠實的措辭**，這是 4.7 節末尾那個「結果未知」原則的延伸。

單位傳播的實作不難：**單位子句（unit clause）**是只有一個文字的子句。若 $C = L \lor C'$ 且存在單位子句 $U = L'$ ，其中 $L$ 與 $L'$ 極性相反且可統一，則把 $C$ 裡的 $L$ 刪掉、把統一結果套用到其餘子句。建議在 `accept()` 裡做一趟掃描，並讓主迴圈（`prover.js:163`）優先挑選單位子句。

**需要新增什麼測試。**

1. **項排序的性質測試**：子項性與可變元性；
2. **子句數下降的量化測試**：跑群論範例（`theorem-prover/examples/group.txt`），斷言產生的子句數**不超過原本 1537 的一半**。這是本練習最有價值的測試，因為它把「效能提升」變成一個可自動檢查的數字。
3. **飽和語意的測試**：找一個原本 `proved` 的例子現在變成 `saturated`，並在測試裡**註明這是預期行為**（例如「受方向限制的替換不足以推出結論」）。這個測試的價值在於**把文件裡的措辭與實作的行為綁在一起**。

**驗收標準。**

- `node bin/cli.js --demo` 的群論範例「產生 N 個子句」明顯小於 1537，且仍然是 `✔ 證明成功`；
- `npm test` 全綠，且測試斷言的是**子句數上限**而不只是 `proved`；
- `theorem-prover/README.md` 的限制段落要從「等式推論沒有項排序與化簡」改成說明「已有項排序，但方向受限，因此完备性下降，`saturated` 的語意已調整」。

## 8.5.4 練習四：加一個 `auto` 策略

**要改哪裡。** `lean-prover/src/lean.js` 的 `tactic()`（`lean.js:129-174`），新增一個 `case 'auto':`。**核心一行都不用改**——這正是 8.3.3 節要說明的重點，也是本練習最值得體會的地方。

**建議做法。** 8.3.3 節已經給了完整的設計草稿，這裡補充實作上的三個關鍵決定。

**第一，候選產生器要讀 `check()` 的規則表。** `check()` 的 case 清單就是可用規則的清單：假設引用、`andI`/`andE1`/`andE2`、`orI1`/`orI2`/`orE`、`impI`/`impE`、`botE`、`allI`/`allE`、`exI`/`exE`。候選產生器是它的反函式。**不要另外寫一套推論邏輯**——那會產生兩份可能不一致的規則定義，這是 de Bruijn 準則要防的事。

**第二，終止條件要三層。**

| 條件 | 建議預設 | 為什麼 |
|---|---|---|
| 深度上限 | 5 | 防止 `intro` / `apply` 交替造成的無限路徑 |
| 節點（候選）上限 | 200 | 防止組合爆炸 |
| 目標數上限 | 20 | 防止 `constructor` 反覆分裂目標 |

這三個上限都應該讓使用者可調（例如 `auto 10` 表示深度上限 10），並且在超限時**丟出明確的錯誤**（例如「auto: 超出預算，請改用手動策略」），而不是讓程式 hang 住。

**第三，可讀性的折衷。** 具體做三件事：

1. **留下足跡。** `auto` 執行完之後，在命令列輸出裡印出它使用的規則序列（例如 `auto: apply h2 → apply h1 → exact hp`）。8.3.4 節說過，自動化侵蝕的是「可審查性」，所以讓 `auto` 自我說明是最低成本的補救。
2. **只做收尾。** `auto` 應該只處理「用區域假設就能收尾」的目標，不要試圖一口氣解決整個定理。實作上最簡單的做法是：`auto` 只作用於**當前目標**（`S.goals[0]`），不跨目標。
3. **證明項仍然可攤平。** `sx()`（`lean.js:179`）本來就能把證明項印成巢狀的文字，`auto` 產生的證明項經過它之後必須是可讀的——這是「`auto` 沒有偷偷用奇怪的規則」的可視證據。

**需要新增什麼測試。**

1. 一個 `auto` 能完成的定理，斷言 `status === 'done'`（**這同時測到核心接受 `auto` 的證明項**）；
2. 一個 `auto` 失敗的定理，斷言 `status === 'error'` 而不是 `open`（`auto` 找不到辦法時應該報錯，不該留下半成品）；
3. **一個 `auto` 產生了錯誤證明項的情況**：這個測試比較難構造，但可以透過「手動破壞策略層」來做——例如臨時讓 `auto` 產生一個型別不符的證明項，斷言核心以 `kernel` 狀態拒絕。這測的是「自動化不能繞過核心」這個不變式。

**驗收標準。**

- `node bin/cli.js --demo` 多印出一個 `auto` 範例，且輸出裡有 `auto` 的足跡；
- `npm test` 全綠；
- 報告層的 `auto` 輸出格式要與其他命令一致（1.3.3 節的五種狀態之一）。

## 8.5.5 練習五：把三個系統做成同一個前端

**要改哪裡。** 這個練習需要新增檔案（不動既有核心），例如：

```
tools/
  cross-check.js      交叉驗證的主程式
  shared.js           共用的 AST 與顯示層
```

**建議做法。** 三種做法，難度遞增：

**做法 A：共用顯示層。** 三個系統的「命題 → 字串」函式（`lean.js:42` 的 `fm`、`cube.js:19` 的 `show`）各寫各的，但輸出格式可以統一。**最簡單，價值最低**，但做完之後三份輸出能並排成表，對第 6 章那種對照的呈現有幫助。

**做法 B：互轉譯。** 這是本練習的重點，而且**比想像中容易**，因為 `lean-prover` 與 `theorem-prover` 的命題 AST 幾乎同構：

| 意義 | `lean-prover`（`lean.js:21-34`） | `theorem-prover`（`prover.js:20-38`） |
|---|---|---|
| 原子 | `{ t: 'atom', n, a }` | `{ t: 'atom', n, a }` |
| 蘊含 | `{ t: 'imp', l, r }` | `{ t: 'imp', l, r }` |
| 合取／析取 | `{ t: 'and'/'or', l, r }` | 同上 |
| 全稱 | `{ t: 'all', v, f }` | 同上 |
| 存在 | `{ t: 'ex', v, f }` | 同上 |
| 否定 | 展開成 `A → ⊥` | `{ t: 'not', f }` |

差別只有三處：**否定**（一方展開、一方是獨立節點）、**項的表示**（`lean.js:16` 的 `term()` 只做函式應用，`prover.js:15` 的 `term()` 還處理常數與變數的區分）、以及**雙條件句**（`lean.js:17` 展開成兩個蘊含，`prover.js:16` 保留為 `iff`）。

所以轉譯器大致是：把 `lean-prover` 的 AST 轉成 `theorem-prover` 的 AST（處理否定與項的差異），然後呼叫 `P.prove(premises, goal)`。**反方向**也值得做：把 ATP 的一條子句 $L_1 \lor \dots \lor L_n$ 轉成 ITP 的 `or` 鏈，再交給 `L.runThm()` 跑。

**做法 C：交叉驗證的測試。** 把第 6 章的那批命題寫成一份**共享的命題檔**（例如 JSON），讓三個系統各跑一次，產出一張對照表：

```
命題              ITP        ATP        λ-Cube
合取交換律        done       proved     ok
雙重否定消去      done       proved     open(直觀邏輯下不可證)
Peirce 定律       done       proved     open
群論 inv(e)=e     open       proved     n/a
```

**這張表就是第 6 章的實驗版**，而且**可重跑**。這是本練習真正的價值：把書裡的論述變成一個每次改動核心都會重新執行的實驗。

**需要新增什麼測試。**

- `tools/cross-check.js` 自己就是測試：它對每條共享命題斷言「三個系統的結果符合預期表」；
- 建議加一個 `npm run cross` 的 script（各專案的 `package.json` 都可以加）；
- 轉譯器的**往返測試**：`lean → ATP → lean` 之後 AST 必須結構相等（用 `lean.js:57` 的 `eq()` 判斷），這是保證轉譯器正確的基本性質。

**驗收標準。**

- `node tools/cross-check.js` 印出一張三欄對照表，且與第 6 章的結論一致；
- 往返測試全綠；
- 三個專案的 `npm test` 仍然全綠（**新工具不得破壞既有測試**）。

## 8.5.6 收尾：證明是程式碼，所以要跑得完

五個練習結束了。把這一章從頭到尾看一遍，會發現一條貫穿的線索，而它正是全書的中心問題——**「當我們說『一個命題已被證明』時，機器究竟檢查了什麼？」**——的另一面：

> **證明是程式碼，所以要跑得對，就得先確保它跑得完。**

這句話可以拆成兩半，各自對應本章的兩條主線。

**「要跑得對」** 對應核心與證明力。8.1 節談歸納型別、宇宙階層與 η 規則，是在問「核心能接受什麼樣的證明項」；8.2 節談古典邏輯的代價，是在問「『可證』這個詞有多重」。兩者的結論是同一個：**可信核心的職責是精確地定義『可證』，而每一次擴充可證的範圍，都必須同時精確地說明擴充帶來了什麼代價**。8.1 節末尾那個「核心小，不代表核心不用長大」的論點，就是這件事的工程面。

**「要跑得完」** 對應搜尋與效率。8.3 節談 `auto`，8.4 節談 SMT 與 ATP 的天花板，是在問「機器能把多少推理攬到自己身上」。結論也是同一個：**自動化能擴大證明器的適用範圍，但它擴大的是「不需要巧思的那一部分」，而需要巧思的部分永遠留給人**。這正是 8.4.5 節那個「廣度優先 vs 深度優先」的總結。

所以，這三個玩具與真實證明器之間的差距，可以用一句話概括：**它們缺的不是聰明，而是「承載更多種類的證明」所需要的機制**——歸納型別、宇宙階層、η 規則（8.1 節），古典性的隔離（8.2 節），自動化策略（8.3 節），項排序與理論組合（8.4 節）。這五個練習，就是把那些機制逐一補進來的動手版本。

最後是一個實用的提醒：**動手改之前，先把 `src/` 當成唯一的真相來源**（1.3.2 節說過：`web/index.html` 是產物，永遠不要直接改它）。每改動核心檔案，就跑一次 `npm run build` 與 `npm test`。第 7.5 節講過測試策略的核心原則：**核心必須拒絕偽造的證明**——每加一條新規規則就要重新確認一次這個原則，因為新規則最容易引入「宣稱的結論與實際推出的結論不一致」這類漏洞。

本章結束。第 9 章是附錄：語法速查、命令列用法與原始碼索引。本章提到的每一個行號——`lean.js:98` 的 `dne`、`cube.js:97` 的 `Type 沒有型別`、`prover.js:131` 的雙向替換、`prover.js:144` 的預算上限——在那裡都查得到。**把這張索引釘在螢幕上，然後去改那些行。**
