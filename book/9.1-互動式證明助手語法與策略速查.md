# 9.1 互動式證明助手：語法與策略速查

本節是 `lean-prover` 的操作手冊。它回答三個問題：**我該怎麼寫命題**、**我該用哪一條策略**、**出錯時訊息在說什麼**。所有條目都對應到 `lean-prover/src/lean.js` 的某一行；第 3 章講「為什麼這樣設計」，本節只負責「怎麼用」。寫策略時把這張表攤在旁邊，寫完一行就查一次策略表，比事後回頭查錯誤訊息省時間得多。

## 9.1.1 檔案格式與定理標頭

一個 `.lean` 檔可以放多個定理。`splitThms()`（`lean.js:221`）用 `/^\s*theorem\b/m` 把檔案切成一段一段，每一段交給 `runThm()`（`lean.js:181`）處理。

| 項目 | 寫法 | 說明 | 原始碼 |
|---|---|---|---|
| 註解 | `--` 到行末 | 整行或行內皆可 | `lean.js:182` |
| 定理標頭 | `theorem 名稱 (h : 前提) ... : 結論 := by` | 必須在**同一行** | `lean.js:184-185` |
| 前提括號 | `(名稱 : 命題)` | 可以有 0 個以上 | `lean.js:187-191` |
| 策略行 | `intro hp` | 一行一條策略 | `lean.js:200` |
| 策略行縮排 | `·` `•` `*` `-` 加空白 | 這些前綴會被剝掉 | `lean.js:198` |

標頭的正則（`lean.js:184`）是這樣的：

```js
const m = L[hi].trim().match(/^theorem\s+([\w']+)\s*(.*?)\s*:=\s*by\s*$/);
```

三個重點。第一，名字必須符合 `[\w']+`，可以含數字、底線與撇號（`h1'` 是合法的假設名）。第二，`(.*?)` 不含換行，所以**標頭不能跨行**——這與第 5 章 λ-Cube 的行為不同（`cube.js:186` 允許標頭跨行）。第三，`:= by` 結尾的 `by` 是必須的，它標示「接下來是策略腳本」。

一個完整的例子：

```
-- 假言三段論
theorem syllogism (h1 : P -> Q) (h2 : Q -> R) : P -> R := by
  intro hp
  apply h2
  apply h1
  exact hp
```

## 9.1.2 命題連接詞語法表

命題語法由 `P()`（`lean.js:10-36`）決定。表格分成三欄：你在檔案裡怎麼寫、解析器把它變成什麼 AST、核心（`check()`）用哪條規則檢查它。

| 你寫的 | Unicode 別名 | 解析後的 AST | 核心規則（`lean.js`） |
|---|---|---|---|
| `A -> B` | `A → B` | `imp` | `impI`（:95）、`impE`（:96） |
| `A & B` | `A ∧ B` | `and` | `andI`（:89）、`andE1`（:90）、`andE2`（:91） |
| `A \| B` | `A ∨ B` | `or` | `orI1`（:92）、`orI2`（:93）、`orE`（:94） |
| `~A` | `¬A` | `imp(A, ⊥)` | 同 `->` |
| `A <-> B` | `A ↔ B` | `and(imp(A,B), imp(B,A))` | `andI` + `impI`/`impE` |
| `forall x. A` | `∀ x. A` | `all` | `allI`（:99）、`allE`（:100） |
| `exists x. A` | `∃ x. A` | `ex` | `exI`（:101）、`exE`（:102-106） |
| `False` | `⊥` | `bot` | `botE`（:97） |
| `True` | — | `imp(⊥, ⊥)` | `impI`/`impE` |

Unicode 別名來自 `GREEK` 表（`lean.js:6`）：

```js
const GREEK = { '∀': ' forall ', '∃': ' exists ', '¬': '~', '∧': '&', '∨': '|', '→': '->', '↔': '<->', '⊥': ' False ' };
```

三個符號對照關係是全書反覆出現的，值得記清楚：

- `~A` 就是 $A \to \bot$ 。解析期就展開（`lean.js:23`：`{ t: 'imp', l: un(), r: BOT }`），核心裡沒有「否定」這種節點。
- `A <-> B` 就是 $(A \to B) \wedge (B \to A)$ 。展開在 `lean.js:17`，`iff()` 每次把累積起來的左邊重新包成 `and(imp(l,r), imp(r,l))`，所以它是右結合的。
- `True` 就是 $\bot \to \bot$ （`lean.js:31`），`False` 就是 $\bot$ （同行的 `if (n === 'False') return BOT;`）。

另外有兩個反斜線別名，但**只有一個真的能用**。`lex()`（`lean.js:7`）寫的是：

```js
const lex = s => s.replace(/[∀∃¬∧∨→↔⊥]/g, c => GREEK[c]).replace(/\\/g, '&').replace(/\\\//g, '|').match(/<->|->|[A-Za-z_][\w']*|\S/g) || [];
```

`String.prototype.replace` 的替換字串裡，`&` 是特殊字元，代表「被匹配到的那段文字」。所以 `.replace(/\\/g, '&')` 的實際效果是「把反斜線換成反斜線」，整條規則等於什麼都沒做。實測結果：`P \/ Q` 會正確變成 `["P","|","Q"]`（因為替換字串 `|` 沒有特殊意義），但 `P \& Q` 會得到 `["P","\\","&","Q"]` 而解析失敗。第 3.2 節把這個 bug 當作「失敗也要記錄」的案例分析過。

## 9.1.3 項、括號與優先序

**項**只有兩種形狀（`term()`，`lean.js:16`）：

| 形狀 | 寫法 | AST |
|---|---|---|
| 變數 | `x`、`h1'`、`socrates` | `{ v: 名稱 }` |
| 應用 | `f(a, b)`、`f(g(a), b)`、`P` | `{ f: 名稱, a: [項...] }` |

識別字規則是 `[A-Za-z_][\w']*`（`lean.js:7` 的詞法正則）：首字元是英文字母或底線，之後可以是英文字母、數字、底線、撇號。

**這裡有一個與 ATP 系統的重大差異值得停下來想清楚。** 在 `lean-prover` 裡，公式中的每一個名字都是**常數**：解析器只把「出現在量詞綁定位置的名字」記進 AST 的 `v` 欄位（`lean.js:28`），而公式裡的 `P(x)` 裡的 `x` 只是 `P` 的一個**參數項**。系統裡沒有「自由變數」這種東西，也沒有型別。所以 `forall x. P(x)` 與 `forall y. P(y)` 在核心眼裡是同一個命題（`key()` 在 `lean.js:56` 把綁定變數一律換成 `#0`、`#1` 來做 $\alpha$ 等價）。第 4 章的 `theorem-prover` 恰好相反：未被量詞綁定的名字會變成零元函數符號，這是那個系統能處理等式推理的關鍵。

**括號**用圓括號，`(` 開頭就一定是一個完整公式（`lean.js:30`）。

**優先序**由解析函式的呼叫鏈決定。`parseF()`（`lean.js:37`）呼叫 `iff()`，`iff()` 呼叫 `imp()`，`imp()` 呼叫 `or()`，`or()` 呼叫 `and()`，`and()` 呼叫 `un()`。呼叫鏈由外而內，因此**綁定強度由鬆到緊**是：

| 強度 | 連接詞 | 結合方向 | 原始碼 |
|---|---|---|---|
| 最鬆 | `<->` | 右結合（特殊展開） | `lean.js:17` |
| | `->` | 右結合 | `lean.js:18` |
| | `\|` | 左結合 | `lean.js:19` |
| | `&` | 左結合 | `lean.js:20` |
| 最緊 | `~`、量詞、括號、原子 | — | `lean.js:21-34` |

四個可以拿來自我檢查的例子：

| 輸入 | 解析結果 |
|---|---|
| `P & Q \| R` | $(P \wedge Q) \vee R$ |
| `P -> Q -> R` | $P \to (Q \to R)$ |
| `~P & Q` | $({\neg P}) \wedge Q$ |
| `A <-> B <-> C` | $((A \leftrightarrow B) \to C) \wedge (C \to (A \leftrightarrow B))$ |

最後一個例子值得停一下：雙條件句被展開成 `and` 之後，外層的 `<->` 看不到內層的 `->` 了，所以 `A <-> B -> C` 的意思是 $(A \leftrightarrow B) \to C$ ，而不是 $(A \leftrightarrow (B \to C))$ 。這是 `iff()` 用 `while` 迴圈累積的必然結果。

## 9.1.4 策略速查表

策略層在 `tactic()`（`lean.js:129-174`）。每一條策略做同一件事：**把棧頂的第一個目標換成新目標，並給它指派一個含有洞（`meta`）的證明項**。目標清單與證明項的填補由 `runThm()` 收尾（`lean.js:209` 的 `inst()`）。

| 策略 | 適用目標 | 參數 | 產生什麼證明項 | 對應核心規則 | 原始碼 |
|---|---|---|---|---|---|
| `intro` | `->` 或 `forall` | 可選新假設名（`->` 預設 `h`，`forall` 預設 `x`） | `impI` 或 `allI` | `impI`/`allI` | `lean.js:139-144` |
| `exact` | 任何 | 一個「假設名 + 項」字串 | `hyp` / `impE` / `allE` 的組合 | 對應三條 | `lean.js:145` |
| `assumption` | 目標與某假設 $\alpha$ 等價 | 無 | `hyp` | `hyp` | `lean.js:146` |
| `apply` | 目標是某命題的結論 | 一個「假設名 + 項」字串 | `impE` | `impE` | `lean.js:147-152` |
| `constructor` | `&` | 無 | `andI` | `andI` | `lean.js:153` |
| `left` | `\|` | 無 | `orI1` | `orI1` | `lean.js:154` |
| `right` | `\|` | 無 | `orI2` | `orI2` | `lean.js:154` |
| `cases h with a b` | `h` 是 `&`、`\|` 或 `exists` | 假設名 + 分支名（預設 `h1`、`h2`） | `let`+`andE1`/`andE2`、`orE`、`exE` | 三條消去規則 | `lean.js:158-164` |
| `exists t` | `exists` | 一個項 | `exI` | `exI` | `lean.js:155` |
| `exfalso` | 任何 | 無 | `botE` | `botE` | `lean.js:156` |
| `by_contra h` | 任何 | 可選假設名（預設 `h`） | `dne` + `impI` | `dne`（:98） | `lean.js:157` |
| `have h : A` | 任何 | 一個命題 | `let`（兩個目標） | `let`（:88） | `lean.js:165-169` |
| `have h := f a` | 任何 | 一個「假設名 + 項」字串 | `let`（一個目標） | `let` | `lean.js:167` |
| `show A` | 任何 | 一個命題 | 不產生（只檢查） | — | `lean.js:170` |
| `sorry` | 任何 | 無 | `sorry` | `sorry`（:86） | `lean.js:171` |

### 「假設名 + 項」的統一語法

`exact`、`apply`、`have h := ...` 都走同一個 helper：`app()`（`lean.js:112-128`）。它把字串拆成「第一個名字 + 後續的一串名字或項」，然後逐段套用：

- 後續的名字**如果剛好是某個假設的名字**，就走 $\to$ 消去（`impE`），前提必須型別吻合（`lean.js:119`）。
- 否則就解析成一個**項**，走 $\forall$ 消去（`allE`），被套用的命題必須是 `forall`（`lean.js:123`）。

判斷順序是「先看是不是假設名，再看是不是項」（`lean.js:116`），所以：

```
exact h socrates m
```

裡的 `h` 是假設名、`socrates` 是項、`m` 是假設名，於是產生 `allE` 再 `impE` 的一段鏈。這就是蘇格拉底三段論範例（`lean.js:237`）一行解決的原因：

```
theorem socrates (h : forall x. Man(x) -> Mortal(x)) (m : Man(socrates)) : Mortal(socrates) := by
  exact h socrates m
```

### 三個容易誤會的策略

- **`constructor` 只認 `&`。** `A <-> B` 在解析期已經展開成 `and`，所以要證雙條件句必須 `constructor` 兩次或 `intro` 後分兩邊處理——錯誤訊息會明說「(↔ 已展開成 ∧)」（`lean.js:153`）。
- **`by_contra` 是古典規則。** 它把目標 $A$ 換成 $\bot$ ，前提是 $\neg A$ ，最後用 `dne`（雙重否定消去，`lean.js:98`）收尾。這個系統是古典邏輯，不是直觀主義邏輯。
- **`have h : A` 產生兩個目標。** 一個是「證明 $A$ 」，另一個是「帶著 $A$ 繼續證原本的目標」（`lean.js:168`）。`have h := f a` 則只產生一個。

## 9.1.6 常見錯誤訊息對照表

下表把 `lean.js` 裡的字串整理成「訊息 → 原因 → 怎麼修」。左欄是實際會看到的原文。

| 訊息 | 觸發位置 | 原因 | 怎麼修 |
|---|---|---|---|
| `找不到假設 h` | `lean.js:85`（核心）、`lean.js:114`（`app`）、`lean.js:134`（策略層） | 假設名拼錯，或它已被 `intro`／`cases` 改名 | 看 `--trace` 印出的上下文清單，照抄名字 |

| `標頭格式:theorem 名稱 (h : 前提) : 結論 := by` | `lean.js:185` | 標頭不符合格式 | 標頭必須在**一行** |
| `前提格式:(名稱 : 命題)` | `lean.js:189` | 前提括號裡沒有冒號 | 補上 `:` |
| `標頭缺少 ":" 與結論` | `lean.js:192` | 括號寫完後沒有 `: 結論` | 補上結論 |
| `看不懂這一行` | `lean.js:200` | 該行的第一個字不是合法的策略名（正則 `/^(\w+)\s*(.*)$/`） | 策略名只能用英文字母、數字、底線 |
| `核心推出的命題與宣告不符` | `lean.js:210` | 策略層交出的證明項推不出宣告的命題 | 這通常是**核心的裁決**，代表策略層有 bug |
| `未知的策略 X` | `lean.js:173` | 策略名拼錯 | 對照 9.1.4 的策略表 |

## 9.1.7 五個狀態燈號

`statusText()`（`lean.js:219-220`）定義了五種狀態。它們的完整判讀流程在第 1.3.3 節，這裡只留速查：

| 狀態 | 燈號 | 一句話 | 原始碼 |
|---|---|---|---|
| `done` | ✔ | 策略跑完、目標清空、核心重算的命題與宣告 $\alpha$ 等價 | `lean.js:211` |
| `sorry` | ⚠ | 核心通過了，但證明項裡混進了 `sorry` 節點 | `lean.js:171`、`lean.js:86` |
| `error` | ✘ | 某一條策略拋出例外，後面的行全部沒跑 | `lean.js:201` |
| `open` | … | 腳本跑完了，但目標棧沒清空 | `lean.js:207` |
| `kernel` | ✘ | 核心拒絕了這個證明項 | `lean.js:212` |

`done` 與 `sorry` 只差一個字，但 `sorry` 的核心**照樣通過**——`check()` 遇到 `sorry` 節點時只是記下 `fl.sorry = true` 然後回傳該目標（`lean.js:86`）。所以 `sorry` 狀態的證明看起來完成，實際上什麼都沒證明。

## 9.1.8 這一節怎麼用

把 9.1.4 的策略表當成「寫策略時的選單」、9.1.6 的錯誤表當成「除錯時的字典」，兩張表都要放在螢幕上。**最有效率的除錯方式永遠是 `--trace`**：它把每一條策略執行完之後的目標上下文全部印出來，而 `intro`／`apply`／`exact` 的失敗幾乎都是「上下文跟我想的不一樣」造成的。你不需要記住每一條錯誤訊息，只要會看目標快照。

下一節處理完全不同的哲學：`theorem-prover` 不接受你給的證明，它自己找證明。
