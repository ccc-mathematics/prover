# 9.2 歸結法證明器：問題檔格式與命令列

`theorem-prover` 與第 9.1 節的 `lean-prover` 哲學相反：你不寫策略，你寫**問題**。它自己搜尋矛盾，找到就報「證明成功」，找不到就報「飽和」。本節說明問題檔長什麼樣、命令列怎麼用、輸出怎麼讀，以及——最重要的——回傳物件裡的每個欄位代表什麼。

## 9.2.1 問題檔格式

問題檔是一個純文字檔，規則只有三條，全部由 `theorem-prover/bin/cli.js:12-23` 實作：

| 規則 | 寫法 | 說明 |
|---|---|---|
| 前提 | 每行一個公式 | 除了 `|-` 開頭的行，其他非空行都是前提 |
| 結論 | `|-` 開頭的行（也接受 `⊢`） | 冒號後面的內容是結論 |
| 註解 | `#` 開頭的行 | 整行忽略 |

```js
function run(lines, name) {
  const premises = []; let goal = '';
  for (const raw of lines) {
    const l = raw.trim();
    if (!l || l.startsWith('#')) continue;
    if (l.startsWith('|-') || l.startsWith('⊢')) goal = l.replace(/^(\|-|⊢)/, '').trim();
    else premises.push(l);
  }
  if (name) console.log(`\n== ${name}`);
  try { console.log(P.format(P.prove(premises, goal || null))); }
  catch (e) { console.log('錯誤:' + e.message); }
}
```

**省略結論**是一個有意義的用法：`goal` 為空字串時，`prove()` 收到的是 `null`，此時它只檢查前提是否互相矛盾。`hasGoal` 欄位會告訴你當初有沒有結論。

三個現成的範例檔：

| 檔案 | 內容 | 會得到什麼 |
|---|---|---|
| `examples/socrates.txt` | 蘇格拉底三段論 | `proved` |
| `examples/barber.txt` | 理髮師悖論，**省略結論** | `proved`（前提自相矛盾，`hasGoal` 為 `false`） |
| `examples/group.txt` | 群論：單位元的反元素是單位元 | `proved`（要走等式推理） |

`examples/socrates.txt` 的完整內容：

```
# 蘇格拉底三段論
forall x. (Man(x) -> Mortal(x))
Man(socrates)
|- Mortal(socrates)
```

`examples/group.txt` 展示了等式推理：

```
# 群論:單位元的反元素是單位元
forall x. mul(e,x) = x
forall x. mul(inv(x),x) = e
forall x y z. mul(mul(x,y),z) = mul(x,mul(y,z))
|- inv(e) = e
```

注意 `forall x y z.` 的**多變數量詞**：變數之間用空白分隔，句點結束（`prover.js:25`）。這與 `lean-prover` 相同，但與 λ-Cube 的 `forall (x : A), B` 完全不同。

## 9.2.2 語法表

解析器在 `parse()`（`prover.js:7-42`）。下表左欄是 ASCII 寫法，中欄是 Unicode 別名，右欄是解析後的 AST 節點。

| 你寫的 | Unicode 別名 | AST 節點 | 原始碼 |
|---|---|---|---|
| `~A` | `¬A` | `not` | `prover.js:22` |
| `A & B` | `A ∧ B` | `and` | `prover.js:19` |
| `A \| B` | `A ∨ B` | `or` | `prover.js:18` |
| `A -> B` | `A → B`（也接受 `⊃`） | `imp` | `prover.js:17` |
| `A <-> B` | `A ↔ B` | `iff` | `prover.js:16` |
| `forall x. A` | `∀ x. A` | `all` | `prover.js:23-28` |
| `exists x. A` | `∃ x. A` | `ex` | `prover.js:23-28` |
| `a = b` | — | `atom`（名字為 `=`） | `prover.js:32-36` |
| `a != b` | — | `not` 包住 `atom`（名字為 `=`） | `prover.js:32-36` |

Unicode 別名表（`prover.js:4`）比 ITP 版本多一個 `⊃`：

```js
const SYM = { '∀': ' forall ', '∃': ' exists ', '¬': '~', '∧': '&', '∨': '|', '→': '->', '↔': '<->', '⊃': '->' };
```

### 變數與常數的分界

這是 ATP 系統與 ITP 系統最要命的差別，也是第 4 章「Skolem 化」與「等式推理」得以成立的前提。`term()`（`prover.js:15`）只看一件事：**這個名字當下有沒有被量詞綁定**。

```js
const term = () => { const n = ident(); if (peek() === '(') { p++; return { f: n, a: args(term) }; } return bound.includes(n) ? { v: n } : { f: n, a: [] }; };
```

| 情況 | 例子 | 結果 |
|---|---|---|
| 被量詞綁定 | `forall x. P(x)` 裡的 `x` | 變數 `{ v: 'x' }` |
| 沒被綁定 | `Man(socrates)` 裡的 `socrates` | 常數 `{ f: 'socrates', a: [] }`（零元函數符號） |
| 零參數謂詞 | `P` | 常數 `{ f: 'P', a: [] }` |
| 帶參數謂詞 | `P(a)` | 函數符號 `{ f: 'P', a: [...] }` |

所以「沒有綁定的名字」不是「自由變數」，而是**零元函數符號**。這個設計讓 Herbrand 展開有了明確的對象：全域的項集合由常數與函數符號組成，量詞綁定的變數則被 Skolem 函數取代。

### 等式的特殊處理

等式不在 AST 裡另設節點，而是被編成一個名叫 `=` 的原子（`prover.js:32-36`）：

```js
if (peek() === '=' || peek() === '!=') { // 等式:t1 = t2 或 t1 != t2
  const neg = T[p++] === '!=', l = a.length || !bound.includes(n) ? { f: n, a } : { v: n };
  const e = { t: 'atom', n: '=', a: [l, term()] };
  return neg ? { t: 'not', f: e } : e;
}
```

三個後果。第一，`a != b` 不是獨立的運算子，它在解析期就被編成 `not(= a b)`。第二，等式是**左中綴**的：`f(a) = g(b)` 的左邊必須是一個原子（可帶參數），不能是任意項。第三，左邊若是量詞綁定的變數，它就會被保留成變數（`{ v: n }`），這是等式推理（paramodulation）能運作的前提。

### 優先序

解析函式的呼叫鏈由外而內是 `iff` → `imp` → `or` → `and` → `un`，因此**綁定強度由鬆到緊**是 `<->` → `->` → `|` → `&` → `~`／量詞／括號／原子。這與第 9.1 節的 ITP 完全一致——因為兩者都要解析同一門一階語言。

| 例子 | 結果 |
|---|---|
| `P & Q \| R` | $(P \wedge Q) \vee R$ |
| `P -> Q -> R` | $P \to (Q \to R)$ （右結合） |
| `~P & Q` | $({\neg P}) \wedge Q$ |

與 ITP 不同的是：**這個系統裡的 `iff` 不在解析期展開**。`prover.js:56` 才在 NNF 轉換時把它展開成 `and(imp(A,B), imp(B,A))`，所以 `parse()` 的輸出裡還看得到 `iff` 節點。

## 9.2.3 命令列用法

四種執行模式，全部由 `theorem-prover/bin/cli.js` 提供：

```bash
cd theorem-prover

node bin/cli.js --demo                        # 內建範例（九個）
node bin/cli.js examples/socrates.txt         # 從檔案讀取
node bin/cli.js -e "forall x. (P(x) -> Q(x))" "P(a)" "|- Q(a)"   # 直接在命令列輸入
cat examples/socrates.txt | node bin/cli.js   # 從標準輸入讀取
```

`-e` 模式（`bin/cli.js:27`）把每個命令列參數當成「一行」，所以 `|-` 前綴的規則跟檔案模式完全一樣：最後一個 `|-` 開頭的參數是結論，其餘是前提。

`--demo` 會依序跑 `prover.js:211-221` 的九個內建範例：

| # | 名稱 | 前提 | 結論 | 預期狀態 |
|---|---|---|---|---|
| 1 | 蘇格拉底三段論 | 2 條 | `Mortal(socrates)` | `proved` |
| 2 | 理髮師悖論（前提矛盾） | 1 條 | 省略 | `proved` |
| 3 | Peirce's law | 無 | `((P -> Q) -> P) -> P` | `proved` |
| 4 | 飲酒者悖論 | 無 | `exists x. (D(x) -> forall y. D(y))` | `proved` |
| 5 | 傳遞關係 | 4 條 | `R(a,d)` | `proved` |
| 6 | 等式代入 | `a = b`、`b = c`、`P(a)` | `P(c)` | `proved` |
| 7 | `f(f(a)) = a` 的推論 | 2 條 | `f(a) = a` | `proved` |
| 8 | 群論：單位元的反元素 | 3 條 | `inv(e) = e` | `proved` |
| 9 | 非定理（應回報失敗） | 無 | `P -> Q` | `saturated` |

`theorem-prover/test/test.js:4` 正是靠名字裡有沒有「非定理」來決定期望值——這是三個專案裡唯一一個**測試失敗案例**的測試。

兩支維護命令：

```bash
npm test        # 跑測試
npm run build   # 修改 src/ 或 web/template.html 之後重新產生 web/index.html
```

`npm run build` 對應 `theorem-prover/scripts/build-web.js`，它做的事只有一句話：把 `src/prover.js` 的內容塞進 `web/template.html` 裡的 `/*PROVER*/` 位置，寫回 `web/index.html`。`src/` 是唯一的真相來源。

## 9.2.4 作為函式庫使用

`prover.js:223` 匯出的 API 是：

```js
const API = { parse, prove, format, statusText, examples };
```

| 函式 | 用途 |
|---|---|
| `parse(src)` | 把字串解析成 AST，回傳 AST 節點；語法錯誤會拋例外 |
| `prove(premises, goal, opts)` | 跑歸結搜尋，回傳結果物件 |
| `format(r)` | 把結果物件轉成可讀文字（狀態行 + 推導鏈） |
| `statusText(r)` | 只取狀態那一行 |
| `examples` | 九個內建範例，每個有 `name`、`premises`、`goal` |

一段可跑的範例程式碼：

```js
const P = require('./src/prover.js');

const r = P.prove(
  ['forall x. (Man(x) -> Mortal(x))', 'Man(socrates)'],
  'Mortal(socrates)'
);

console.log(P.format(r));
console.log('狀態:', r.status, '子句數:', r.generated, '耗時:', r.ms, '毫秒');
```

輸出：

```
✔ 證明成功(產生 6 個子句,2 ms)
  1. ~Man(X2) | Mortal(X2)    [前提]
  2. Man(socrates)    [前提]
  3. ~Mortal(socrates)    [否定結論]
  5. ~Man(socrates)    [歸結 1, 3]
  6. ⊥    [歸結 5, 2]
狀態: proved 子句數: 6 耗時: 2 毫秒
```

`prove()` 的第三個參數 `opts` 有兩個選項（`prover.js:144`）：

| 選項 | 預設值 | 作用 |
|---|---|---|
| `opts.maxMs` | `10000` | 毫秒上限，超過就回報 `timeout` |
| `opts.maxClauses` | `20000` | 產生的子句數上限，超過就回報 `timeout` |

例如給一個難題多一點時間：

```js
const r = P.prove(premises, goal, { maxMs: 60000, maxClauses: 200000 });
```

## 9.2.5 回傳物件的欄位

`prove()` 回傳的物件由 `fin()` 組出（`prover.js:189-197`）：

```js
return { status, steps, generated: gen, ms: Date.now() - t0, hasGoal: !!goal };
```

| 欄位 | 型別 | 意義 |
|---|---|---|
| `status` | 字串 | `proved` / `saturated` / `timeout` 三者之一 |
| `steps` | 陣列 | 從前提到矛盾空子句的**推導鏈**，每一步是一個子句 |
| `generated` | 數字 | 整個搜尋過程中被接受的子句總數（含被剪掉的） |
| `ms` | 數字 | 從進入 `prove()` 到離開的毫秒數 |
| `hasGoal` | 布林 | 當初有沒有給結論 |

`steps` 每一筆的形狀（`prover.js:194`）是 `{ id, text, rule, from }`：

| 欄位 | 意義 |
|---|---|
| `id` | 子句編號，`accept()` 給的遞增序號（`prover.js:150`） |
| `text` | 子句的可讀形式，例如 `~Man(X2) \| Mortal(X2)`；空子句印成 `⊥` |
| `rule` | 產生它的規則標籤 |
| `from` | 產生它所依賴的子句編號陣列（前提與否定結論的 `from` 是空陣列） |

`rule` 的取值由 `fmtRule()`（`prover.js:203`）翻譯：

| 原始標籤 | 顯示 | 意義 |
|---|---|---|
| `premise` | `前提` | 直接由前提子句化而來 |
| `negated goal` | `否定結論` | 由被否定後的結論而來 |
| `resolve` | `歸結 ` | 二元歸結 |
| `factor` | `因子化 ` | 同一子句內兩個互補文字的因子化 |
| `para` | `等式替換 ` | paramodulation，用等式改寫另一子句的子項 |
| `eqres` | `等式歸結 ` | 消去 `t != t'` 形式的文字 |

## 9.2.6 三種結果怎麼讀

### `proved`：找到了矛盾

`prove()` 找到一個**空子句**（`prover.js:152`：`if (!l.length) empty = c;`），也就是 `⊥`。搜尋停止，`status` 是 `proved`。

`hasGoal` 決定狀態行的措辭（`prover.js:205`）：

- `hasGoal` 為 `true` → `✔ 證明成功`：被否定後的結論與前提一起矛盾了，所以結論是前提的邏輯後果。
- `hasGoal` 為 `false` → `✔ 前提互相矛盾`：你沒給結論，系統只是發現前提彼此衝突。理髮師悖論就是這種情形。

### `saturated`：搜完了，沒找到矛盾

被動子句集（passive）清空而仍無空子句（`prover.js:161`：`if (!passive.length) return fin('saturated');`）。狀態行是：

```
✘ 無法證明:子句集已飽和,結論不是前提的邏輯後果
```

**這不是反例。** 嚴格來說，它只代表「在目前的時間與子句數上限內沒找到矛盾」。第 4.6 節說明剪枝如何讓飽和提早發生——被剪掉的子句有可能正是通往矛盾的那一步。要判定「真的不是邏輯後果」，需要配合 Herbrand 定理（第 2.4 節）以及一個更完整的飽和策略。

### `timeout`：撞到上限

時間或子句數超標（`prover.js:162`）：

```js
if (Date.now() - t0 > maxMs || gen > maxN) return fin('timeout');
```

狀態行是 `… 超過時間或子句數上限,結果未知`。它同時可能是「可證但太難」或「根本不可證」，**不能**當成否定證據。

### 怎麼讀 `steps`

`steps` 不是搜尋的全部歷程，而是**從空子句回溯出來的一條最短證明鏈**。`fin()`（`prover.js:190-195`）從空子句出發，沿 `from` 欄位往回走，把走到的所有子句依編號排序後輸出。

所以讀法是**由下往上**：

1. 最後一行通常是 `⊥    [歸結 a, b]`，它是整條鏈的終點。
2. 每一行的 `from` 指向它的「原料」。
3. `前提` 與 `否定結論` 是鏈的兩端起點——一端是你的前提，另一端是被否定後的結論。

以蘇格拉底三段論為例：

| 步 | 子句 | 規則 | 讀法 |
|---|---|---|---|
| 1 | `~Man(X2) \| Mortal(X2)` | 前提 | `forall x. (Man(x) -> Mortal(x))` 子句化後的結果 |
| 2 | `Man(socrates)` | 前提 | 第二條前提 |
| 3 | `~Mortal(socrates)` | 否定結論 | 結論 `Mortal(socrates)` 被否定 |
| 5 | `~Man(socrates)` | 歸結 1, 3 | 把 `Mortal(X2)` 與 `~Mortal(socrates)` 歸結，得到 `~Man(socrates)` |
| 6 | `⊥` | 歸結 5, 2 | `~Man(socrates)` 與 `Man(socrates)` 歸結，得空子句 |

注意編號不是連續的（1、2、3、5、6）。跳號代表中間產生過別的子句，但它們沒被用到——**推導鏈只保留必要的部分**，這是歸結法證明的可讀性所在。

另外兩個顯示上的小細節：`pv()`（`prover.js:201`）把內部產生的變數名 `_1`、`_2` 改寫成 `X1`、`X2` 讓人看得懂；`format()`（`prover.js:208`）用 `padStart(3)` 對齊編號。

## 9.2.7 這一節怎麼用

寫 ATP 問題時遵守三條守則：**一是每個前提寫一行**，不要用換行續寫（換行會被當成兩個前提）；**二是結論一定要用 `|-` 前綴**，忘了寫它就變成「檢查前提是否矛盾」；**三是不要把 `saturated` 當成反例**，它只代表沒找到。

讀結果時先看 `status` 行，再看 `steps` 的最後一行是不是 `⊥`——是的話，`proved` 是可信的；不是的話，`steps` 會是空的，這本身就是「沒證成」的資訊。

下一節是最年輕的那個系統：λ-Cube 裡沒有「命題」這種東西，只有型別。
