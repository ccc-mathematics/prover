# 9.4 原始碼索引與延伸閱讀

本節是全書的查詢入口：前半段把三個 `src/*.js` 的每一個主要函式整理成一張「行號 → 職責」對照表，讓你可以從書上看到的任何一個概念反查它在程式碼裡的落點；後半段是延伸閱讀與一張「從本專案走向真實系統」的對照表。最後以一段結語收束全書。

## 9.4.6 從本專案走向真實系統

下表把本專案的每一塊拼圖，對應到真實系統裡的哪一個部分。這是第 8 章的浓缩版，也是「這個玩具如果要長大，該往哪裡長」的施工圖。

| 本專案的做法 | 對應真實系統的哪個部分 | 缺什麼、要怎麼補 |
|---|---|---|
| `lean.js` 的 `check()`（80-109） | Lean／Coq／Agda 的 **kernel type checker** | 真實核心要處理 de Bruijn 索引、η 等價、universes；Lean 把它寫成 Rust 以求效能 |
| `S.goals` 目標棧（194） | Lean 的 tactic framework、Coq 的 proof state | 真實系統要支援多目標並行、`all_goals` 與 focus 切換 |
| `meta` 洞與 `inst()`（87、177） | Lean 的 metavariable、`MetaM` 與 unification | 真實系統用**單一賦值 metavariable 求解**取代預先綁定 |
| 策略 `intro`／`apply`／`cases` | Lean 的同名 tactic | 真實系統的 tactic 要回傳 `Lean.Elab.Tactic.Syntax`，並支援重寫與 unification 產生的洞 |
| `by_contra` 與 `dne`（157、98） | Lean 的 `Classical.byContradiction` | 真實系統把古典邏輯放進一個獨立的 type class，不讓它污染核心 |
| `sorry` 與 `fl.sorry`（86、171） | Lean 的 `sorry`（編譯期警告） | 真實系統不允許 `sorry` 進入正式建置 |
| `prover.js` 的 `prove()`（143-198） | Vampire／EProver 的 saturation loop | 真實系統有 term indexing、mode selection、SAT 求解器的整合 |
| `clausify()`（74） | Vampire 的 clausification（NNF + Skolem + CNF） | 真實系統處理 equational reasoning 的 **ordered rewriting**（預設把等式當成規則） |
| `unify()`（79-86） | Robinson 一致合一、Prolog 的合一 | 真實系統要處理 occurs check 的效率（term indexing） |
| `subsumes()`（104） | Vampire 的 subsumption 與 set-of-support | 真實系統還要加「反向 subsumption」與 literal selection |
| `para()`（128） | E-equations / paramodulation | 真實系統需要項排序與化簡，否則等式推理會爆炸（README 明確寫了這個限制） |
| `cube.js` 的 `infer()`（94-115） | System F 與 Calculus of Constructions 的型別檢查器 | 真實系統要處理 universes 與 cumulativity |
| `CUBE` 表（5-6） | Barendregt 的 λ-Cube | 真實系統（Coq）只實作其中一個頂點，加上歸納型別與 universes |
| de Bruijn 索引（`shift`／`subst`／`inst`） | Coq、Agda、Lean 的項表示 | 真實系統多用**具名項**（Lean's `Expr`）以利錯誤訊息 |
| Church 編碼（`def And`、`def Or`、`def Ex`） | System F 的 Church 編碼；Coq 的 `Inductive` | 真實系統用歸納型別，因為 Church 編碼的消去規則不夠用 |
| 沒有歸納型別 | Coq 的 `Inductive`、Agda 的 `data` | 第 8.1 節：加入歸納型別是最大的單一擴充 |
| 沒有宇宙階層 | Coq 的 `Type@{i}`、Lean 的 `Type u` | 第 8.1 節 |
| 沒有 η 規則 | Lean／Coq 的 η 轉換 | 第 5.5 節：`conv` 需要加一條 η 規則才完整 |
| 沒有隱含參數 | Coq 的 implicit generalization、Lean 的 auto-bound implicit | 需要 unification 支援 |
| `def` 不能遞迴 | Coq 的 structural recursion、Agda 的 termination checker | 需要守衛性檢查或大小遞減 |
| `theorem` 不透明 | Lean 的 `theorem` 不透明、`def` 透明 | 這個區別本專案已經做對了，可以直接沿用 |

## 9.4.7 全書結語

三個程式教會我們的事情，可以濃縮成三句話。

**第一，可信核心可以很小。** `lean.js` 的 `check()` 是 30 行，`cube.js` 的 `infer()` 是 22 行，`prover.js` 的整個引擎不到 60 行。這個專案從頭到尾只做了一件事，就是把「相信我」的面積壓到最小：策略層可以寫錯，寫錯了只是拿不到 ✔；核心不行，核心是唯一的裁判。第 7 章談的 De Bruijn 準則不是信仰，是架構——而架構是可以用行數衡量的。

**第二，可讀的證明項是可能的，而且值得追求。** `lean.js` 的 `sx()` 與 `prover.js` 的 `format()` 做的事情，是把機器內部的資料結構重新變成人可以讀的推導鏈。一個證明如果只有核心看得懂，那它就只證明了「某個東西成立」，沒有證明「那個東西就是我想說的那件事」。第 6 章比較三種系統對同一批數學的推理鏈，就是為了讓這件事看得見。

**第三，形式化是有代價的，而且代價是可以盤點的。** 這個專案的每一個限制都是一筆明碼標價的帳：λ-Cube 沒有歸納型別，所以你得用 Church 編碼硬寫 ∧ 與 ∨；`theorem-prover` 沒有項排序，所以群論那題要走等式替換；`lean-prover` 沒有自由變數，所以「對所有 $x$ 」永遠得靠 `intro` 顯式引進。盤點這些帳目，就是第 8 章存在的理由——知道代價在哪裡，才知道真實系統的每一個複雜度是買了什麼。

感謝你讀到這裡。三個程式加起來不到 750 行 JavaScript，卻剛好踩在現代邏輯學的三條主幹上；它們不是玩具，是可以讀完、可以改寫、可以延伸的最小完整實作。下一步很簡單：挑一個你原本用自然語言證明的定理，用這三個系統裡的任意一個把它寫出來，然後看它在哪裡卡住——卡住的地方，就是真實系統存在的理由。
